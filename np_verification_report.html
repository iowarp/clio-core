Does the NeuroPress port decide the same way?

One gibibyte generated on the GPU, written through the Clio HDF5 VOL in 256 chunks, then replayed byte-for-byte through the original NeuroPress. Every selection, statistic and artifact compared.

256 chunks 4 MiB each 1.00 GiB total frozen weights lossless

With the model's weights frozen, a chunk's selection is a pure function of its own statistics. Order drops out, concurrency drops out, and any disagreement between the two implementations would be a real defect rather than a scheduling artifact. That is what makes this the configuration worth measuring.

Integrity: is the data actually restored?

Yes. Clio decompresses its own 256 compressed blobs back to the source byte for byte, and NeuroPress decodes those same payloads to the same result. Establishing it took more than the obvious check, because the obvious check was measuring the wrong thing.

What the H5Dread round trip did not show

Clio’s own read reported the dataset restored exactly, and the bytes did match — but it never decompressed anything. On reopen the VOL’s coherence check finds no stamp blob, drops the cache tag, and the read falls through to “native read is the source of truth”: the uncompressed HDF5 copy the VOL also writes.

The run log says so plainly — DelTag successful … removed 1 tags, 256 blobs some 5,000 lines before the read, zero Decompress tasks for the whole run, and every chunk appearing twice in the selection log because a miss re-stages what it just read.

So that check verified HDF5 fidelity, not the compressor. The rows above replace it: the compressed blobs are still live between that close and the reopen, so they are handed straight to AsyncDecompressExplicit — the same call the VOL’s own cache-hit path makes — and separately to NeuroPress’s decoder.

A consequence worth separating from the port’s correctness: because no stamp is written at close, the tier is dropped on every reopen, so a compressed read is never served and each read re-compresses all 256 chunks to re-stage. That is also why reads take 25–40 s against 1.9 s for the write.

What did not: the compressed byte stream

The two produce compressed payloads of identical length that decompress to identical data, but the bytes themselves differ for most chunks. This is not a difference between the two implementations — it is a property of the codec both of them call.

The same binary does this to itself

Running the native replay twice over the identical 256 chunks, changing nothing but the order they are fed in, reproduces the same breakdown: ANS 0/191 byte-identical, Cascaded 41/57, LZ4 8/8 — the Clio-vs-native figures to within two chunks.

Clio compresses chunks concurrently across worker threads, each holding its own manager cache, so a given chunk meets a compressor with a different history than a sequential replay gives it. That difference in history is the entire effect.

What it is not

Each of these was tested, not assumed:

  • Stale output memory. Zeroing the output buffer before every compress changes nothing — 0 of 256 outputs change.
  • A configuration difference. Both pass chunk size 1 << 16, the same default opts, and the same NVCOMP_TYPE_CHAR override for Cascaded — and both link the identical libnvcomp.so.5.3.0.16.
  • Preprocessing. Byte-shuffle is set on every one of these chunks, including the eight LZ4 chunks that match exactly.

What it mostly is

Flushing nvcomp’s manager cache before each chunk takes ANS from 0/191 to 137/191 byte-identical, so the retained manager carries most of it. The residual 54 points at device scratch a fresh manager still inherits from allocator state — not something either project controls.

The byte diff agrees. For one ANS chunk, 487 bytes of 3,500,752 differ — 0.014%, in 253 runs of one or two bytes, with identical headers and identical bulk stream. That is per-block encoder state, not a different encoding.

Across every order and manager policy tried, payload size, selection, achieved ratio and MSE were unchanged. nvcomp’s ANS and Cascaded encoders are simply not byte-reproducible across call histories, and nothing downstream depends on it — every stream decompresses exactly.

How it was measured

Clio generates the dataset on the GPU and writes it through the HDF5 VOL, where the compressor chimod selects a configuration per chunk and logs it. The same run dumps the exact bytes it compressed. The replay driver feeds those bytes to NeuroPress's own gpucompress_compress_gpu() with ALGO_AUTO, in the order Clio completed them, and logs its own selections in the same schema.

Both sides hash the chunk they actually handed to the compressor, so the shared-input claim is measured rather than assumed — Clio stages device-resident chunks to host purely to do it. Statistics come from the code path that ranked on them, not from a separate snapshot, and the native figures come from gpucompress_compute_stats_gpu().

The same pipeline run with online learning enabled reaches 172/256 routing agreement. That divergence is expected, not a defect: the VOL completes chunks concurrently and out of order, so after the first weight update the two are no longer scoring with the same model, and a sequential replay cannot reproduce the interleaving.
