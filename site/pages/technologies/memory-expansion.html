What it is

A paged vector looks like a normal array to the code that uses it. Its contents are split into pages (from 64 KB to several MB, chosen per vector) that are stored as CTE blobs. A GPU block asks for the pages it is about to touch (CoFetch, CoHoldPage), works on them in device memory, and flushes the pages it changed (CoBeginFlush, CoEndFlush). Pages that do not fit in the device cache spill to the next tier: host RAM, NVMe, or another node's memory. The cache size is a parameter, so the same code runs with the whole dataset resident or with a fraction of it.

  • Larger than memory. A dataset is bounded by the tier stack, not by GPU memory or host RAM.
  • One namespace across nodes. A rank reads another node's pages by name, so many codes that used halo exchanges or collectives become plain reads and writes.
  • Compression on the fault path. Pages can be LZ4-compressed as they leave the fast tier, which trades CPU for capacity when the data no longer fits.
  • Portable. The same kernels compile for CUDA and SYCL, and were measured on NVIDIA laptop and A100 GPUs and on Intel GPUs; cpu_vector gives host code the same paging.

Against MPI, oneCCL and Intel SHMEM

The hardest comparison for a paging system is hand-written message passing, where the programmer moves exactly the bytes that are needed. Four very different workloads were rewritten on gpu_vector and run on Aurora (Intel Data Center GPU Max, one tile per rank) against MPI, oneCCL and Intel SHMEM versions of the same code. Ratios below 1 mean the paged version is faster.
