The composable I/O stack

A data-intensive pipeline moves the same bytes through several systems: a simulation writes checkpoints, an analysis job reads them back, a model trains on them, an agent searches them. Each hop usually means a different storage system, a copy and a format. CLIO Core replaces those systems with one runtime and a set of modules you compose, so every hop shares the same substrate.

Basic principles

  • Everything is a module. Storage devices, the blob engine, caches, filesystems and even machine-learning algorithms are modules (ChiMods), shared libraries the runtime loads at startup.
  • A module runs as a pool. A pool is a named instance of a module, addressed by a numeric pool_id, with one container on each node it spans. Two pools of the same module can run side by side with different settings.
  • Work is a task. Clients submit tasks to a pool over shared memory, TCP or sockets; worker threads run them as coroutines, so a task that waits on I/O or another pool never blocks a thread.
  • The stack is a YAML file. The compose list names the pools to create, in order, with each module's own settings. Changing the stack means editing that list, not the code.

Pool queries: choosing where work runs

Every task carries a pool query that tells the runtime which containers of the pool should run it. The same module code can then serve one node or a whole cluster.

  • Local: the container on this node. Used for node-local work and by default in the compose list (pool_query: local).
  • DirectId, DirectHash, Physical: one container, chosen by id, by hashing a key, or by node.
  • Range, Broadcast: many containers, or all of them.
  • Dynamic: the module decides per task. The CTE routes each blob to the node that owns it; the cache routes to the caller's own node.
  • ManyToOne, AllToOne: collectives. Tasks from many containers are batched at one leader, run once, and the result is sent back to all of them; AllToOne waits for every container, like a reduction.

Data operators

Data-path modules form an interposition chain. Each operator speaks the storage engine's interface, receives its calls, handles the ones it cares about and forwards the rest to its next_pool_id. Because the interface is the same above and below, an operator can be inserted or removed without touching the modules around it, and everything above it (the FUSE mount, the Python API, other operators) works unchanged.

filesystem 560.0 → your operator 600.0 → cache 563.0 → indexer 564.0 → replication 561.0 → core 512.0

An operator is a C++ class whose handlers are coroutines. This one counts the bytes written to each tag: it forwards the write down the chain, waits for it, and counts it only if it succeeded.

class Runtime : public clio::cte::core::CoreInterposer {
 public:
  clio::run::TaskResume PutBlob(
      clio::run::shared_ptr<clio::cte::core::PutBlobTask> &task) {
    CLIO_TASK_BODY_BEGIN
    CLIO_CO_AWAIT(ForwardToCore(clio::cte::core::Method::kPutBlob,
                                task.template Cast<clio::run::Task>()));
    if (task->GetReturnCode() == 0) CountBytes(*task);  // after it succeeded
    CLIO_CO_RETURN;
    CLIO_TASK_BODY_END
  }
  // ...
};
CLIO_TASK_CC(Runtime)   // export the module from the shared library

Build it outside the CLIO Core tree, point CLIO_REPO_PATH at the library, and add it to the chain:

compose:
  - mod_name: clio_demo_bytecount
    pool_name: bytecount
    pool_query: local
    pool_id: "600.0"
    next_pool_id: "563.0"     # forward to the cache

What you can build

Because a module is just code the runtime hosts, the same mechanism scales from a few lines in the storage path to an entire application.

  • The storage layer. A new block-device type or a module attached as a tier puts data somewhere new: another device, an object store, a remote service. A placement policy changes where data lands and when it moves. See Extend the storage system.
  • Data operators in the I/O path. Encryption, deduplication, format conversion, auditing or custom caching, applied to every write and read that passes through, with no change to the application.
  • In-transit analytics. An operator sees data as it is written, so it can index, summarize, reduce or check it before it ever lands, with the collective pool queries to combine results across nodes. The indexer and summarizer are built this way.
  • Full workloads. Whole computations can run as modules next to the data they use. The clio-ml algorithms (k-means, ALS, gradient-boosted trees, CNNs and more) are modules that train out of core on data the stack already holds.
