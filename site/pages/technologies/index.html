Beyond message passing

MPI is the standard way to write parallel programs: a fixed set of ranks is launched together, exchanges messages and collectives, and exits together. That model fits a single simulation. It fits less well when one data set passes through a simulation, an analysis service, a model and an agent, each with its own lifetime, and when data must also move between memory, local disks and cloud storage.

The Context Runtime starts from a different unit. Instead of ranks, it hosts modules as long-lived pools on every node. Instead of messages, clients submit tasks to a pool, and the runtime decides which node runs them, on which worker, and over which transport. The same runtime moves bytes over the network and onto storage, so a transfer to another node and a transfer to an NVMe tier or an S3 bucket go through one interface.

  • MPI: processes and messages; fixed membership; a rank failure usually ends the job; storage is a separate library.
  • Context Runtime: modules and tasks; nodes can be added and pools created or destroyed while it runs; clients survive restarts; network and storage paths share one abstraction.

The two coexist. An MPI application can keep its ranks and use the runtime underneath for I/O, checkpoints and memory expansion.

Diverse transfer paths

A task reaches its module over the cheapest path available, without the caller choosing it.

  • Within a node: shared-memory rings, or a Unix socket when shared memory is unavailable. Code already inside the runtime hands tasks over directly, with no serialization.
  • Across nodes: TCP, with small messages on a latency lane so probes and acknowledgements never wait behind large transfers.
  • From GPUs: GPU kernels can submit tasks themselves, through a GPU queue served by the runtime.
  • Into storage: block devices for RAM, pinned and GPU memory, files and asynchronous I/O, Amazon S3 and Google Cloud Storage, and erasure-coded arrays built from any of them, with GPUDirect Storage support.

Abstractions

  • Modules (ChiMods) are shared libraries that define a set of methods. Storage, caching, replication, filesystems, search and machine-learning algorithms are all modules.
  • Pools are running instances of a module, with one container on each node. Two pools of one module can run side by side with different settings.
  • Tasks are method calls on a pool. Handlers are coroutines, so a task that waits on I/O or on another pool frees its worker thread.
  • Pool queries say where a task should run: this node, one container chosen by key, a range, every container, or wherever the module decides. Collective queries batch tasks from many nodes, run them once and return the result to all of them.
  • Interposition lets a module stand in front of another and forward what it does not handle. Caching, replication, compression and indexing are added this way, without changing the modules above or below.

Dynamic recomposition

The stack is described by a compose file, a list of pools and their settings. The runtime creates them at startup, and clio_run compose start and compose stop create or destroy the pools in a compose file while the runtime keeps serving. New modules are discovered from a library path, so an operator built outside the tree can be added to a running deployment. Pools are recorded in a durable registry, so a restarted node brings its composition back.

Scheduling

Each node runs a pool of worker threads with roles: scheduling, network send and receive, a GPU queue, and I/O workers in cost classes. Tasks are mapped by predicted cost, learned from observed run times: large I/O is spread across I/O workers, cheap tasks run inline, and everything else goes to the least-loaded worker in its class. A monitor moves the queue of a worker stuck on one task to a fresh worker, grows a class whose workers are saturated, and retires idle extra workers.

Elasticity

Nodes can be added to a running cluster. When a node is registered, every module's containers receive an Expand callback so they can re-partition data or update routing. Containers can be migrated to another node through a Migrate callback, and after a node is lost, a Recover callback rebuilds a container elsewhere from replicas or checkpoints, with ScheduleRecover letting the module pick where. Container ids are fixed by the host list, so hashing stays stable while nodes come and go.

Failure detection

  • Restarted peers are detected from an incarnation number on every message; requests in flight to the old incarnation fail promptly and are retried.
  • Silent peers are probed, and declared dead after 30 seconds of silence. Requests to them fail after a timeout, or immediately in fail-fast mode.
  • Clients detect a lost runtime with a heartbeat, wait for it or fail over to another node, reconnect and resend. The runtime, in turn, survives clients that die.
  • Data survives node loss through the replication module, not through the runtime alone. A gossip detector exists but is off by default, because at large scale wide collectives starved its probes.

Runtime design covers each mechanism and its tradeoffs, and the Context Runtime docs show how to build a module.

How the numbers on these pages were measured

Every figure on the technology pages comes from a benchmark in the repository, with its hardware and its caveats. Where a comparison favors another system, the page says so. Most runs are single runs on one machine or a small allocation; treat them as measured examples, not guarantees for your hardware. Each page links the source document so you can rerun it.
