Key takeaways

  • Mount it like any other directory on Linux, macOS and Windows through FUSE. Applications run unchanged.
  • Files spread across the tiers you compose (RAM, NVMe, erasure-coded arrays, Amazon S3 or Google Cloud buckets) by score, with distributed metadata and no metadata server.
  • Every file is also tags and blobs in the Context Transfer Engine, so search, assimilation and the other technologies use it without a copy.
  • 10 µsstat from the shared-memory mirror
  • 0metadata servers: inodes are homed by path
  • 3 OSesone FUSE daemon for Linux, macOS and Windows
  • N + Mdrives in an erasure-coded array that grows in place

What it is

Context FS is a product of CLIO Core, not the whole of it. It is the filesystem adapter (clio_cte_fuse) plus the filesystem module, composed over the Context Transfer Engine. Directories, inodes and file data are all stored as CTE tags and blobs, so the filesystem inherits tiering, replication, durability and indexing from the engine, and has no central metadata server: each inode is homed on a node by its path.

FUSE on every desktop and cluster

$ clio-run start &
$ mkdir -p ~/clio-mnt
$ CLIO_WITH_RUNTIME=0 clio_cte_fuse ~/clio-mnt -f &
$ cp -r ./results ~/clio-mnt/
$ ls ~/clio-mnt/results

One daemon mounts on all three operating systems with each platform's native driver:

  • Linux: libfuse3, included in the pip wheel.
  • Windows: WinFsp (FUSE 3 compatibility layer), mounted as a drive letter, included in the pip wheel.
  • macOS: macFUSE, or FSKit on macOS 15.4 and newer; build from source.

Writes go straight through, so a file's size is exact as soon as write() returns. Attribute and negative-lookup caches last 1 s, and a shared-memory mirror answers stat without a round trip to the runtime. See the Linux, macOS and Windows tutorials.

Tiering

Each tier in the YAML gets a capacity and a score between 0 and 1. New data lands on the fastest tier with room; data you stop touching is demoted to slower, larger tiers, and a replica on a persistent tier keeps files across restarts.

  1. ram::hotDRAM, for the working setscore 1.0
  2. /mnt/nvmeLocal NVMe, for staged datascore 0.9
  3. safe_bdevErasure-coded array of disksscore 0.4
  4. s3:// · gs://A bucket as the capacity tierscore 0.1

Compose local tiers walks through a full configuration, and Placement and tiering explains the policy.

Expandable RAID with safe_bdev

safe_bdev is a block device made of other block devices. It protects data with Reed-Solomon erasure coding: for N drives that must survive f simultaneous failures it uses k = N − f data drives and m = f parity drives, so 8 drives surviving 2 failures is RS(6, 2) with 25% overhead. Unlike a classic RAID array, it grows in place:

  • Add drives at runtime as data or parity members (safe_bdev_add_bdev). New blocks are allocated round-robin over the members that have room, so total data capacity is the sum of the members' capacities and an added drive's space is usable immediately, even when the array was already mostly full.
  • Mixed sizes. Each member fills to its own capacity; stripes narrower than k are protected as mirrors until enough members have written into them.
  • Replace and rebuild. Remove a failed member and name a replacement; the runtime rebuilds its shards while the filesystem stays mounted, and the dashboard shows recovery progress.

The array is an ordinary tier, so Context FS on top of it needs no changes. The cr_safe_bdev_integration_docker test composes three data drives and one added parity drive under a mounted Context FS, removes a member, rebuilds it, and checks that the data still reads back.

Amazon S3 and Google Cloud as tiers

The block device module has S3 and Google Cloud Storage transports, so a bucket can be a tier like any disk. Give it the lowest score and only data the organizer demotes reaches it. Separately, the assimilation engine imports existing s3:// and gs:// objects, including anonymous reads of public buckets. The cloud storage tutorial covers both.

About 91% of each operation's wall time is kernel transit; the daemon itself spends about 9.6 µs of CPU time per operation.

Against OrangeFS on Ares: IO500

IO500 on 4 and 8 nodes of the Ares cluster, 8 MPI ranks per node. Each node: two Xeon Silver 4114 (40 cores), 46 GB of memory, a Toshiba RD400 NVMe drive and 40 GbE. Every node is both a server and a client of the filesystem under test, and both filesystems ran back to back on the same nodes in one allocation (ares-comp-21 to 23 and 25 for 4 nodes; ares-comp-11 to 16, 30 and 31 for 8; the two nodes whose NVMe drives write at a third of the others' speed were left out).

  • Context FS: release build of cte-shm-cache (a6b70f12c), 20% DRAM / 80% NVMe per node: a 3 GB DRAM tier, pre-faulted at start, over a 12 GB NVMe tier, no replication. The shared-memory metadata cache and the write-back cache over the DRAM tier are on, as in the default configuration.
  • OrangeFS 2.10 (f4854f7): every node a metadata and data server, mounted through pvfs2fuse, all storage on the NVMe drive, TroveMethod directio, so OrangeFS reaches its device with O_DIRECT, as Context FS's file tier does.
  • IO500 (5c2237d) with a 60 s stonewall and data capped at about 27 GB, so most data lands on NVMe. These are not valid IO500 list submissions, which need a 300 s stonewall. One run per system and scale.

Context FS scores 3.3x OrangeFS on 4 nodes and 3.2x on 8. It leads on every ior write and file-per-process read and on every create, stat, read and find phase except one: by 7-17x on stat and over 500x on find, which Context FS answers from its directory tables. On 4 nodes OrangeFS reads the single shared ior-hard file slightly faster (0.213 vs 0.201 GiB/s); on 8 nodes Context FS leads it (0.590 vs 0.403). mdtest-hard write is 6% ahead on 4 nodes and 9% behind on 8. Deleting the small mdtest-hard files is the remaining weak point: 0.59-0.82 thousand per second against 0.68-1.31 for OrangeFS.

Two things in this setup cost OrangeFS bandwidth. directio keeps the server page cache from standing in for the device, and pvfs2fuse uses the FUSE 2 API, which splits writes into pieces of at most 128 KiB, so a 2 MiB IOR transfer reaches the device as 16 synchronous writes. OrangeFS through its kernel module, or with its default buffered alt-aio method, would post higher bandwidth. pvfs2fuse also needed a four-line fix: when several nodes create the shared ior-hard file at once, the losers got EEXIST from an open(O_CREAT) without O_EXCL, which aborted IO500 on NVMe every time. The patched client opens the existing file instead, as POSIX requires.

Against DAOS and Flare on Aurora: IOR read bandwidth at 128 nodes

IOR on 128 compute nodes of Aurora, 16 ranks per node (2,048 ranks), in four access patterns. Each system reads its data for 60 seconds, and each rank reads data written by another node. Every read uses direct I/O (--posix.odirect), so the kernel page cache serves nothing and each system is measured on its own data path.

  • Context FS: build of clio-cache-cow-cost-models (PR #1376, 33fedf5de). The shared-memory cache holds file data over write-through, with a DRAM tier twice the size of the data over a DAOS tier reached natively through libdfs. CLIO_FUSE_ODIRECT=1 makes the FUSE mount honor O_DIRECT.
  • DAOS: a POSIX container in the same pool, mounted with dfuse.
  • Context FS and DAOS each read a 256 GiB footprint. Flare (Lustre) ran in a separate job with a 96 GiB footprint because of the project's storage quota, so its numbers are a rough comparison, not a matched one.

Scientific workflows on Aurora: WfCommons at 256 nodes

Three I/O-heavy workflows from WfCommons, generated with WfBench from the recipes of real runs and executed by Parsl on 256 Aurora nodes (16 workers per node, 4,096 task slots). Every task does a token amount of CPU work, so the run time is the workflow's I/O and its dependencies. Each task checks the size of every file it reads and writes; all tasks completed on all three systems, with no short or stale files.

WorkflowTasksFilesRead by tasksWritten by tasks

Epigenomics (genome sequencing)7,99721,964181 GB41 GB
SRASearch (sequence search, file sizes scaled to one tenth)3,9976,064194 GB194 GB

Context FS ran this module composition on every node, with the write-through cache:

  • Filesystem (clio_cte_filesystem, pool 560): the FUSE mount's directories, inodes and file pages, writing through the shared-memory cache.
  • Shared-memory cache (core_shm_cache_writethru, pool 568): a 32 GB segment holding file data, which every process on the node reads and writes directly; it flushes to the policy cache below, eight batches in flight.
  • Write-through policy cache (core_persist_write_thru, pool 567): every write goes to both cores below before it completes.
  • Volatile core (clio_cte_core, pool 540): DRAM, 512 MB reserved for filesystem metadata plus a data tier sized at eight times the node's share of the workflow.
  • Persistent core (clio_cte_core, pool 512): a DAOS tier of the same size per node, reached natively through libdfs in the same pool DAOS dfuse used.
  • Stream (clio_cte_stream, pool 565) for appends; nodes talk over Thallium on Slingshot (ofi+cxi).

DAOS mounted a POSIX container of the same pool with dfuse, and Flare ran on Lustre directly. The build is the one merged in PR #1376 (2999d5b0e).

Checkpointing a simulation through the tiers

From the Eternia paper's evaluation: Gray-Scott on 2 Aurora nodes, 8 steps, a checkpoint every 2 steps. Each checkpoint is a copy-on-write snapshot that CLIO Core drains down the tier stack in the background, in a layout the HDF5 VOL can read. It is compared with a conventional synchronous checkpoint, in which the simulation waits until the snapshot reaches persistent storage; in the Lustre-heavy composition that is a simulation writing its checkpoint to the parallel file system. Total runtime in seconds, lower is better.

The asynchronous snapshot is 15-25% faster in every composition. Persisting the grid four times still moves 25-62 s of data against 10-48 s of computation; the snapshot lets that traffic proceed in the background instead of blocking the run on the slowest tier. For a science application at larger scale, see the Gray-Scott comparison against DDN, Hermes and cuFile.

Against NTFS on a Windows workstation

The same Python script (1 GiB written in 1 MiB writes and fsynced, read back, then 2,000 files of 4 KiB created, stat'ed and listed) on an NTFS directory and on a Context FS mount at Z:. Release build of dev (f88db54bf), default runtime configuration bound to 127.0.0.1, WinFsp 2.0. Ryzen 7 3800X, 32 GB RAM, WD Black SN850X NVMe. Bars are the mean of two runs.

Bars are the mean of two runs; the two runs were within 1,081-1,258 vs 2,347-3,838 MB/s for writes and 2,122-2,278 vs 965-1,354 MB/s for reads (NTFS vs Context FS).

Read the write result carefully: in this run the runtime registered a single storage target, the DRAM tier, so Context FS writes landed in memory and were not on disk when fsync returned, which NTFS guarantees. With a persistent disk tier active, writes also pay for the replica. Reads, file creation and metadata cross the WinFsp kernel boundary on every call, which is where NTFS leads. Defender real-time scanning was on for both. Single machine, two runs each.

Build from source

A source build has many settings and configurations to optimize the installation for your specific system. We keep an INSTALL.md in the root of the repository, written to help AI agents install CLIO Core. The default installers include Context FS on Linux and Windows. Build from source to mount on macOS, or to tune the build for your machine. To have a coding agent do it, give it a prompt like this:

Clone https://github.com/iowarp/clio-core and follow INSTALL.md to build CLIO Core
from source on this machine with the FUSE mount enabled
(-DCLIO_CTE_ENABLE_FUSE_ADAPTER=ON). Install the system packages it lists for my
OS, then start the runtime, mount a test directory and copy a file through it
to verify the install.

The agent should name the options it chose for your system; the install page lists the options that matter here.
