What it is

Context FS is a product of CLIO Core, not the whole of it. It is the filesystem adapter (clio_cte_fuse) plus the filesystem module, composed over the Context Transfer Engine. Directories, inodes and file data are all stored as CTE tags and blobs, so the filesystem inherits tiering, replication, durability and indexing from the engine, and has no central metadata server: each inode is homed on a node by its path.

FUSE on every desktop and cluster

One daemon mounts on all three operating systems with each platform's native driver:

  • Linux: libfuse3, included in the pip wheel.
  • Windows: WinFsp (FUSE 3 compatibility layer), mounted as a drive letter, included in the pip wheel.
  • macOS: macFUSE, or FSKit on macOS 15.4 and newer; build from source.

Writes go straight through, so a file's size is exact as soon as write() returns. Attribute and negative-lookup caches last 1 s, and a shared-memory mirror answers stat without a round trip to the runtime. See the Linux, macOS and Windows tutorials.

Tiering

Each tier in the YAML gets a capacity and a score between 0 and 1. New data lands on the fastest tier with room; data you stop touching is demoted to slower, larger tiers, and a replica on a persistent tier keeps files across restarts.

Expandable RAID with safe_bdev

safe_bdev is a block device made of other block devices. It protects data with Reed-Solomon erasure coding: for N drives that must survive f simultaneous failures it uses k = N − f data drives and m = f parity drives, so 8 drives surviving 2 failures is RS(6, 2) with 25% overhead. Unlike a classic RAID array, it grows in place:

  • Add drives at runtime as data or parity members (safe_bdev_add_bdev). New blocks are allocated round-robin over the members that have room, so total data capacity is the sum of the members' capacities and an added drive's space is usable immediately, even when the array was already mostly full.
  • Mixed sizes. Each member fills to its own capacity; stripes narrower than k are protected as mirrors until enough members have written into them.
  • Replace and rebuild. Remove a failed member and name a replacement; the runtime rebuilds its shards while the filesystem stays mounted, and the dashboard shows recovery progress.

The array is an ordinary tier, so Context FS on top of it needs no changes. The cr_safe_bdev_integration_docker test composes three data drives and one added parity drive under a mounted Context FS, removes a member, rebuilds it, and checks that the data still reads back.

Amazon S3 and Google Cloud as tiers

The block device module has S3 and Google Cloud Storage transports, so a bucket can be a tier like any disk. Give it the lowest score and only data the organizer demotes reaches it. Separately, the assimilation engine imports existing s3:// and gs:// objects, including anonymous reads of public buckets. The cloud storage tutorial covers both.

Parallel I/O with IOR

IOR, the standard HPC I/O benchmark, weak-scaled from 1 to 6 MPI ranks on one node: each rank writes and then reads its own 256 MiB file in 1 MiB transfers, with fsync after writing and the page cache dropped between the write and read phases. Context FS (release build of dev at c5dba42bc, default runtime configuration, one DRAM tier) against ext4 on the same machine: WSL2 Ubuntu 24.04 with 6 cores and 11 GB of memory, on a Ryzen 7 3800X with NVMe. Each bar is the mean of three runs, in MiB/s, higher is better.

On a single node, ext4 leads at every rank count. ext4 is a kernel filesystem on local NVMe, while Context FS routes every 1 MiB transfer through FUSE to the runtime process and back. Context FS write bandwidth grows 1.8x from 1 to 4 ranks and then levels off at about 600-640 MiB/s; reads stay between 180 and 280 MiB/s. Where Context FS is built to help is across nodes, where it presents one namespace over every node's tiers without a metadata server. Multi-node IOR results on the Ares cluster will be added here.

Checkpointing a simulation through the tiers

From the Eternia paper's evaluation: Gray-Scott on 2 Aurora nodes, 8 steps, a checkpoint every 2 steps. Each checkpoint is a copy-on-write snapshot that CLIO Core drains down the tier stack in the background, in a layout the HDF5 VOL can read. It is compared with a conventional synchronous checkpoint, in which the simulation waits until the snapshot reaches persistent storage; in the Lustre-heavy composition that is a simulation writing its checkpoint to the parallel file system. Total runtime in seconds, lower is better.

The asynchronous snapshot is 15-25% faster in every composition. Persisting the grid four times still moves 25-62 s of data against 10-48 s of computation; the snapshot lets that traffic proceed in the background instead of blocking the run on the slowest tier. For a science application at larger scale, see the Gray-Scott comparison against DDN, Hermes and cuFile.

Bars are the mean of two runs; the two runs were within 1,081-1,258 vs 2,347-3,838 MB/s for writes and 2,122-2,278 vs 965-1,354 MB/s for reads (NTFS vs Context FS).

Read the write result carefully: in this run the runtime registered a single storage target, the DRAM tier, so Context FS writes landed in memory and were not on disk when fsync returned, which NTFS guarantees. With a persistent disk tier active, writes also pay for the replica. Reads, file creation and metadata cross the WinFsp kernel boundary on every call, which is where NTFS leads. Defender real-time scanning was on for both. Single machine, two runs each.
