Key takeaways

  • No source changes for HDF5: set HDF5_VOL_CONNECTOR=clio or HDF5_DRIVER=clio_vfd and the application's reads and writes go through CLIO.
  • POSIX, STDIO and MPI-IO calls are intercepted only for paths that contain a clio:: component. Every other file passes straight through to the real library.
  • The HDF5 connectors keep the native file authoritative and use the CTE as a cache that can be thrown away. The interceptors and the ADIOS2 engine store the data only in the CTE.
  • None of the adapters ship in the pip wheel or conda. Spack builds them as variants (+posix +stdio +mpiio +vol +vfd +adios2); a CMake source build turns each on with its own option.

What it is

Most scientific codes do their I/O through a library: the C library's open and fopen, MPI-IO, HDF5, ADIOS2. Rewriting them against a new storage API is rarely an option. The adapters meet those codes where they are. Each one implements the interface of an existing I/O library and turns the calls into operations on the Context Transfer Engine (CTE), so the data lands on the tiers the runtime composes: RAM, NVMe, disk or cloud buckets.

  1. Front endsContext FS, memory expansion, machine learning, CAE, CEE
  2. InterceptorsPOSIX, STDIO and MPI-IO interceptors, HDF5 VOL and VFD, ADIOS2 engine
  3. ChiMod chainCache, replication, compressor, indexer, summarizer
  4. CTE coreTags, blobs, placement across tiers
  5. Context RuntimeModules, pools, tasks, scheduling, transports
  6. StorageBlock devices: RAM, NVMe, SSD, HDD, S3/GCS

Which one to use

  • Your code uses HDF5 and re-reads datasets in later sessions from slow storage (a parallel filesystem, network storage, a cold disk): use the VOL connector. It caches whole dataset images of atomic types and serves later reads from the tier.
  • Your HDF5 workload is something the VOL passes through (compound or variable-length types, metadata-heavy I/O): the VFD works at the byte level below HDF5. Its read tier is experimental and off by default; without it the VFD is a write-through replacement for HDF5's default sec2 driver.
  • Your code uses ADIOS2: switch the IO's engine to the plugin engine in code or in the ADIOS2 XML file.
  • Your code writes plain files with open/write, fopen/fwrite or MPI_File_*, and you can choose the path it writes to: preload the POSIX, STDIO or MPI-IO interceptor and give it a clio:: path.
  • Your code needs a whole directory tree, or cannot be preloaded (a static binary, macOS, Windows): mount Context FS through FUSE instead. It serves the same namespace as the interceptors.
  • Neither HDF5 connector helps when the file sits on a local disk and fits in the page cache: a tier hit then replaces a page-cache hit with a round trip to the runtime.

Built to fail safe

  • Opt-in by path. An interceptor never captures a system library, a configuration file or any path without the clio:: marker.
  • The native HDF5 file stays the authority. Every write goes to the file first. With no runtime, no CTE pool or the cache switched off, both HDF5 connectors fall back to the native file and stay correct.
  • Coherence stamps. At close the VOL connector (and the VFD, when its read tier is on) records the file's device, inode, size and modification time. A file changed between sessions by any other tool no longer matches, and its cache is dropped.
  • Silent fallback can be turned into an error. CLIO_REQUIRE_RUNTIME=1 makes an HDF5 open fail when the CLIO tier cannot be reached, so a test or benchmark cannot pass by quietly never using CLIO.

Performance

No adapter benchmark with stated hardware has been published in the repository yet, so this page gives no figures. The HDF5 connectors' compatibility is checked by a differential suite against native HDF5 (benchmarks/hdf5-ingest/hdf5_compat_suite.py, CTest cte_hdf5_vol_compat_suite and cte_hdf5_vfd_compat_suite). To measure the VOL connector on your own system, compare against CLIO_VOL_CACHE=0, which runs the same connector with the tier switched off, rather than against running without the connector.

Build from source

A source build has many settings and configurations to optimize the installation for your specific system. We keep an INSTALL.md in the root of the repository, written to help AI agents install CLIO Core. The I/O adapters are I/O library extensions, so they come from a source build with that adapter turned on: Spack, where each adapter is a variant, or CMake. To have a coding agent do it, give it a prompt like this:

Clone https://github.com/iowarp/clio-core and follow INSTALL.md to build CLIO Core
from source on this machine with the HDF5 VOL connector and the ADIOS2 engine
(-DCLIO_CTE_ENABLE_HDF5_VOL=ON -DCLIO_CTE_ENABLE_ADIOS2_ADAPTER=ON). Install HDF5
1.14+, ADIOS2 and the other system packages it lists for my OS, then run the
adapter tests with ctest to verify the install.

The agent should name the options it chose for your system; the install page lists the options that matter here.
