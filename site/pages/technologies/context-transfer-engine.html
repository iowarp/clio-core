Key takeaways

  • A key-value store for C++ and Python: tags hold blobs, with partial reads and writes by offset.
  • Each blob is placed on a tier by its score; changing the score moves it.
  • Regex, keyword and time-window queries, and a shared-memory path for clients on the same node.
  • The substrate every other technology writes to.
  • 42.6kYCSB-B ops/s, against Redis 16.8k
  • ~2xRedis on read-heavy YCSB workloads
  • 15-16 GB/sasync GPU checkpoint into a RAM tier
  • 2.0xthe HDF5 async VOL on that checkpoint

The data model

A tag is a named collection, a blob is a named value inside it. Puts and gets take an offset, so large values can be written and read in pieces. Each put carries a score from 0 to 1 that the placement policy uses to choose a tier, and the organizer can move a blob later with ReorganizeBlob. Queries match tag and blob names with regular expressions, and the default setup indexes what you write for keyword (BM25) search.

import clio_cte_core_ext as cte

cte.clio_init(cte.RuntimeMode.kClient, False)
cte.initialize_cte("", cte.PoolQuery.Dynamic())

tag = cte.Tag("experiments/run-42")          # get or create the namespace
tag.PutBlob("params", b'{"dt": 0.01}')       # put bytes (zero-copy in runtime mode)
size = tag.GetBlobSize("params")
print(tag.GetBlob("params", size, 0))        # get bytes back
print(tag.GetContainedBlobs())               # list keys in the tag

The same operations exist in C++ (clio::cte::core::Tag::PutBlob, GetBlob), with asynchronous variants such as AsyncPutBlob, and on the client for whole-store queries (TagQuery, BlobQuery, SemanticSearch). The Python API reference lists them all.

Performance against Redis, RocksDB and DynamoDB

The repository's YCSB binding (context-transfer-engine/benchmark/ycsb) runs the standard workloads against CLIO Core and three other stores. Throughput in operations per second, higher is better:

Higher is better. 100k records of about 1.1 KB, 100k operations, 4 threads, one WSL2 machine. CLIO Core measured 34,566-55,866 on workload C across runs; the bar shows the low end.

How to read it:

  • CLIO Core's shared-memory read path is about twice as fast as Redis on the read-heavy workloads, B and C.
  • The update-heavy workloads, A and F, are slower than Redis because the binding implements an update as a full-record read followed by a full-record rewrite, where Redis updates one hash field. A partial put at an offset is the planned fix.
  • Embedded RocksDB has no inter-process hop at all and leads every workload. CLIO Core is a separate runtime process that many clients and nodes share.
  • DynamoDB Local is the local emulator, not the AWS service. All records sit in one tag, so scale-out across tags is not exercised. These are single-node numbers on a development machine.

Against Redis and Redis Cluster on Ares

clio_cte_bench and a Redis client built on the same measurement loop issue puts, then gets, over a 1 GiB working set (262,144 keys of 4 KiB, 16,384 of 64 KiB, 1,024 of 1 MiB), 15 s per point, at 1, 4 and 16 client threads with 1 or 16 requests in flight each. Ares nodes: two Xeon Silver 4114 (40 cores), 46 GB of memory, 40 GbE. Redis 7.4.0 runs without persistence. CLIO Core is a release build of cte-shm-cache (a6b70f12c) with 4 runtime workers and a 16 GB DRAM tier, measured without a cache and with the shared-memory write-through cache (4 GB) on top: puts and gets the cache absorbs complete in the client's own process, and the cache writes puts through to the core in the background.

One node, against Redis

4 client threads, 16 requests in flight each; higher is better. Across all 36 points (6 operation and size pairs, 6 thread and depth settings) the cache beats Redis at every one: 12.0x on the geometric mean, 2.6x at the closest point. With the cache keeping its blob bytes in extents leased from the node's RAM device (an opt-in layout), it beats Redis at every point by 13.2x on the geometric mean.

Four nodes, against Redis Cluster

Aggregate over 4 nodes, one client process per node, 4 threads with 16 requests in flight each; higher is better. Keys are spread across nodes by hash for both systems. Across all 36 points the cache beats the better Redis Cluster layout at every one: 19.9x on the geometric mean, 8.2x at the closest point.

How to read it:

  • Without the cache, CLIO Core pays a hop to its runtime process on every operation and trails Redis on small puts. The shared-memory cache removes that hop for the operations it absorbs, which is where most of the gain comes from.
  • A put the cache absorbs is acknowledged once it is in the node's shared memory; the cache writes it to the core in the background, and a sync (SyncTag) waits for it. Redis here keeps everything in memory with no persistence either.
  • In the cluster runs each node reads back the keys it wrote, so cached gets are served from that node's own memory, while Redis Cluster sends every get to the key's master. Workloads where nodes read each other's keys hit the cache less.

GPU checkpoints through the store

The kvhdf5 adapter writes HDF5-style datasets from GPU kernels as CTE blobs. Its scaling campaign checkpoints a Gray-Scott simulation on an RTX 4090 with local NVMe, comparing asynchronous blob puts against HDF5:

  • CLIO async puts~15.6 GB/s
  • HDF5 async VOL~7.8 GB/s
  • Threaded raw writer7.2 GB/s
  • Inline raw writer5.8 GB/s

I/O-bound GPU checkpoint (8 steps) into a RAM tier, higher is better. The HDF5 async VOL figure is derived from the campaign's measured 2.0x ratio. On an NVMe file tier every arm is disk-bound at about 1.1 GB/s.

Absolute numbers are this machine's; the campaign notes that the ratios carry over but the bandwidths must be re-measured on your hardware.

Put and get bandwidth on a workstation

clio_cte_bench, put then get, 4 client threads with 8 requests in flight each, against a separate runtime with a 16 GB DRAM tier (cte_config_ram.yaml). Release build of dev (f88db54bf) on Windows: Ryzen 7 3800X, 32 GB RAM. The client reaches the runtime over loopback TCP, the transport Windows auto-selects.

Aggregate bandwidth: 1,474 MB/s at 1 MiB, 945 MB/s at 64 KiB, 106 MB/s at 4 KiB.

One run each. Longer 64 KiB and 4 KiB runs (80,000 operations) stopped partway with put errors on this build, so the small-value rows use shorter runs.

Build from source

A source build has many settings and configurations to optimize the installation for your specific system. We keep an INSTALL.md in the root of the repository, written to help AI agents install CLIO Core. The default installers include the Context Transfer Engine. Build from source to write ChiMods against the C++ headers, or to add optional backends such as compression or cloud storage. To have a coding agent do it, give it a prompt like this:

Clone https://github.com/iowarp/clio-core and follow INSTALL.md to build CLIO Core
from source on this machine with the Context Transfer Engine and its tests
(-DCLIO_CORE_ENABLE_TESTS=ON). Also enable compression
(-DCLIO_CTE_ENABLE_COMPRESS=ON). Install the system packages it lists for my OS,
then run the cte tests with ctest to verify the install.

The agent should name the options it chose for your system; the install page lists the options that matter here.
