A composable I/O stack
for data-intensive pipelines.

CLIO Core is a runtime of storage, memory and compute modules that you compose from one YAML file. Turn the RAM, NVMe, disks, GPUs and cloud buckets you already have into the I/O path each stage of your pipeline needs: a filesystem, a key-value store, GPU memory that never runs out, or machine learning that trains where the data lives.

Install it the way your site works. The pip wheel runs on Linux, Windows and Apple Silicon Macs; HPC sites can use Spack, containers the Docker image, and a source build adds GPUs, MPI, HDF5 or ADIOS2.

pip

$ pip install iowarp-core
$ python -c "import iowarp_core; print(iowarp_core.get_version())"

conda

$ conda create -n iowarp -c iowarp -c conda-forge iowarp-core
$ conda activate iowarp

Docker

$ docker run -d -p 9413:9413 --memory=8g --name iowarp \
    iowarp/deploy-cpu:latest clio_run start

Spack

$ git clone --recurse-submodules https://github.com/iowarp/clio-core.git
$ spack repo add clio-core/installers/spack
$ spack install iowarp +fuse

Source

$ git clone --recurse-submodules https://github.com/iowarp/clio-core.git
$ cd clio-core
$ cmake --preset release-fuse
$ cmake --build build -j"$(nproc)" && sudo cmake --install build

01 / Technologies

Mask diverse storage
under cohesive interfaces.

Storage is becoming more diverse and increasingly integrated into memory to drive down costs. A single system may include DRAM, NVMe, burst buffers, Amazon S3 or Google Cloud as candidate storage. CLIO Core presents that complex, distributed storage through simple, cohesive interfaces: filesystems, a key-value store, memory expansion and popular machine-learning algorithms. You worry about the data; CLIO Core worries about where it is placed.

02 / Compose

Compose a storage stack
special for your case.

Every workload wants something different from storage. A simulation wants fast checkpoints, an analysis wants its hot files close at hand, and an archive wants cheap space that survives failures. CLIO Core lets you build the stack each one needs from a menu of parts, and leave out the parts it doesn't.

  • Use what you already own. RAM, NVMe, disks and S3 or Google Cloud buckets each become a storage tier. You rank them, and CLIO Core keeps the most important data on the fastest one.
  • Pick a way in. Mount a folder, keep your HDF5, MPI-IO or POSIX code as it is, or call the key-value API from C++ or Python.
  • Add only the features you need. Caching, replication, compression and search are separate modules. Each does one job and each costs a little time or space, so you turn on the ones you use.
  • One file describes it all. A short YAML file lists the parts, and the runtime starts them.

Leave a module out and the stack closes around the gap; add one and nothing else changes.

How the pieces fit together →
The YAML for a stack like this 
compose:
  - mod_name: clio_cte_core            # tiers and placement
    pool_id: "512.0"
    storage:
      - path: "ram::hot"
        bdev_type: "ram"
        capacity_limit: "16GB"
        score: 1.0
      - path: "/mnt/nvme/clio.dat"
        bdev_type: "file"
        capacity_limit: "1TB"
        score: 0.6
        persistence_level: "long_term"
      - path: "s3://my-bucket/clio"
        bdev_type: "s3"
        score: 0.1
    dpe:
      dpe_type: "max_bw"

  - mod_name: clio_cte_replication     # durable copies
    pool_id: "561.0"
    next_pool_id: "512.0"
    replication_factor: 1
    replica_score: 0.2

  - mod_name: clio_cte_compressor      # optional data operator
    pool_id: "562.0"
    next_pool_id: "561.0"
    default_compress: "zstd"
    default_preset: "balanced"

  - mod_name: clio_cte_indexer         # keyword search
    pool_id: "564.0"
    next_pool_id: "562.0"

  - mod_name: clio_cte_cache           # hot copies, top of the chain
    pool_id: "563.0"
    next_pool_id: "564.0"
    min_score: 0.5

03 / Extend

Develop, upgrade, and install
custom extensions with ease.

Everything in CLIO Core, from the block devices to the filesystem, is a module (a ChiMod): a small shared library the runtime loads. Yours are built the same way and get the same powers: they run next to the data, on every node, scheduled by the same runtime as the built-in ones. You build them out of tree against an installed CLIO Core, and you need no fork.

  • Two halves, one module. A runtime library holds the code that runs inside the daemon; a client library gives applications a typed way to call it. A short clio_mod.yaml names the module and its methods.
  • Drop into the data path. A module can sit in the chain in front of storage, handle the calls it cares about and pass the rest on, so the applications above it never change.
  • Add and remove while it runs. clio_run compose start creates pools of your module in a running cluster, and compose stop removes them, while every other pool keeps serving.
  • Upgrade without rebooting the machine. Installing a new module library, or a new version of one, takes a restart of the CLIO runtime only. Connected clients detect the restart, wait and reconnect, and pools recorded in the pool log come back by themselves.
Write your first module →
Data operators
Encrypt, checksum, deduplicate or redact data on its way to storage; tag what each file contains for later search.
Storage backends
Turn a new device, an object store or a remote service into a tier that the placement engine ranks like any other.
In-situ analysis
Compute statistics, thumbnails or summaries of simulation output as it is written, on the node that holds it.
Domain services
A key-value store with your own semantics, a catalog for an instrument, or a feature store for training.
Accelerated kernels
Analytics and ML kernels that run on GPUs over paged data larger than device memory, as clio-ml does.

Swapping a module's code inside a live pool, with no runtime restart at all, is designed for but not yet enabled; see Extending the runtime.

04 / Scale

Support for parallelism
at extreme scales.

CLIO Core runs as one runtime per node, and every module is a pool with a container on each node. Work and data spread across the machine instead of funnelling through a central server, so a pipeline that grows from one node to many keeps the same configuration.

How the runtime schedules work →
  • No central servers. Each pool places a container on every node. Context FS homes each inode on a node by its path, so there is no metadata server to saturate.
  • Many clients at once. The runtime runs requests as lightweight coroutine tasks across worker threads, and clients reach it over shared memory, TCP or Unix sockets.
  • Parallel from inside GPU kernels. With memory expansion, every GPU block issues its own batched, asynchronous fetches and flushes, so data movement overlaps computation.
  • Tiers on every node. Each node composes its own RAM, NVMe, disks and buckets, and the engine places data across all of them.
  • 64 nodesEternia within 0.88-1.19x of MPI, oneCCL and Intel SHMEM on Aurora
  • 1 → 16 nodesclio-ml time per iteration stays flat; Spark MLlib's grows 3.6x
  • 2xlarger Gray-Scott runs than DDN, Hermes and cuFile on 4 Delta nodes

05 / Assimilate

Assimilate diverse data
for better agentic exploration.

Pipeline data rarely lives in one place. The Context Assimilation Engine pulls it into the stack from local files, HDF5 datasets, web URLs, Amazon S3, Google Cloud Storage and Globus endpoints. Each source becomes a tag of blobs that every product can read, the indexer can search and an agent can explore.

  • One OMNI file lists the transfers: a source, a destination tag and a format, with optional byte ranges and dependencies.
  • HDF5 datasets each become their own tag, so a search or an agent can address a single variable instead of a whole file.
  • The summarizer can run a language model over each blob as it lands and store the reply beside it, so data can be found by what it means, not only by its name.
The assimilation engine → 
name: ocean_run_42

transfers:
  - src: hdf5::/scratch/run42/output.h5
    dst: iowarp::run42
    format: hdf5
  - src: s3://climate-obs/sst/2024.bin
    dst: iowarp::sst_obs
    format: binary
  - src: file::/home/me/notes/run42.md
    dst: iowarp::run42_notes
    format: binary

$ clio_cae transfers.yaml

06 / Explore

Ask for data
by what it says.

The Context Exploration Engine is one interface over everything in the stack, whichever product wrote it. Bundle sources in, then query them three ways: by tag and blob name patterns, by keyword relevance (BM25) against the contents, or by when the data was last modified. Retrieve the matches as one packed buffer, capped in size, ready to hand to an analysis or a model.

  • context_bundle assimilates a group of related sources.
  • context_query returns the names that match a pattern, a prompt or a time window.
  • context_retrieve returns the matching data, fetched in parallel batches.
  • context_destroy removes a context when the work is done.
Query files from Python → 
import clio_cee as cee

ctx = cee.ContextInterface()      # connects to the runtime on first use

ctx.context_bundle([
    cee.AssimilationCtx(src="hdf5::/scratch/run42/output.h5",
                        dst="iowarp::run42", format="hdf5"),
])

# Names whose contents best match a prompt (BM25), top 5
hits = ctx.context_query("run42.*", ".*", max_results=5,
                         prompt="sea ice extent anomaly")

# The matching data, packed into one buffer of at most 64 MB
data = ctx.context_retrieve("run42.*", ".*", max_results=5,
                            max_context_size=64 << 20,
                            prompt="sea ice extent anomaly")

10 / Questions

Common questions.

Is CLIO Core a filesystem?

Not only. Context FS is one product built from CLIO Core's modules. The same runtime also composes into a key-value store, GPU and CPU memory expansion, and clio-ml. Use the one that fits each stage of your pipeline; they share data.

Do my applications need to change?

No. Through the FUSE mount, CLIO Core looks like a local directory. Applications that use HDF5, ADIOS2 or MPI-IO can also use a plugin instead of the mount for lower overhead.

Does my data survive a restart?

Yes, with the default configuration. Every write is copied to a persistent disk tier and recorded in a metadata log under ~/.clio. clio_run start recovers from that log. RAM-only setups are volatile by design.

Can I use Amazon S3 or Google Cloud Storage?

Yes, in two ways. The assimilation engine imports s3:// and gs:// objects into the filesystem. A build with the cloud options enabled can also use a bucket as a storage tier. See the cloud storage tutorial for what each one supports.

Does it scale past one machine?

Yes. Runtimes on several nodes form a cluster from a hostfile. Each tier can place data on neighboring nodes, and the filesystem namespace has no central metadata server.

How mature is the project?

CLIO Core is under active development. The filesystem, the runtime and the Python bindings run in CI on Linux, macOS and Windows. Report an issue if something does not work.
