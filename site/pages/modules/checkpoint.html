What it does

The CTE core lets a tag register a fault handler: a pool that is asked to produce a blob whenever a get or put finds the blob missing under that tag. The checkpoint module is the handler used for copies. A copy tag registers pool 566.0 as its handler and the source tag as the handler's parameter. When the core faults a blob of the copy, the module reads the whole blob from the source, writes it into the copy, and then lets the original operation proceed against the copy's own blob.

It exists for Copy on the CPU and GPU paged vectors, the checkpoint primitive of memory expansion. An untouched copy occupies no storage, so taking a checkpoint costs a flush and two metadata operations, and bytes move only for pages that are later read back, overwritten in the source, or materialized explicitly.

Where it sits

The runtime class derives from the core's interposer base, so it speaks the core's task interface and forwards every core verb it does not handle to next_pool_id. It is not part of any client's data path, though: no client binds to it, and it is not in the default chain in context-runtime/config/clio_default.yaml. The CTE core is its only regular caller.

  • Called by: the core, on a miss in a fault-handled tag and from the copy-on-write hook, always with a local pool query, so the fault runs on the node that holds the blob's container. Vectors also call it directly from MaterializeAll.
  • Calls: next_pool_id (the core, or the top of the chain in front of it) for the source lookup, the size probe, the whole-blob read and the materializing put. Unset, it uses the core pool 512.0.
  • Interposed verb: GetBlob only. Create, Destroy and Monitor are its own lifecycle methods; everything else is forwarded.

Composing it

Usually nothing needs composing. Copy creates the pool itself, idempotently, before registering the copy tag:

clio::cte::checkpoint::Client ckpt(
    clio::cte::checkpoint::kCheckpointPoolId, storage_pool_id_);
clio::cte::checkpoint::CheckpointConfig params;
params.next_pool_id_ = storage_pool_id_;
auto cf = ckpt.AsyncCreateCheckpoint(
    clio::run::PoolQuery::Dynamic(),
    clio::cte::checkpoint::kCheckpointPoolName,   // "clio_cte_checkpoint"
    clio::cte::checkpoint::kCheckpointPoolId,     // 566.0
    params);
cf.Wait();

The dynamic query matters. The core dispatches a fault to the handler on the node where the faulting blob lives, which need not be the node that took the copy, so the pool has to exist on every node.

The module's config parser also reads a compose entry, so a deployment can create the pool at startup. No shipped configuration does this; the entry below is an example:

compose:
  # ... the CTE core (512.0) and any chain above it, first
  - mod_name: clio_cte_checkpoint
    pool_name: clio_cte_checkpoint
    pool_query: local
    pool_id: "566.0"
    next_pool_id: "512.0"

Keep the pool name clio_cte_checkpoint. The core turns on copy-on-write only for a fault registration that names that pool (kCowFaultPoolName in core_tasks.h), and the module's kCheckpointPoolName is defined from it.

Operations

From checkpoint/clio_mod.yaml:

MethodIdMeaning
kCreate0Creates the container. The parameters are a CheckpointConfig holding next_pool_id_.
kDestroy1Destroys the container. It holds no state to clean up.
kMonitor9Standard monitor. Returns success and does nothing else.
kGetBlob16The fault entry point. It carries the core's own GetBlob id, and the task is the core's GetBlobTask: the copy tag, the missing blob's name, the requested range and buffer, and the source in Context::fault_params_.

A GetBlob with size 0 and a null buffer is a materialize-only fault: copy the blob into the copy tag and serve nothing. The core issues that form before a put into a missing blob and from the copy-on-write hook; MaterializeAll issues it once per page. The client class only creates the pool (AsyncCreateCheckpoint); it inherits the core client, but callers never address the pool for data.

Taking a copy

Both vectors' Copy(new_name, sync = false) follow the same steps (adapter/cpu_vector/include/clio_cte/cpu_vector/cpu_vector.h, adapter/gpu_vector/include/clio_cte/gpu_vector/gpu_vector.h):

  1. Check the source name. It must be shorter than 64 bytes, the size of Context::fault_params_. A longer name throws, since the core would silently truncate it and resolve a different tag.
  2. Flush. Every resident page goes to the CTE, so the copy snapshots what the vector holds now rather than what happened to be flushed.
  3. Create the pool at 566.0 with a dynamic query, as above.
  4. Register the copy tag. AsyncGetOrCreateTag(new_name, 566.0, "clio_cte_checkpoint", source_name) on the core. The container that owns the name stores the handler. Because the pool name is the copy-on-write name, it then looks the source up (a lookup that never creates; a missing source fails the call) and broadcasts CowLink (core method 62) to every core container. Each container records the link from source to copy and installs the copy's handler locally, with the source named by id as #major.minor, so the copy still resolves after the source's name is gone. The call returns after every container has the link.
  5. Optionally materialize. With sync = true, MaterializeAll sends a materialize-only fault for every page, 32 in flight by default, and Copy throws unless every page succeeds.

The same registration is available to any core client: pass the pool id, pool name and source tag name to the four-argument AsyncGetOrCreateTag, as test_checkpoint_fault.cc does.

Resolving a fault

When a get or put on the copy finds no blob and the request does not carry kNoFault, the core sends a GetBlobTask to the handler with a local query. A get forwards its range and buffer and returns the handler's result. A put sends a materialize-only fault, then probes again and writes against whatever now exists, so a partial put into a page lands on top of the source's bytes rather than zeros. The handler (checkpoint/src/checkpoint_runtime.cc) then:

  1. Rejects an empty parameter. A fault with no source is a registration bug and fails with return code 1.
  2. Keeps an existing copy. For a materialize-only fault it first probes the copy. If the blob is already there, even as an empty tombstone, nothing happens: rematerializing would replace the copy's bytes with the source's current ones.
  3. Resolves the source. An id-form parameter is used directly; a plain name goes through GetOrCreateTag. A failed lookup returns 1.
  4. Sizes the source blob. If the source has no bytes for it, a materialize-only fault writes an empty tombstone into the copy, so the copy records the blob as absent and never faults on it again. Any other fault is forwarded to the copy unchanged with kNoFault, so create-on-get and not-found behave exactly as on a tag without a handler.
  5. Copies the whole blob. The handler reads the entire source blob into a staging buffer the size of the blob (return code 2 if it cannot be allocated) and puts it into the copy at offset 0. It copies the whole blob even for a range read: the fault is triggered by the blob being missing, so a partial copy would leave holes that no later access could detect.
  6. Serves the request. For a get, the original range is re-issued against the copy with kNoFault. It is not a memcpy from the staging buffer because the caller's buffer can be device memory (a GPU vector page fault), which only the core's serve path knows how to fill.

Every core operation the handler issues carries kNoFault, so it cannot fault again. The materializing put also carries kNoCow and clears create_on_get: it writes the copy's own bytes, not a change to a source.

Copy-on-write

Faulting alone would copy a blob from the source as it is at the first touch, so a source overwritten in between would leak later bytes into the copy. The copy-on-write hook in core/src/core_runtime.cc closes that window. Before the owner container changes a source blob, each copy registered on that source receives the blob's current bytes:

  • PutBlob, including each record of a batched put. Replica and shadow writes, emulated writes, and the handler's own kNoCow puts skip the hook.
  • DelBlob and DelTag, before blocks are freed.
  • TruncateBlob, only when it shrinks the blob.

The hook runs under the blob's write token, so two writers to one blob materialize it once. For each copy it probes the copy; a copy that already holds the blob costs only that probe. Otherwise it sends a materialize-only fault to the checkpoint pool on the same node. If the pool is absent there, the mutation fails with return code 2 (kCowErrFaultPoolMissing) rather than dispatching a task the router would retry forever.

The consequences, all exercised by test_checkpoint_cow.cc:

  • An overwrite of a source blob leaves the copy with the old bytes and the source with the new ones.
  • A blob the source gains after the copy was taken is recorded in the copy as a tombstone by its first put, so it stays absent from the snapshot.
  • Two copies taken at different times each keep their own version.
  • Deleting a source blob that a copy has not materialized saves it into the copy first.
  • Deleting a copy removes its links, and writes to the source then proceed without the hook.
  • A tag with no copies of its own is unaffected.

When a snapshot cannot be saved, the source change does not happen. A put, delete or shrinking truncate returns the hook's error. A tag delete keeps each blob it could not save, together with the tag's metadata and links, and logs an error. A source tag deleted completely drops all its links, since its copies then hold every blob.

Configuration

next_pool_id
The pool the handler resolves sources through and materializes copies into, as "major.minor". Copy sets it to the vector's storage pool. Unset falls back to the core pool 512.0. It is the only key; parsing is best effort, and a malformed value leaves it unset.

The pool id and name are fixed constants in checkpoint_tasks.h: kCheckpointPoolId is 566.0 and kCheckpointPoolName is clio_cte_checkpoint. The id is 566 rather than 565 because the stream module owns 565.0; a shared id made Copy resolve its handler to the stream pool (issue #1186). The module has no entry in clio_default.yaml.

Collision with the write-through cache. The write-through cache also defaults to 566.0 (kWriteThruCachePoolId). If you compose the write-through cache, give it a different pool_id: the checkpoint id is fixed in code, the write-through cache's is set by its compose entry.

Who uses it

  • CPU and GPU paged vectors. Copy and MaterializeAll; both adapter targets link clio_cte_checkpoint_client. See the memory expansion API.
  • GPU vector benchmarks. The grayscott, gmx, lammps_md and lbann paged benchmarks take an end-of-run checkpoint with Copy through benchmark/bench_ckpt.h, lazy by default and synchronous with --ckpt-sync. Their CMake files add a build dependency on the runtime library, since the runtime loads the module rather than linking it and Copy otherwise throws "checkpoint pool create failed". clio_gpu_vector_copy_sync_bench compares the cost of lazy and synchronous copies.
  • CTE vector stress benchmark. context-transfer-engine/benchmark/clio_cte_vector_stress.cc takes a copy every --ckpt-every steps and materializes the node's own pages.

The CAE uses the same core fault-handler mechanism to ingest data on first access, with its own pool as the handler. It does not go through this module.

Behaviors worth knowing

  • A lazy copy is a snapshot from the moment Copy returns. sync = true or MaterializeAll makes it real bytes immediately; neither is needed for snapshot correctness.
  • MaterializeAll runs entirely inside the runtime: each page is a whole-blob read and write between tags, and no bytes cross to the client.
  • A copy is independent once materialized. Writes to the copy do not reach the source, and later source writes do not reach the copy.
  • A copy returned by the GPU vector's Copy builds no device views. A kernel that must read it opens its own vector on the copy's tag.
  • A tag has one fault handler. Registering again overwrites it; GetOrCreateTag without fault arguments leaves an existing registration alone.

Limits

  • The source tag name must fit in 64 bytes including the terminator.
  • A fault stages the entire source blob in one buffer, whatever range was requested.
  • Fault registrations and copy-on-write links live in memory. The core's transaction log records a tag's name and id, not its handler, so materialize a copy that has to survive a runtime restart.
  • The checkpoint pool must exist on every node that holds blobs of a copy or its source. Copy ensures this; code that registers copy tags itself must too.
  • The core does not check the return code of a put-side fault. If materialization fails, the put proceeds on a new, empty blob.

How it is tested

  • context-transfer-engine/test/unit/test_checkpoint_fault.cc (ctest cte_checkpoint_fault): get faults, copy and source independence, put-side materialize-then-merge, whole-blob faulting on range reads, and the source-absent fallback.
  • context-transfer-engine/test/unit/test_checkpoint_cow.cc (ctest cte_checkpoint_cow): the copy-on-write cases listed above, on one node.
  • context-transfer-engine/adapter/gpu_vector/test/test_gpu_vector_copy_gpu.cc (ctest cte_gpu_vector_copy, CUDA builds): host and device reads of a copy materialize from the source.
  • context-transfer-engine/test/unit/test_well_known_pool_ids.cc (ctest cte_well_known_pool_ids): compile-time check that 566.0 does not collide with the CTE module ids it lists. The write-through cache's default, also 566.0, is not in that list.

The two checkpoint unit tests are built only when the clio_cte_checkpoint_client target exists, that is, with CLIO_CTE_ENABLE_CHECKPOINT=ON.
