What it does

Every CTE operation on the task path allocates a task, wakes a worker, walks the interposition chain and signals completion. For large transfers that overhead is noise; for a process doing many small puts, gets and size queries on one node it dominates. This module moves the common cases into the client process. The runtime creates a shared-memory segment per node; a connected clio::cte::core::Client maps it and runs PutBlob, GetBlob, GetBlobSize and GetOrCreateTag against it first.

  • A put copies the bytes into the blob's buffer in the segment and appends the exact byte range written to one shared dirty-range log, then returns. The chain has not seen the write yet.
  • A get copies out of the segment when the cached bytes are known to be current for the requested range.
  • A size or tag open is answered from the segment's blob and tag tables when they hold the answer.
  • The module's periodic FlushLog task is the log's only consumer. It coalesces the logged ranges per blob and sends them down next_pool_id as MultiPutBlob batches.

The module also speaks the full core task interface, so task callers (remote nodes, processes that cannot map the segment, runtime-internal clients) see the same view. Anything it does not serve itself is forwarded after the writes buffered on this node have landed.

Where it sits

The default configuration composes the cache at the top of the chain, above the data transformations and data caches (context-runtime/config/clio_default.yaml). The opt-in indexer, when composed, goes above it:

[indexer(564.0) ->] shm cache(568.0) -> [compressor(562.0) ->]
  core_persist_write_back(567.0)
  -> volatile core(540.0)
  -> replication(561.0) -> persistent core(512.0)

The default entry sets md_only: true: the write-back cache at 567.0 already holds the bytes in RAM, so this layer caches tag and blob metadata only (blob sizes, tag name-to-id bindings, tag size and times). Every put and every get then takes the task path through the chain, and only size queries and tag opens complete in the client.

With md_only: false (data mode) the cache also holds blob bytes and absorbs plain writes, either in its own segment or, in extent mode, in granules leased from a node-local RAM bdev. The four-node coherence suite runs it this way, directly over the cache module. The chain design page covers how the layers stack.

How clients connect

  1. The runtime publishes a locator. When the pool is created it formats the segment, named clio_wtc_<runtime pid>_<major>_<minor>, and registers a locator in the runtime's metadata segment under the cache's pool id. The locator carries the runtime pid, the segment root's offset and entry_pool_id.
  2. The core hands out the keys. The CTE core's Create, and a get-or-create of a core pool that already exists, returns CreateParams::cache_keys_: the keys of the cache whose chain of next pools ends at that core. If several match, the last one registered wins. With no such cache the keys are all zero.
  3. CLIO_CTE_CLIENT_INIT binds and maps. It get-or-creates the canonical core pool (512.0) and reads the keys. With valid keys it rebinds the client to entry_pool_id (or the cache pool when that is unset), so every task-path request passes every module above the cache and then the cache itself, and calls Client::ConnectCache(keys) to map the segment.
  4. CLIO_CTE_POOL overrides the binding. With CLIO_CTE_POOL=major.minor set, the client is bound to that pool and then calls ConnectCache(), which fetches the keys with the same get-or-create of 512.0. It connects only when the named pool is the cache pool or its entry pool.

Other clients connect explicitly. The filesystem module's client binds its data client to the filesystem pool's next_pool and calls ConnectCache(), and the Python bindings expose ConnectCache as well. HasCache() reports whether a client is connected.

A client stays on the task path when:

  • the keys are zero: no cache fronts the core;
  • the client is bound to a pool that is neither the cache pool nor its entry pool (for example CLIO_CTE_POOL=561.0), since its tasks would bypass the cache;
  • the process is not attached to that runtime's shared memory: a TCP or unix-socket client, a client on another node, or a runtime with a different pid. Only the SHM transport attaches the runtime's metadata segment;
  • the segment cannot be mapped, has another layout version, or (in extent mode) the RAM bdev's segment cannot be mapped.

When CLIO_CTE_CLIENT_INIT finds a cache but cannot map it, it logs shm cache present but not mappable from this process and leaves the client bound to the core pool. When it finds no keys it logs nothing.

Segment layout

Everything in the segment is addressed by offset, so it may map at a different address in each process. It is formatted as a multi-process allocator, and every page is mapped at format time so that a writing client does not take a page fault per 4 KiB of first touch. The first allocation is the root; the rest are:

  • Root: magic and layout version, the pushed and flushed range counters that make up the barrier, the statistics counters, the tag lock and 64 stripe locks.
  • Blob table: max_blobs entries split into 64 stripes. A key hashes to one stripe and probes at most 64 slots inside it, so one stripe lock covers every slot the key can occupy. An entry holds the key (blob names up to 200 bytes), the buffer offset and capacity, the logical size, the range known current, pending and pin counts, write and invalidation generations, a seqlock over the bytes, and frecency counters.
  • Tag table: max_tags entries with the created flag, the sticky flush error, and the cached name (up to 255 bytes), size and times.
  • Name index: twice max_tags slots mapping a tag name to its id, for tag opens.
  • Dirty-range log: one multi-producer ring of log_depth entries, each a 24-byte record of slot, generation, offset and size.
  • Owner map: one word per 4 KiB of segment naming the entry whose buffer starts there, used by eviction to free contiguous windows.
  • Blob buffers: the rest of the segment. Each blob has one contiguous buffer, at least 4 KiB, rounded to 4 KiB and grown by half its size at a time. Holes read as zeros.

Write path

A segment write (View::TryPut) is accepted only in data mode, for a blob name of at most 200 bytes, with no put flag other than kCtePutDroppable. A metadata-only segment refuses every write, and so does a write whose droppable flag differs from what earlier writes of a buffered blob carried.

  1. Room in the log. Neither clients nor runtime workers block on a full log: a write is refused when the log is within 1024 entries (or a quarter of its depth, if smaller) of full.
  2. Find or insert the entry under its stripe lock. If the stripe has no free slot, the lowest-frecency entry in the stripe with nothing pending or pinned is reclaimed, and the insert is retried.
  3. Make room in the buffer. A buffer that must grow is reallocated, evicting clean buffers when the segment is full. A buffer that is pinned (a flush or a read is copying it) is never grown or moved: the write is refused as busy and nothing is changed.
  4. Publish. The logical size and the current range are updated, the pending count and write generation are bumped, the seqlock is opened and the entry is pinned, all under the stripe lock.
  5. Copy outside the lock. The bytes are copied into the buffer with only the pin held, then the seqlock closes and the pin drops.
  6. Log the range. The pushed counter is bumped before the exact range written enters the log, so a barrier taken afterwards always covers it.

A client retries a busy refusal up to 8 times with back-off from 4 to 256 microseconds, holding no lock, and takes the task path on any other refusal. On the task path the module's PutBlob handler tries the segment again with the task's bytes when the put is plain (no explicit score, a default context, no flag other than droppable). A put refused for room waits up to nospace_wait_ms for the ranges buffered before it to land, since flushed buffers are clean and evictable, then retries 20 more times about 50 microseconds apart; a busy put retries 12 times with back-off from 10 microseconds to 1 ms. A put that still does not fit, and every put that is not plain, writes around the cache: the blob's pending ranges land first, the local copy is invalidated, the put is forwarded down the chain, and the local copy is invalidated again once it has landed. MultiPutBlob batches are absorbed record by record the same way; a record that does not fit is written around on its own.

Read path

  • Hit. A read is served from the segment when the entry is resident and either holds the whole blob and the request is within its size, or the request lies inside the range written through this cache since its last invalidation. The copy is protected by the seqlock: a read that overlaps a writer's copy is retried up to 256 times, then counts as a miss.
  • Whole-blob copies. An entry holds the whole blob when it was filled from the chain, or when it was created by a write under a tag that this cache saw created (a new tag has no older bytes anywhere).
  • Miss. The client sends a GetBlob task. The handler waits for the blob's own pending ranges to land, registers this node with the blob's home, asks the chain for the blob's size, and when it is at most max_fill fetches the whole blob and installs it, unless a local write or an invalidation moved the entry's generations meanwhile. It then serves the read from the fresh copy, or forwards the read down the chain.
  • Sizes. GetBlobSize is answered from the segment when the entry holds the whole blob or a size fetched from the chain. A miss is fetched and recorded the same way, also in metadata-only mode.
  • Tags. A plain GetOrCreateTag of an existing name is answered from the name index when the tag's attributes are cached too. A miss creates or opens the tag through the chain, registers with the tag's home, confirms the binding and caches the name and the tag's cluster-wide size and times.

Reads that carry flags, a context, or vectored segments, and every read in metadata-only mode, skip the segment.

Flusher

Create starts one periodic FlushLog task per container, every flush_period_us microseconds. A barrier wakes it directly instead of waiting for the period. One pass runs until the log is empty:

  1. Pop and coalesce. A batch pops up to 8192 ranges, 65,536 log entries or flush_batch_bytes of payload. A range whose bytes an earlier flush already carried is retired without a resend. The rest are sorted and merged per blob where they overlap or touch.
  2. Group by home. Each blob's home is its hash modulo the number of containers in the cache pool.
  3. Send. In segment mode the records are pinned and the tasks point straight at the bytes in the segment: a record homed on this node goes to next_pool_id as a MultiPutBlob, a remote one to its home's cache as HomeFlush. When pinning fails, and always in extent mode, the bytes are copied into one staging buffer per home (waiting for room rather than dropping), the local group is split into flush_shards tasks by blob so one blob's ranges stay ordered, and each remote home gets one HomeFlush.
  4. Pipeline. Up to flush_depth batches are in flight and land oldest first; a batch that touches a blob still landing in an older one waits for it. The flusher stops starting batches while a chain read of a blob is waiting.
  5. Land. A failed batch is replayed record by record up to flush_retries times. A record that still fails sets its tag's sticky error. Only then does flushed advance.

Writes are acknowledged before they reach the chain. A write's failure surfaces at the next SyncTag of its tag, which returns the sticky error and clears it; a put refused for space is reported as the sync's no-space code.

Coherence and invalidation

Each blob has a home container: BlobHash(tag, blob) modulo the cache pool's container count. Tag metadata uses the same rule, under a reserved blob name. The home keeps a sharer directory of the other containers that cache each key, bounded by max_sharer_entries; overflow forgets an entry by invalidating its holders.

  • Register. A container registers with the home before it fetches a fill, a size or tag metadata. A write that lands at the home afterwards invalidates it, which bumps the entry's epoch and voids a fill still in flight.
  • Invalidate on landing. HomeFlush forwards the batch down the chain, then invalidates every sharer except the writer before it acknowledges. The writer is invalidated too when another container has also written the blob, since its buffer may lack those bytes. A flush that lands on its own home invalidates the same way.
  • Invalidate on write. Puts written around the cache and blob deletes send their keys to the homes in batches: one lane per home, keys de-duplicated, at most one Invalidate in flight per home.
  • invalidate_on_flush. With it set, those writes and single-blob deletes send no invalidation of their own. The default write-back cache names 568.0 as its flush_pool, so each flushed range lands through this pool on the blob's home, which invalidates its sharers then. Tag deletes, multi-blob deletes and truncates still invalidate at once.
  • Invalidated entries. The entry loses its whole-blob flag, known size and current range. Its buffer is freed unless ranges are still pending (they still flush, but are never served) or it is pinned (eviction reclaims it later).

Barriers: DelTag, SyncTag and every core verb the module does not handle itself wait until flushed reaches the pushed value seen on entry, polling every 10 microseconds. SyncTag also waits for the tag-metadata invalidations of the landed writes, syncs the tag on every remote home this node's ranges landed on, and then forwards. DelTag then broadcasts a drop of the tag's entries to every node. On a single-node runtime no invalidation messages are sent.

Extent mode

With md_only: false, a data_pool and a nonzero data_capacity, blob bytes live in a node-local RAM bdev instead of the segment. At Create the cache leases data_capacity from that bdev in 64 MiB requests until it has it all or the device is full, and uses whatever it got. Adjacent leased blocks merge into one extent.

  • Each blob is stored as up to 8 runs of 4 KiB granules. Growth appends runs, so bytes already written never move and there is no power-of-two rounding.
  • A data_pool minor of 0 means this node's own device of that core: the minor becomes 1 plus the container id ("540.0" is the first storage device of core 540 on this node).
  • Clients map the RAM bdev's segment as well; if they cannot, they do not use the cache at all. CLIO_PREFAULT in a client maps the leased pages at attach time: 0 maps all of them, a size maps that much.
  • The flusher always uses staging buffers in this mode.
  • Destroy returns the leased blocks to the bdev.

Configuration

Every key is optional. Sizes accept suffixes such as M and G. Parsing is best-effort: a malformed value leaves the remaining keys at their defaults without an error.

next_pool_id
Pool below this one, as "major.minor". Unset falls back to the core pool 512.0. The default configuration uses 567.0.
entry_pool_id
Pool clients bind to so their tasks pass every module above the cache. Unset means the cache pool itself, as in the default configuration. Set it to 564.0 when the opt-in indexer is composed above the cache.
md_only
Cache tag and blob metadata only; blob bytes go down the chain. Default false; the default configuration sets true.
invalidate_on_flush
Writes send no invalidation of their own; set it only with a write-back cache below whose flush_pool is this pool. Default false; the default configuration sets true.
capacity
Segment bytes: buffers, tables and log. Default 256 MiB.
log_depth
Dirty-range log entries. Default 0: automatic, one entry per KiB of capacity with a floor of 65,536 and a cap of 228, or 65,536 in metadata-only mode.
flush_batch_bytes
Most payload one flush batch pops. Default 16 MiB.
flush_period_us
Flusher period in microseconds. Default 50. Each run drains the log completely.
flush_retries
Per-record retries of a failed batch before the tag's error sticks. Default 3.
flush_shards
Parallel MultiPutBlob tasks for this node's own blobs on the staged path. Default 8.
flush_depth
Flush batches in flight. Default 4.
max_tags
Tag table entries. Default 4096.
max_blobs
Blob table entries, metadata and buffers alike, divided evenly among 64 stripes. Default 65,536.
max_fill
Largest blob a read miss copies into the cache; larger blobs are read through but not cached. Default 16 MiB.
evict_sample
Clean entries sampled per eviction. Default 16.
half_life_ms
Frecency decay half-life: an entry's score is its hit count times 2-age/half_life. Default 10000.
max_sharer_entries
Sharer-directory entries on a home. Default 65,536.
nospace_wait_ms
Most a task-path put refused for room waits for earlier buffered ranges to flush before it writes around the cache. Default 250.
data_pool
RAM bdev for extent mode, as "major.minor". Unset: bytes live in the segment.
data_capacity
Bytes leased from data_pool. Default 0, which leaves extent mode off.

Environment: CLIO_CTE_POOL and CLIO_PREFAULT are read by clients (above); CLIO_WTC_TRACE=1 makes the runtime log every flush group, home flush, sync and failed chain read with a [WTC-TRACE] prefix.

Operations

From clio_mod.yaml and the method header. The interposed verbs use the core's own method ids.

  • Interposed: GetOrCreateTag (14), PutBlob (15), GetBlob (16), DelBlob (18), DelTag (19), GetBlobSize (23), MultiPutBlob (48) and SyncTag (56). PutBlob, GetBlob, GetBlobSize, MultiPutBlob, GetOrCreateTag, DelTag and DelBlob run on the submitting node, since the segment is per node.
  • Forwarded: every other core method keeps the core's routing, waits for this node's log to drain and is forwarded. Truncates, multi-deletes, renames and tag-name updates then invalidate the keys they changed.
  • Own verbs: FlushLog (100), the periodic drain; Invalidate (101), the coherence message (drop, register, fan out, drop a tag); HomeFlush (102), a flush batch landing at its home, carrying the core's MultiPutBlob task; and TagAttrs (103), which answers a cluster-wide GetTagSize from the segment. A connected client sends a broadcast AsyncGetTagSize to TagAttrs on the local cache.

The module's own clio::cte::shm_wtc::Client only creates the pool (AsyncCreate) and runs a flush pass on demand (AsyncFlushLog). Data traffic goes through a core client bound to the cache or its entry pool. Monitor answers no queries.

Statistics

When the runtime stops, each container with a segment logs one line at warning level:

[shm-cache stats] node= puts= put_MiB= refused: log= slot= buf= busy= miss= waits= flush_batches= flush_ranges= flush_MiB= flush_skipped= fills= md_fills= get_hits= get_misses= (absent= nonres= range= busy=) invalidations= evictions=
  • refused counts puts the segment turned away: log nearly full, no blob slot, no buffer space, entry pinned, and miss for a metadata-only segment or a flag the segment cannot carry. In the default metadata-only configuration every put lands in miss.
  • waits counts the task path's retries for room or a pin.
  • flush_skipped counts ranges retired without a resend because an earlier flush already carried their bytes.
  • get_misses are split by reason: no entry, entry without bytes, range not known current, and writer mid-copy.

Clients read the same counters at any time through Client::CacheStats().

Behaviors worth knowing

  • A client that initializes while the runtime is still composing, after the core exists but before the cache pool is created, gets zero keys from the core's Create. CLIO_CTE_CLIENT_INIT then leaves the client bound to the core pool (512.0) on the task path, logs nothing, and never retries for the life of the process: the client bypasses the whole chain above the core. Start clients after composition finishes.
  • The blob table is a fixed-size open-addressed table. Inserting a new blob probes at most 64 slots of its stripe, and reclaiming a clean entry only helps when that entry falls in the probe window. A node writing more distinct blobs than max_blobs (default 65,536) therefore starts refusing puts of new blobs (refused: slot=) and writes them around the cache through the task path. Size it above the node's working set of blobs.
  • A connected client's synchronous PutBlob tries the segment whatever its score and context arguments; the cache does not carry them. A put that must carry a score or a context should use AsyncPutBlob, which is always the task path. To keep one put out of the segment, set Context::kBypassShmCache (bit 1u << 11 of op_flags_) in the context passed to PutBlob: the client sends a task instead. The Async* methods never consult the segment.
  • An acknowledged put in data mode is in the segment, not the chain. It is durable, and visible to task callers on other nodes, once the flusher lands it; SyncTag waits for that.
  • With invalidate_on_flush (the default configuration), other nodes drop their cached metadata of a blob when the write-back cache flushes the write, not when the write happens.
  • The barrier is node-wide: SyncTag of one tag waits for every range buffered on the node before it, not only that tag's.
  • A blob larger than max_fill is never cached by a read; only writes through this cache populate it.

Limits

  • A blob's home is computed as hash modulo the cache pool's container count and addressed directly, duplicating the core's placement. It is only right while placement is plain hash modulo N with one container per node: successor failover or migration below breaks it. Tracked as iowarp/clio-core#1372.
  • Processes that cannot map the segment stay on the task path, and one bound to the core directly instead of the cache's entry pool bypasses invalidation.
  • The segment is formatted empty when the pool is created, and the module's Destroy does not flush it. Nothing in it survives a runtime restart: a data-mode write the flusher has not landed when the runtime goes down is lost. SyncTag is the durability point.
  • Blob names longer than 200 bytes and tag names longer than 255 bytes are never cached.
  • In extent mode an entry holds at most 8 runs. Growth that cannot be placed in the remaining runs, even after evicting, writes around the cache.
  • The flusher's zero-copy path sends one MultiPutBlob task per coalesced record rather than one per home.
