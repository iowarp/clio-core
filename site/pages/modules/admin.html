What it does

The admin module is the runtime's own module. Each node creates its admin container during server start, before compose runs, and keeps it until the runtime shuts down. Through it the runtime:

  • creates pools of every other module (GetOrCreatePool), whether the request comes from a client's AsyncCreate, the compose section of the configuration or the dashboard;
  • destroys and unplugs pools (DestroyPool), running each module's own Destroy first so buffered data is made durable;
  • drains the cross-node send queues and answers client connection handshakes;
  • registers shared-memory and GPU memory backends that clients allocate (RegisterMemory);
  • adds nodes, migrates containers and redistributes a dead node's containers;
  • probes peers for liveness (SWIM and the task-progress probe);
  • answers monitoring queries and serves the web dashboard.

Where it sits

Admin is not part of the data path and not in any interposition chain. Every other module depends on it:

  • Pool creation. A module client's create task is a GetOrCreatePoolTask addressed to the admin pool, not to the module's own pool (clio::run::kAdminPoolId). The MOD_NAME template's AsyncCreate shows the pattern; see Module template.
  • Pool destruction. Each module's kDestroy handler receives the admin DestroyPoolTask (it is the standard DestroyTask), and reports what it flushed in that task's blobs_flushed_ and bytes_flushed_.
  • The CLI. clio-run stop sends StopRuntime, clio-run start --induct broadcasts AddNode, clio-run status sends Heartbeat, clio-run pool and clio-run compose use Compose, ListContainers and the two-phase DestroyPool, clio-run migrate sends MigrateContainers, clio-run monitor sends the worker_stats Monitor query and clio-run viz sends the viz_* queries.
  • The IPC manager. A client connecting to the runtime sends ClientConnect; a client that grows its shared memory, or allocates a GPU backend, sends RegisterMemory.
  • The scheduler. The default scheduler pins the admin periodics that own network sockets to dedicated workers: Send (14) to the network send worker; Recv (15), ClientRecv (20) and ClientSend (21) to the network receive worker.

Pool id 1.0 is reserved (kAdminPoolId in context-runtime/include/clio_runtime/types.h). A default-constructed clio::run::admin::Client targets it, and CLIO_ADMIN returns the process's admin client.

Composing it

Admin does not appear in compose and must not be added there. PoolManager::ServerInit creates it on every node with a local create of module clio_admin, pool name admin, pool id 1.0. clio-run start exits with an error if it cannot find the clio_admin module. Its container count is one per node, and recovery never moves it (see below).

Creating pools

  1. A create sent with a Dynamic pool query is resolved by admin's scheduler hook: Local if a pool of that name exists on this node, or if the create names a fixed pool id that exists here; Broadcast otherwise.
  2. A client create for a pool that the configuration's compose section defines (matched by pool id, or by name when the create names no id) waits, yielding, until compose has created it, for up to 300 seconds. Without this wait a client could create the pool first with default parameters.
  3. PoolManager::CreatePool then creates the pool, or binds to the existing one, and awaits the module's own Create. An exception sets return code 99.

Destroying and unplugging pools

DestroyPool takes a bit set of destruction flags, defined in admin_tasks.h. The same flags reach the module's own Destroy:

kDestroyPoolKeepRestartable (0x1)
Keep the pool's entry in each node's pool log, so the next clio-run start re-creates it. clio-run pool stop sets it.
kDestroyPoolNoFlush (0x2)
Skip the flush and go on even if the module's Destroy fails (--force). Buffered, unflushed data is discarded.
kDestroyPoolDeleteData (0x4)
Delete the pool's data: backing files, metadata logs, cached copies. clio-run pool rm sets it.
kDestroyPoolQuiesceOnly (0x8)
Run the module's Destroy but keep the pool: phase one of a two-phase destroy.

The client helper UnplugPool issues both phases as Broadcast: phase one with kDestroyPoolQuiesceOnly makes every node flush while all containers of the pool still exist, since a multi-node pool's containers flush to each other; phase two removes the pool. On a node that hosts a real container of the pool, admin first sends the module's kDestroy as a local subtask and adds its flushed counters to the task. A nonzero return from the module stops the destroy and leaves the pool running, unless kDestroyPoolNoFlush is set. If the module names an unplug successor, the pool manager installs a redirect to it.

Create also starts the peer receive threads and, in SHM mode, the thread that drains the inbound shared-memory rings, and registers a hook that stops them before the transport is freed.

The send loop

Each tick of Send snapshots the depth of the four network send queues. It drains the two latency queues completely, then drains the two bulk I/O queues alternately up to a byte budget per tick (kNetQueueIoByteBudget). A tick that takes 500 ms or more logs a [SLOW-SEND-TICK] warning with a per-phase breakdown. The period is held at or below 50 µs by a static assertion, because the worker services periodic tasks in buckets by period and a longer period would put every cross-node send into a much slower bucket.

Failure detection and recovery

SWIM

HeartbeatProbe does nothing unless swim: enabled: true. When enabled, each tick:

  1. Sends one direct Heartbeat to the next peer in round-robin order, skipping peers that are suspected, probe-failed or already being probed. Dead peers are still probed, so a node that comes back can be seen.
  2. A direct probe that times out, or completes with an error, marks the peer probe-failed and asks up to three random live peers to probe it (ProbeRequest). With no live helper, the peer is marked suspected at once.
  3. When every indirect probe fails or times out, the peer becomes suspected.
  4. A suspected peer past the suspicion timeout is declared dead, unless it has sent this node traffic within that timeout. Then the leader starts recovery.
  5. A successful probe of a dead peer marks it alive again (rejoined).

If more than half of the other nodes are suspected or dead, the node self-fences: it logs an error, keeps probing, and skips recovery. The fence clears when connectivity returns.

Task-progress probes

Independently of SWIM, the Send loop's maintenance step probes nodes that hold cross-node tasks for too long:

  • Replicas outstanding beyond task_progress_interval_ms get a QueryTaskProgress probe to the node holding them, at most 256 new probes per scan, each with a 5 second network timeout. Two "gone" answers for the same replica let the origin stop waiting for it.
  • Peers heard from before but silent for 10 seconds get an idle probe. Peers held dead are re-probed every 2 seconds, so a node that only lost connectivity can answer and rejoin.
  • A probe with no answer for CLIO_PROBE_SILENCE_S (default 30 s) marks its target dead, unless anything was heard from that node, or a pong arrived on the control channel, within that window. Three consecutive failed probes have the same effect. If this node's own scan ran late, pending probes are re-armed instead of judged.
  • A node that receives rejoin notices from at least half of its peers within 60 seconds records that it was failed over, so that state it homes (for example the filesystem's cached home directories) is reloaded, since a stand-in may have changed it.

Recovery

Recovery is run by the leader, the lowest-numbered node this node sees alive. It is claimed once per membership epoch and dead node, so a node that dies, rejoins and dies again is recovered again. The plan assigns each of the dead node's containers to the destination its pool's local container chooses (ScheduleRecover), or round-robin over live nodes. The plan is broadcast as RecoverContainers: every node updates its address table and write-ahead log; each destination creates the container and calls its Recover. The admin pool is never in a plan, since every node already has its own admin container.

Configuration

Admin has no compose entry. It reads these runtime settings:

swim.enabled
Default false. Turns on the SWIM detector. The default configuration explains why it is off: a wide collective can starve probe replies long enough to declare healthy nodes dead.
swim.direct_probe_timeout_sec
Default 300.0. Deadline for a direct probe's reply.
swim.indirect_probe_timeout_sec
Default 150.0. Deadline for an indirect probe; also how long a ProbeRequest waits for its heartbeat.
swim.suspicion_timeout_sec
Default 3600.0. Time from suspected to dead, which triggers recovery.
runtime.task_progress_interval_ms
Default 5000. How long a cross-node task may run before its node is probed. 0 disables the stuck-task and idle probes. The environment variable CLIO_TASK_PROGRESS_INTERVAL_MS overrides it.
runtime.client_reap_grace_s
Default 30. WreapDeadIpcs reclaims a dead client's shared memory only when it has no task in flight and has been idle this long. 0 never reaps while the runtime runs.
viz.enabled, viz.port, viz.bind, viz.max_threads
The dashboard admin starts. Defaults: off for an embedded runtime, port 8080, bind 127.0.0.1, 16 threads. clio-run start enables it unless the configuration or CLIO_VIZ_ENABLE says otherwise. See Dashboard.
CLIO_PROBE_SILENCE_S (environment)
Default 30. Silence window of the task-progress probes.

The dashboard

Admin starts one HTTP server per node in its Create and owns the dashboard shell: / lands on /viz/clio_admin/index.html, with pages for nodes, pools and configuration in admin/viz/. Its routes, in src/admin_viz.cc, are /api/health, /api/topology, /api/pools, /api/config, /api/routes, /api/chimods, the per-node /api/nodes/{node}/workers, containers, bdevs and system_stats (Monitor queries above), /api/pools/{pool}/monitor for any module's Monitor, and two writes: POST /api/pools/compose and POST /api/pools/{pool}/destroy. The destroy route refuses the admin pool. A port already in use disables the dashboard; it never fails the runtime. See the dashboard tutorial.

Behaviors worth knowing

  • Recovery never redistributes the admin pool. Moving it would build a second admin container on a survivor and duplicate its periodic tasks.
  • RecoverContainers is idempotent: an assignment whose container already exists on the destination is skipped.
  • MigrateContainers fails a container that is not hosted on the node running it, rather than migrating that node's own container of the pool. Run it on the node that hosts the container.
  • StopRuntime does not tear down the runtime on the worker that runs it. It requests the stop and returns; shutdown proceeds after the reply. StopRuntimeTask::kForceShutdown (clio-run stop --force) skips the graceful teardown.
  • Flush checks the containers of the node it runs on. Admin's own remaining work is the number of cross-node tasks in its send and receive maps.
  • At server start the runtime replays the pool log itself. RestartContainers is the same replay as a task; the CTE restart and replication-persistence integration tests use it.
  • With SWIM disabled, the task-progress probes can still mark a silent node dead, so that tasks waiting on it fail instead of hanging.

Limits

  • One admin pool per runtime, at 1.0 and named admin. Multiple admin pools are not supported.
  • The leader is computed from each node's own membership view. During churn two nodes can both believe they lead; the per-epoch claim prevents one node from recovering the same death twice, not two nodes from each starting one.
  • Recovery re-creates containers through their Recover method. What state survives is up to each module; admin moves ownership, not data.
  • Device memory (kGpuDeviceMemory) is registered by recording the client's handle bytes; opening the IPC handle on the runtime side is not implemented yet.
  • The GPU and HBM fields of system_stats are always zero.
