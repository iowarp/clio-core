What it does

The CTE runs two cores that never move data between each other: a volatile core (540.0) on DRAM, which has no write-ahead log and is empty after every start, and a persistent core (512.0), normally reached through the replication module (561.0). A policy cache joins them. The write-through policy writes every put to the persistent chain, then updates a copy of the blob in the volatile core so later reads are served from RAM.

All logic lives in the shared policy-cache base, context-transfer-engine/cache_base (CacheBase, derived from the core's DualTargetInterposer). This module only fixes the policy. The write-back module, which the default configuration composes at 567.0, is the same code with the other policy, and most of its mechanics (locking, fill, eviction, tag deletes) apply here unchanged.

Consistency model

Write-through is strongly consistent at this module's interface:

  • Every blob verb runs on the blob's owner container (chosen by hashing tag and blob name), so each blob has at most one volatile copy in the cluster, and every operation on a blob is serialized there by a per-blob lock.
  • A put is acknowledged after the persistent chain has accepted it and the owner's volatile copy has been brought up to date (or removed, if it could not be). A read from any node after the acknowledgement sees the write, with no fsync needed.
  • The volatile copy never holds bytes the persistent chain lacks. A crash of the cache loses nothing that was acknowledged.
  • Acknowledged means accepted by the persistent chain, not synced to a device. Device durability still comes from the chain itself: its tiers, its write-ahead log, replication and SyncTag (fsync). See durability.

Where it sits

It takes the write-back cache's place in the chain:

indexer(564.0) -> shm cache(568.0) -> [compressor(562.0) ->]
  core_persist_write_thru
  -> volatile core(540.0)
  -> replication(561.0) -> persistent core(512.0)

The persistent chain (next_persistent) is the interposer's single next pool: every verb the module does not handle is forwarded there and owner routing follows the core's rules. The volatile core (next_volatile) is reached only through a core client with local queries.

  • Interposed core verbs, with the core's method ids: PutBlob (15), GetBlob (16), DelBlob (18), DelTag (19), GetBlobSize (23), FlushData (34), TruncateBlob (37), MultiPutBlob (48) and SyncTag (56), plus Create, Destroy and Monitor.
  • Own verb: DropTagCopies (100), sent by the cache to its own containers to drop a tag's copies. clio_mod.yaml also lists ids 101 and 102, which the dispatch table does not implement.
  • Every other core verb is forwarded to the persistent chain.

Composing it

Choose a pool id other than 566.0. The default id in core_persist_write_thru_tasks.h is the same as the checkpoint module's fixed id, which vector copies look up by number. Set pool_id explicitly in the compose entry, as below, whenever checkpoints may be used.

The default configuration does not compose this module. To use it, put an entry like this in place of the write-back entry, after the volatile core, replication and the persistent core:

compose:
  - mod_name: clio_cte_core_persist_write_thru
    pool_name: clio_cte_core_persist_write_thru
    pool_query: local
    pool_id: "566.0"
    next_volatile: "540.0"              # volatile core (required)
    next_persistent: "561.0"            # replication -> persistent core
    fill: on_hit_count:2                # on_hit_count:N | on_read_miss | none

Then point the shm cache's next_pool_id (or the compressor's, when composed) at "566.0", and set the shm cache's invalidate_on_flush to false. That option relies on a write-back cache below landing each flushed range through the shm cache; this module flushes nothing, so the shm cache must invalidate on every write instead. The pool id is free to choose: the clio-fs test suite composes this module at 567.0 when run with --cache write_thru.

Create fails with return code 1 when next_volatile is missing. Without next_persistent the module is volatile-only and forwards every verb to the volatile core. The client class, clio::cte::core_persist_write_thru::Client, is a core client plus AsyncCreateCache.

Configuration

The module reads the same keys as the write-back cache (PolicyCacheParams in cache_base/include/clio_cte/cache_base/cache_config.h). A malformed value is logged and leaves that key at its default.

next_volatile
The volatile core, as "major.minor". Required.
next_persistent
The persistent chain. Unset: volatile-only.
fill
When a read miss copies the blob into the volatile core: on_hit_count:N on the Nth miss (default on_hit_count:2; N of 0 is treated as 1), on_read_miss on every miss, none never. It governs reads only; writes always refresh or create the copy.
evict
lru (default) or lfu. Parsed, but eviction orders victims by last access time only, so both evict least-recently-used copies.

Ignored by this policy: flush_period_ms, flush_fill_pct, flush_dirty_mb, flush_pool and fallback_to_persistent. No flusher or stop hook is started, since nothing is ever dirty.

Routing

  • Blob verbs (PutBlob, GetBlob, GetBlobSize, DelBlob, TruncateBlob) are routed exactly as the core routes them: to the blob's owner, with the core's failover applied.
  • FlushData and DropTagCopies stay on the container they were sent to.
  • When a blob verb reaches a container that does not own the blob (an interposer above forwards to its local container), it is sent on to the owner. If the owner dies in flight, the request is resent up to ten times, one second apart, to whichever container failover then names. Appends are not resent, since a lost one may have landed.

Write path

  1. Lock the blob on its owner.
  2. Special puts (append, replace, put-if-absent, put-if-version) depend on the persistent copy's state: the volatile copy is dropped, the put goes to the persistent chain, and no copy is kept.
  3. Write persistent. The put is forwarded to the persistent chain. If it fails, the put fails and the copy is left as it was.
  4. Refresh the copy. If the blob has no copy yet and the write covers only part of an existing persistent blob, the whole blob is first read from the persistent chain into the volatile core, so a copy is always the entire blob. The written regions are then put into the volatile core. On no-space, up to four least-recently-used copies are evicted and the put is retried once.
  5. If the copy cannot be refreshed, it is deleted from the volatile core. The put still succeeds: persistent holds the bytes, and the next read goes there.
  6. Acknowledge.

Batched writes

A MultiPutBlob whose records the receiving container all owns locks every record's blob in key order, drops their volatile copies, forwards the batch to the persistent chain, and releases the locks only afterwards, so no read can refill a copy that misses the batch's bytes. The next read refills per fill. A batch with records owned elsewhere is split into one PutBlob per record, each sent to its owner, where it takes the write path above.

Reads

  • GetBlob on the owner: a present copy serves the read from the volatile core. If the copy fails to serve, it is dropped and the read goes to the persistent chain.
  • Miss: the read is served by the persistent chain. If fill admits the blob, the whole blob is then copied into the volatile core (a partial read fills the whole blob).
  • GetBlobSize answers from the copy's size when a copy exists, else from the persistent chain.
  • Other reads (tag sizes, blob listings, searches, Pod reads) go straight to the persistent chain: the copies hold nothing it lacks.

Deletes, truncates and writes behind the cache

  • DelBlob drops the copy, then deletes on the persistent chain.
  • TruncateBlob drops the copy, then truncates the persistent blob.
  • DelTag is forwarded to the persistent chain, then broadcast as a tag delete on the persistent chain and as DropTagCopies to every container of this pool.
  • PodPutBlob and PodMultiPutBlob write behind the cache: every live container drops its copies of the tag before the write and again after it.
  • Writes sent straight to the persistent pools, bypassing this module, invalidate nothing; an existing copy keeps serving the old bytes.

fsync and flush

SyncTag finds nothing dirty and is forwarded to the persistent chain, which syncs its devices. Concurrent syncs of the same tag with the same arguments share one round. FlushData completes at once with nothing flushed; the module starts no periodic flush.

Eviction and capacity

  • Eviction is a DelBlob of the copy on the volatile core, choosing among up to 256 least-recently-used unlocked copies. Every copy is clean, so eviction never writes anything.
  • A full volatile core never fails a put. The put is already on the persistent chain; only the copy is skipped.
  • The cache has no size setting of its own; it uses the volatile core's tiers and their capacity_limit.

Stop, unplug and restart

  • clio_run pool stop <pool> has nothing to flush. After the pool is removed, tasks addressed to it are redirected to the persistent chain. clio_run pool rm <pool> also drops every volatile copy.
  • On restart the volatile core is empty and the cache's bookkeeping is gone. Every acknowledged write is on the persistent chain; copies refill on read per fill, or on the next write.
  • A dead owner's copies die with it. With the core's failover_to_successor and replication's remote copies, its blobs are served by the successor from the persistent chain.

Monitoring

The Monitor query stats returns the same msgpack map as the write-back cache, with policy set to "write-through"; its dirty and flush counters stay at zero. dirty_count returns 0. Other queries are forwarded to the persistent chain.

Behaviors worth knowing

  • Every put pays the persistent chain's latency, plus one extra copy of the payload into the volatile core.
  • Writes allocate: a written blob gets a volatile copy whatever fill says, so a write-once stream can push hot data out of the volatile core.
  • A partial write to a cold blob reads the whole blob from the persistent chain to build the copy.
  • Batched writes to blobs the container owns drop their copies instead of refreshing them.

Limits

  • evict: lfu is accepted but behaves like lru.
  • The copy is kept only on the blob's owner; a read from another node crosses the network to it.
  • Writes that bypass the module leave existing copies stale.

Write-through or write-back

Choose write-through when an acknowledged write must already be on the persistent chain and visible from every node without an fsync: for example, applications that share files across nodes without calling fsync, or deployments where losing buffered writes on a crash is not acceptable. The cost is the persistent chain's latency on every write. Choose the write-back cache, the default, when applications mark durability and cross-node visibility points with fsync and should otherwise write at RAM speed.

How it is tested

  • context-transfer-engine/test/unit/test_policy_cache.cc (ctest cte_policy_cache) creates a write-through cache at 566.0 over a persistent file core and a volatile RAM core. "Write-through: persistent first, copy kept current" checks that a full write and a partial overwrite reach both cores immediately. "A blob read twice is filled into the volatile core" checks on_hit_count:2 admission and that a partial read fills the whole blob.
  • context-transfer-engine/test/integration/clio_fs_suite: suite.py --cache write_thru runs the multi-node filesystem suite with this module at 567.0. Its agents then skip the fsync on close they use under write-back, so the suite checks that writes are visible across nodes at once.
