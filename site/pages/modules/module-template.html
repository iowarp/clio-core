What it is

The template is a complete, buildable module named MOD_NAME in namespace clio::run. context-runtime/modules/CMakeLists.txt always builds it, next to admin, bdev and safe-bdev, producing clio_MOD_NAME_client and clio_MOD_NAME_runtime.

It plays two roles:

  • Starting point. Copy the directory, rename it, delete the test methods and add your own. Build a ChiMod walks through this file by file, and Write a chain operator builds a complete module outside the tree.
  • Test vehicle. Runtime tests and benchmarks use its methods to drive the scheduler, coroutines, locks, output streaming and collectives: its own unit tests, the recovery, migration, leader-election and reconnect integration tests, and the throughput benchmark clio_run_thrpt_bench, which measures round-trip latency with Custom.

Operations

Every method in MOD_NAME/clio_mod.yaml. Ids 2 to 5 (NodeFailure, Recover, Migrate, Upgrade) are -1, not implemented.

IdMethodWhat the handler does
0CreateCounts the create and logs. The container is already initialized when it runs.
1DestroyLogs and returns 0. A real module releases its resources here.
9MonitorIgnores the query and returns ten sample records (id, value, name) as msgpack: the shape a dashboard page can decode.
10CustomA configurable test task. With chain_depth_ above 0 it sends itself a child Custom and awaits it; at depth 0 it sleeps block_us_ and busy-spins spin_us_ without yielding. It does not modify data_ or read operation_id_.
20CoMutexTestHolds a CoMutex for hold_duration_ms_.
21CoRwLockTestHolds a CoRwLock as reader or writer for hold_duration_ms_.
23WaitTestRecurses through the client to depth_ levels, awaiting each subtask.
24TestLargeOutputReturns 1 MiB of output (byte i is i % 256), to exercise output streaming.
25GpuSubmitComputes test_value_ * 2 + gpu_id_, so a GPU-submitted task's result can be checked.
26SubtaskTestReturns test_value_ + 1.
27ManyToOneSumCollective sum for PoolQuery::ManyToOne: members' inputs are folded by AggregateIn, and the handler copies the total to sum_.
28AllReduceThe same sum for PoolQuery::AllToOne, the analogue of MPI_Allreduce with MPI_SUM.
29BarrierNo payload. Completing it under PoolQuery::AllToOne means every participant arrived.

Each client method takes a PoolQuery first. The create, like every module's, is a GetOrCreatePoolTask<CreateParams> sent to the admin pool, not to the module's pool; see Admin:

clio::run::MOD_NAME::Client client(pool_id);
auto create = client.AsyncCreate(clio::run::PoolQuery::Dynamic(),
                                 "my_pool", pool_id);
create.Wait();
auto task = client.AsyncCustom(clio::run::PoolQuery::Local(), "hello", 0);
task.Wait();

How the code is generated

Two files under autogen/ are generated from clio_mod.yaml by clio-run refresh <repo_dir> (the older spelling clio_run repo refresh <repo_dir> still works). <repo_dir> is the directory that holds a clio_repo.yaml; for the in-tree modules that is context-runtime/modules. The command:

  1. Reads clio_repo.yaml and regenerates every module named in its modules: list. In the tree that list is MOD_NAME, admin and bdev.
  2. Takes every top-level key of the module's clio_mod.yaml that starts with k and has an integer value as a method. Methods set to -1 are skipped; ids below 10 are grouped as inherited. kRestart, if set to 0 or more, generates a Restart override instead of a dispatch case.
  3. Writes include/<prefix>/<module_name>/autogen/<dir>_methods.h: a GLOBAL_CROSS_CONST per method, kMaxMethodId (one past the largest id) and GetMethodNames(). The include prefix is found on disk, the first include/ subdirectory that holds the module's runtime header (clio_runtime here); with none, it is the namespace with :: as _.
  4. Writes src/autogen/<dir>_lib_exec.cc: Init, Run, SaveTask, LoadTask, AllocLoadTask, the Local* variants, NewCopyTask, NewTask, AggregateOut and AggregateIn.

The dispatch relies on naming. Key kFoo calls a handler Foo with a task type FooTask. The exceptions are kCreate (CreateTask), kDestroy (DestroyTask) and methods starting with GetOrCreate, which use the templated GetOrCreate…Task<CreateParams>. Both files are overwritten on every run; keep hand edits out of them.

The generated Init calls the base Init, builds the module's own client_, and registers the per-method cost model (DefineModel(Method::kMaxMethodId)) and the method names, which the dashboard and the scheduler's cost model use.

Starting a module from it

  1. Copy context-runtime/modules/MOD_NAME to the new module's directory, in the tree or in your own repository with a clio_repo.yaml at its root.
  2. Rename the files, the include directory and every MOD_NAME identifier. Set module_name and namespace in clio_mod.yaml, and make chimod_lib_name in CreateParams match LIB_NAME in CMakeLists.txt.
  3. In clio_mod.yaml, keep ids 0, 1 and 9, delete the test methods, and number your own from 10. A chain operator that speaks the storage engine's interface uses ids of 100 and above so they never collide with the engine's (see Custom data operators).
  4. Add the module to modules: in clio_repo.yaml and run clio-run refresh on that directory.
  5. Write one task struct and one Async* client method per method, and the handlers in the runtime source. Remove the template's test-only state (the counters, the static locks, the cost cases for deleted methods).
  6. Build, point CLIO_REPO_PATH at the build directory, and start the runtime. Build a ChiMod covers the build, loading and composing steps.

Existing guides copy the dispatch file by hand. Custom data operators advises copying the dispatch file from an existing operator rather than generating it. The generator described above now finds the include prefix on disk; either way, check that the generated #include lines name your headers.

Configuration

The template's CreateParams carries worker_count_ (default 1) and config_flags_ (default 0). They are serialized with the create task, but nothing in the runtime reads them. It has no LoadConfig, so it reads no keys from a compose entry; a module meant to be composed adds one, as described in Build a ChiMod.

Behaviors worth knowing

  • Custom's spin does not yield. That is deliberate: tests and the scheduler benchmark use it to wedge a worker. A real handler waits with CLIO_CO_AWAIT.
  • The CoMutex and CoRwLock used by the lock tests are static members, shared by every MOD_NAME container in the process.
  • GetTaskStats shows how to report task costs: fixed costs, data-proportional costs and per-item costs, keyed by method. See Report task costs.
  • The collective tasks show the two aggregation hooks: AggregateIn folds a member's inputs into the aggregate task, and AggregateOut merges a replica's outputs back into the origin.
  • GetWorkRemaining returns 0, so admin Flush never waits on a MOD_NAME container.

Limits

  • No method does useful work: the module is a template and a test fixture, not a service to deploy.
  • No state survives a restart, a migration or a recovery; the template overrides none of Restart, Recover, Expand or Migrate.

How it is tested

  • context-runtime/modules/MOD_NAME/test: cr_all_flush_tests (test_flush_correctness.cc, admin Flush), cr_all_comutex_tests (test_comutex.cc), cr_all_wait_functionality_tests (test_wait_functionality.cc), cr_all_streaming_tests (test_streaming.cc, 1 MiB outputs) and cr_all_collective_tests (test_collectives.cc, single-node ManyToOneSum, AllReduce and Barrier). test_stall_migration.cc builds clio_run_stall_migration_tests, which is not registered with ctest.
  • context-runtime/test/unit/test_autogen_coverage.cc and context-runtime/test/unit/autogen_more: the generated dispatch code.
  • context-runtime/test/integration: recovery, migrate, leader_elect, reconnect and collective_bench create MOD_NAME pools on Docker clusters.
