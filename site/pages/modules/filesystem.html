What it does

The CTE core stores blobs in tags and knows nothing about paths, sizes that differ from the bytes stored, directories or permissions. The filesystem module adds exactly that layer, in one place, so every entry point behaves the same: the libfuse daemon clio_cte_fuse, the POSIX, STDIO and MPI-IO interceptors and the HDF5 VFD all delegate to it.

  • Namespace: names, directories, hard links, symbolic links and rename, stored as directory blocks with no metadata server.
  • Inodes: one record per file, directory or symlink with type, mode, owner, times and link count.
  • File data: offsets map to 1 MiB page blobs in the file's own tag, written through the chain at next_pool_id.
  • Logical size: delegated to the stream module, which also merges deferred O_APPEND writes from many nodes.

For what Context FS is and how to mount it, start at the Context FS overview. The filesystem design page walks through every operation and the consistency model step by step; this page lists the module's contract.

Where it sits

The filesystem is not an interposer. It speaks its own task interface (paths and handles, not tags and blobs) and is a client of the CTE pool named by next_pool_id, which should be the top of the interposition chain. In the default configuration that is the indexer:

filesystem(560.0) --pages, blocks, records--> indexer(564.0) -> shm cache(568.0)
    -> [compressor(562.0) ->] write-back(567.0) -> volatile core(540.0)
                                                -> replication(561.0) -> core(512.0)
filesystem(560.0) --sizes, appends--> stream(565.0)
  • Called by: the filesystem client library, shared by clio_cte_fuse and the interceptors. Path operations are sent to the local container; operations on an open handle go straight to the container that issued it.
  • Calls: the CTE pool at next_pool_id for pages, directory blocks, inode records and xattrs; the stream pool for sizes; and its own pool on other nodes for namespace state they own (ShardOp).
  • Data path bypass: clients that write pages themselves (the FUSE adapter) ask the pool for its chain with the Monitor query next_pool and write there directly, so their bytes still pass through replication and the caches.

Clients find the pool by name, not id: the client resolves clio_cte_filesystem, or the name in CLIO_CFS_POOL, which may also be a literal "major.minor" id. It then reads next_pool, stream_pool and data_score from the pool's Monitor. The client creates nothing; an adapter fails if the pool is not composed.

The comment above this entry in clio_default.yaml calls 560.0 "clio::cte::filesystem::kCfsPoolId". No such constant exists in the source; the module defines only the default pool name (kCfsPoolName). 560.0 is the id the default configuration gives it.

Composing it

The entry shipped in context-runtime/config/clio_default.yaml, with its commented defaults. It must come after every chain pool it names and after the stream entry.

compose:
  # ... chain entries (core, replication, write-back, shm cache, indexer) ...
  - mod_name: clio_cte_stream
    pool_name: clio_cte_stream
    pool_query: local
    pool_id: "565.0"
    next_pool_id: "564.0"
    staging_pool_id: "561.0"

  - mod_name: clio_cte_filesystem
    pool_name: clio_cte_filesystem
    pool_query: local
    pool_id: "560.0"
    next_pool_id: "564.0"               # required: the chain top
    metadata_log_path: "${CLIO_STORAGE_ROOT}/cfs_namespace_log"
    # dir_split_entries: 1024
    # dir_log_compact_bytes: 256KB
    # case_insensitive: false
    # data_score: -1.0
    # data_score_head_pages: 1
    stream_pool_id: "565.0"

Pointing next_pool_id at 512.0 bypasses the chain and stores everything in the persistent core directly. Leaving out the stream entry and stream_pool_id is also valid: the filesystem then creates its own stream pool (see Configuration).

Operations

Every method in filesystem/clio_mod.yaml. Return codes are errno values. "Local" routing means the task runs on the submitting node's container, which resolves the path from its own cache of directory blocks; "handle" means it goes to the container whose id is encoded in the top 16 bits of the handle, the inode's home.

Data layout

Everything the module stores is ordinary tags and blobs in the pool at next_pool_id, so tiering, replication and durability apply to metadata and data alike. Verified in fs_shard.h, fs_inode.h, fs_inode_table.h and filesystem_runtime.cc:

Inode ids
Every file, directory and symlink is one CTE tag, and its tag id packed as (major << 32) | minor is the inode number. A container-minted id has major 0x40000000 | home (plus the minter in bits 16 to 28 for newer ids); a client-minted id from a batched create has major 0x80000000 | node << 16 | home. The root directory is the fixed id 0x3FFFFFFF.1.
Inode home
The container encoded in the id. A new file's home is a hash of its own path modulo the container count, so one directory's files spread over every node instead of following the directory.
File data
Blobs named by decimal page index ("0", "1", ...) of 1 MiB each, in the file's tag. Each page is placed by the CTE core's own blob hash. A missing page within the logical size is a hole.
Inode record
Key ~i in the xattr section of the inode's own tag: type, a size snapshot, link count, mode, uid, gid, times, flags (orphan, has-xattrs, fresh), the symlink target, the writing container, a directory's parent and name, and on the root the volume flags and case-fold table version. Format tag CFI2; records of the earlier CFI1 format are refused.
Directory blocks
A directory's rows (canonical name to inode id, type, spelling, state) are split into blocks by extendible hashing: block 0 holds every name at first, and a block over dir_split_entries rows splits by the next hash bit into block k + 2^depth, to a maximum depth of 24. Blocks never merge. Block k is blob d.<k> in the directory's tag, and the container that owns that blob is the block's home. With metadata_log_path set the home keeps it in its node-local journal instead.
Row states
Live, pending (reserved but invisible) and leaving (visible but frozen), so multi-step operations such as mkdir and rename can be finished or undone after a crash.
Extended attributes
One blob per inode, named by its packed id in decimal, in the global tag _clio_xattr_store. Kept out of the file's tag so they never count toward its stored size.
System records
Tag _clio_fs_sys: each container's durable id reservation and its list of inodes unlinked while open.
CTE tag names
Each link is published to the CTE as tag name <leaf>/<inode number>, in batches after each namespace operation, so TagQuery and the indexer see file names. The names are flat and unique per inode; full paths exist only in the directory blocks.
Sizes
The authoritative logical size is the stream pool's, at a stream home equal to the inode home, so the home reads it in-process.

Configuration

Keys read by FilesystemConfig::LoadConfig. Parsing is best-effort: a malformed value leaves the rest at their defaults without an error.

next_pool_id
Required, no default. The CTE pool that stores pages, directory blocks, inode records and xattrs. Without it the pool's create fails. Default configuration: "564.0", the indexer at the chain top.
metadata_log_path
Default unset. Base path of this node's on-disk metadata; ~ and ${VARS} expand. The directory journal is <path>.dirs.<container id>: one small record per change, fsynced by kSyncMeta and every 1 s, and compacted at startup. When the filesystem creates its own stream pool, that pool logs to <path>.stream. Unset, directory blocks are written as CTE blobs, one blob write per change.
stream_pool_id
Default unset. The stream pool for sizes and appends. Unset, the filesystem creates one named <pool_name>_stream at the id one minor above its own (560.1 for a pool at 560.0), over the same next_pool_id. The default configuration names "565.0", a stream pool composed just before it. A pool that already exists keeps its own configuration: the filesystem's .stream log path applies only to a stream pool it creates.
dir_split_entries
Default 1024. Rows a directory block holds before it splits. Values below 16 are raised to 16.
dir_log_compact_bytes
Default 256KB (a size string). Bytes of delta frames a block's CTE blob may hold past its last full image before the next commit rewrites it whole. 0 rewrites the block on every commit. Applies when blocks are stored as blobs.
case_insensitive
Default false. Compare names by Unicode simple case folding while keeping their spelling, as NTFS does: Foo.TXT and foo.txt are one file, Straße and STRASSE are not. Recorded in the root's record when the volume is created; a runtime configured the other way refuses the volume with EINVAL.
data_score
Default -1.0 (off). A value in (0, 1] places file data pages with that score, leaving the highest-scored tier to directory blocks, records and the first data_score_head_pages pages of each file. Any other value is ignored with a warning. The stream pool and the FUSE adapter apply the same rule to the pages they write.
data_score_head_pages
Default 1. Leading 1 MiB pages of each file that keep the default score when data_score is set; 0 means every page uses data_score.

Environment variables read by the runtime side of the module:

  • CLIO_CFS_SHM_FILE_CAPACITY: file records in the shared-memory attribute mirror. Default 262144.
  • CLIO_CFS_SHM_MIRROR_MULTINODE=1: keep the mirror on a multi-node deployment. Only safe when files are never shared across nodes.
  • CLIO_CFS_PREALLOC: a flat per-page preallocation in bytes for kWrite. Unset, each put preallocates twice the written extent of the page, at least 8 KiB and at most 64 KiB.

The CLIO_FUSE_* variables belong to the mount daemon and are listed in the Context FS API reference.

Caches, homes and leases

  • One writer per object. A directory block's home is the only container that changes it, and an inode's home the only one that changes its record. Other containers cache copies and register with the home.
  • Push before acknowledge. The home pushes every change to the registered holders before the operation returns, so a warm path walk on any node needs no round trip.
  • Leases. A cached block or inode is served without asking for 10 s from when it was fetched. A home that cannot reach a holder waits for that lease plus 2 s of slack before acknowledging, so a partitioned node can delay a change but not serve a stale name.
  • Shared-memory mirror. On a single node the container publishes per-path records (logical size, inode, mode, owner, time overrides) into a shared-memory segment that clients read without a task. A directory created through the module is marked complete, so a miss under it is an authoritative ENOENT. It is off on more than one node unless forced.

The consistency model on the design page covers the client-side relaxations.

Failure and restart

  • Crash-safe order. The inode record is stored before its name appears, and link counts rise before links do, so a crash leaks space rather than leaving a name without an inode.
  • Recovering start. A plain clio-run start replays the directory journal before the container answers peers, reads its id reservation and orphan list, destroys the orphans (handles do not survive a restart), reconciles restored stream sizes with inode records and republishes the tag names of every link it homes. start --fresh compacts the journal to empty. See the runtime reference.
  • Sizes after a restart. Loading an inode applies the size in its record to the stream: as the size if another container wrote the record while this one was away, otherwise as a floor, since the stream may have merged appends after the record was written.
  • Dead homes. While a home's node is dead its first live successor serves its blocks and inodes, following the CTE's failover. Each inode record is mirrored, best effort, on the home's first successor. A returning home fetches newer copies of its blocks and records from that stand-in, and a rejoin notice makes clean home blocks reload.
  • Size pushes. An AdvanceSize whose inode home died in flight is resent up to 10 times, 1 s apart, while the cluster marks the node dead.
  • Before Create. Peers can reach a container before its create has bound the CTE client; such metadata I/O waits up to 120 s, then fails with EIO.

Behaviors worth knowing

  • Unlinked files' pages and xattrs are deleted in the background by a periodic purge every 20 ms, not on the unlink path.
  • kWrite updates the in-memory times and size at once; the inode record is logged at close, and by AdvanceSize and truncate before they reply.
  • A file with more than one name, and every symlink, is published to the mirror with the fast path refused, so a second name never serves a stale size.
  • The adapters only look the pool up; composing it is the deployment's job. Remove the entry if no adapter or Context FS mount is used.
  • data_score steers placement only; it does not reserve space on the top tier. When that tier fills, metadata spills down like any data.

Limits

  • The directory journal is node-local. With metadata_log_path set, a node that never returns takes the directory blocks it was home for with it (issue #1263). Without it, blocks are CTE blobs and inherit the chain's replication, at the cost of a blob write per change.
  • Inode records are tag attributes, which the replication module does not copy; their only redundancy is the best-effort mirror on the successor.
  • case_insensitive cannot be changed on an existing volume.
  • A directory splits to at most 224 blocks.
  • SHM_CACHE_DESIGN.md in the module directory is a proposal for a separate write-through shared-memory cache chimod. It is not built; the mirror described above is what exists.

How it is tested

  • context-transfer-engine/test/unit/test_fs_inode_table.cc (cte_fs_inode_table): block and record codecs, delta application, the split tree, stable directory offsets and case folding, without a runtime.
  • context-transfer-engine/test/unit/test_cfs_fsync_durable.cc (cfs_fsync_durable): fsync through the descriptor layer puts a file's pages on the persistent tier behind a write-back cache.
  • context-transfer-engine/test/integration/cfs_distributed: a two-node Docker cluster where one node writes a file and the other must read it.
  • context-transfer-engine/test/integration/clio_fs_suite: the black-box suite through FUSE on 1 to N nodes. POSIX semantics (tests_posix.py), cross-node coherence and races (tests_dist.py), directory storms and partitions (tests_dirs.py), and crashes, node loss and restarts (tests_fault.py).
  • The adapter tests under context-transfer-engine/test/unit/adapters (libfuse, POSIX, STDIO, MPI-IO, VFD) all run on this module.
