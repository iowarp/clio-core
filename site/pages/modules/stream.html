What it does

A tag's stored bytes are not a file's size: truncating up, sparse writes and appends all make the two differ, and short reads at end of file depend on the logical one. The stream module keeps that number for every stream, in one place per stream, and serializes the operations that depend on it.

The second job is O_APPEND from several nodes. Each writer needs the current end, which moves whenever any node appends. Instead of a round trip per append to learn it, the writer stages its bytes locally and the stream's home places every node's appends at the end in batches.

The filesystem module is its main user: every Context FS file is a stream, and the FUSE daemon sends deferred appends here. Nothing in the module is filesystem-specific, so any client that manages page blobs in a tag can use it.

Where it sits

  • Called by: the filesystem module (size reads, raises, truncates, drops and fsync), the filesystem client's fsync, and the FUSE daemon's deferred O_APPEND path.
  • Calls: the CTE pool at next_pool_id for the stream's page blobs, the pool at staging_pool_id for staged appends, and its own containers on other nodes to ship batches.
  • Home container: chosen by the caller and fixed for the stream's life. The filesystem uses the file's inode home, so the size lives on the container that holds the file's record and is read in-process there. Other callers can use Client::DefaultHome(tag, n), a hash of the tag id. Size operations are sent to the home by DirectId; appends and flushes run on the caller's node.
  • Page writes are not its job. Ordinary writes go straight to the CTE chain from the filesystem or the FUSE daemon. The stream module writes pages only when it merges appends.

There is no fixed stream pool id. The filesystem names the pool in its stream_pool_id; if that is unset it creates a stream pool of its own, as described on the filesystem page.

Composing it

The entry shipped in context-runtime/config/clio_default.yaml. Compose it after the chain and before the filesystem, which then binds it by stream_pool_id.

compose:
  # ... chain entries; the replication pool 561.0 must exist first ...
  - mod_name: clio_cte_stream
    pool_name: clio_cte_stream
    pool_query: local
    pool_id: "565.0"
    next_pool_id: "564.0"               # data path: the chain top (indexer)
    staging_pool_id: "561.0"            # replication: durable, uncached
    # log_path: "/mnt/nvme/$USER/clio/cte_stream_log"

  - mod_name: clio_cte_filesystem
    pool_name: clio_cte_filesystem
    pool_query: local
    pool_id: "560.0"
    next_pool_id: "564.0"
    stream_pool_id: "565.0"

Staged appends are written once and read at most once, after a restart, so the default configuration sends them to the replication pool below every cache layer rather than through the caches.

kSizeOp takes one of these operations (StreamSizeOp):

kGet (0)
Read the size; 0 for a stream the home does not know.
kMax (1)
size = max(size, value). A write or close pushes its end with it.
kReserve (2)
Return the old size and add value: a synchronous append offset, linearized at the home.
kSet (3)
size = value, for truncate or extend.
kDrop (4)
Forget the stream and discard its pending appends, for unlink.
kSync (5)
fsync the home's size log; EIO if it fails. Sent by a file's fsync.

kSet and kDrop wait for a merge in progress on the stream, so a truncate lands after an append batch, never inside it. Other operation values are refused with EINVAL.

Append pipeline

  1. Stage. kAppend stamps the append with the origin node's clock (wall-clock nanoseconds, forced to increase on that node), its node id and a per-node counter, and writes the bytes as one blob in the staging tag. A zero-byte append returns at once.
  2. Queue. The entry, with a copy of its bytes, joins the node's queue in acceptance order, and the periodic drain starts if it is not running.
  3. Ship. Every 1 ms the drain groups the queue by stream and home and sends each group to the home as kPlan tasks of at most 16 MiB of inline bytes, one at a time. A home that cannot be reached is retried after 100 ms, and nothing newer for that stream is shipped from this node before the retry.
  4. Order. The home claims the stream (one merge at a time), first re-runs any earlier plan of the stream whose copy failed, drops entries it has already merged, and sorts the rest by clock, then origin, then counter. One node's appends therefore keep their order; appends from different nodes are ordered by their origin clocks.
  5. Reserve and log. The plan's base is the current size, the size grows by the batch, and the plan and new size are written to the log before any byte is copied.
  6. Copy. The bytes are put into the stream's page blobs, read from the batch's inline payload or, for appends recovered after a restart, from their staging blobs, in slices of up to 16 MiB. A failed copy leaves the plan open, to be retried at the same offsets.
  7. Clean up. Merged staging blobs are queued for deletion and removed by the drain, up to 512 per tick.

Appends to a stream that was dropped are discarded at the home along with their staged bytes.

The FUSE daemon chooses between this pipeline and the alternatives with CLIO_FUSE_APPEND: kernel (the kernel's cached size, the single-node default), reserve (kReserve at the home through the filesystem's AdvanceSize, then a normal write) or deferred (this pipeline, the multi-node default). See the Context FS API reference.

Data layout

Pages
A stream is a CTE tag in the pool at next_pool_id. Byte off lives in the blob named by the decimal page index off / 1 MiB, the same layout the filesystem uses for file data. Merged pages follow the page-score rule the co-located filesystem container set (data_score), otherwise the default score.
Staging tag
_clio_stream_staging in the pool at staging_pool_id, with the well-known id 0x3FFFFFFF.2 so a node can use it without reaching the tag's owner. Registration of the name is tried 5 times, 1 s apart, at create, then the well-known id is used.
Staged blob names
sa.<major>.<minor>.<home>.<clock>.<origin>.<counter>, all in hex. The name carries everything needed to merge the append, so a restarted node can find its staged appends by listing the tag.
Size log
<log_path>.<container id>, a self-checking record log with size, drop, plan, done and merged-name records. Records are written with write(2); the log is fsynced by kSync and by the drain at most every 5 s while it holds unsynced records. It is rewritten as a snapshot once 64 MiB have been appended since the last compaction.

Configuration

Keys read by StreamConfig::LoadConfig. Parsing is best-effort: a malformed value leaves the defaults.

next_pool_id
Required, no default. The pool page blobs are read from and written to, normally the chain top. Without it the pool's create fails. Default configuration: "564.0".
staging_pool_id
Default: next_pool_id. Where staged appends are written. Default configuration: "561.0", the replication pool.
log_path
Default unset. Base path of each container's size log; the container id is appended. Unset, nothing is persisted by this module. The configuration file's comment states that file sizes then do not survive a stop and start. A stream pool created by the filesystem instead logs to the filesystem's metadata_log_path plus .stream.

The module reads one environment variable: CLIO_TRACE_STREAM=1 logs one line per merge plan (its node, base offset, bytes and the range of appends from each origin).

Failure and restart

  • Only the home merges. A plan sent to a stand-in for a dead home is refused with EIO, because the stand-in does not know the stream's end. Origins keep the staged appends queued and retry until the home is back.
  • Flush while the home is down. kFlush fails with EIO once it has waited 5 s and the home's node is dead; the appends stay queued. Any flush fails with ETIMEDOUT after 120 s.
  • Recovering start. With a log, a plain clio-run start replays sizes, drops and open plans, then compacts. start --fresh discards the log.
  • Restored sizes are held. A restored size may be stale, since the file may have been served elsewhere while the node was down. Size operations and merges on a restored stream wait until its owner reconciles it, at most 120 s. The filesystem does this when it loads the inode: it applies the record's size as a floor, or sets it outright, discarding open plans, when another container wrote the record meanwhile.
  • Interrupted merges are finished from the drain after reconciliation, at their logged offsets.
  • Staged appends. At create, a restarted node lists the staging tag on every container and re-queues the appends it originated. Appends originated elsewhere are still queued on their own nodes.
  • Exactly once. The home remembers merged staged names and skips them in later batches, so a retried batch never merges twice. The memory is pruned of names older than 600 s once it passes 220 names, and kept in the log's snapshot.
  • Before Create. Tasks that arrive before the container's create has opened its log wait up to 120 s, then fail with EIO.

Behaviors worth knowing

  • An append returns once its bytes are durably staged, before it has an offset. A reader sees it after a kFlush; the FUSE daemon flushes a file's pending appends before it stats, reads or truncates the file and when it publishes the file on close.
  • A flush waits only for appends accepted before it, so later writers cannot starve it.
  • Order across nodes follows the origin nodes' wall clocks. Appends from nodes with skewed clocks are still merged exactly once, but not in real time order.
  • kMax never lowers a size; only kSet and kDrop do.
  • The home's size is in memory; kGet is a map lookup.

Limits

  • Appends to a stream whose home is down are not merged until it returns, and fsync on that stream fails meanwhile.
  • Appends staged but not yet merged when the home's node is lost for good stay in the staging tag; only the home merges them.
  • Without log_path, sizes and open plans live only in memory.
  • The home is chosen by the caller and must not change for the stream's life.

How it is tested

  • context-transfer-engine/test/unit/test_stream_append.cc (cte_stream_append): sizes, concurrent writers merging exactly once in writer order, appends across page boundaries, append after truncate, and appends to a dropped stream, on one node.
  • context-transfer-engine/test/integration/clio_fs_suite through the FUSE mount: append_mode (tests_posix.py); xnode_append_many_writers, xnode_append_burst and append_then_truncate (tests_dist.py); append_home_restart, which kills the stream's home during appends and checks that every fsynced append survives exactly once in writer order, and truncate_during_failover (tests_fault.py).
