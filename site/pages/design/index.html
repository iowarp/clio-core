The stack

The picture has many names in it. The rest of this page introduces them one at a time, from the bottom up, so each piece is explained in terms of the pieces under it.

The pieces, one at a time

1. The runtime: one process per node

The Context Runtime is a single long-running process on each machine, started with clio_run start. By itself it stores nothing. It is a host for modules: it loads them, gives them worker threads, carries requests to them, and connects to the runtimes on the other machines of a cluster. Everything else on this page runs inside it.

Module (ChiMod)
A plug-in: a shared library that adds one capability to the runtime, such as "store bytes on an NVMe drive" or "keep cached copies". Every box in the stack diagram is one.
Pool
A running instance of a module, with a name and a numeric id such as 512.0. Two pools of the same module can run side by side with different settings, for example two caches.
Container
The part of a pool that lives on one node. A pool has one container on every node, so its work and data spread over the whole cluster instead of one server.
Task
One request to a pool: "write these bytes", "look up this name". Applications and modules talk to each other only by sending tasks. The runtime runs each task as a lightweight coroutine, so a task waiting on a disk or another node lets its thread run other tasks.

Because every feature is a module and every interaction is a task, the rest of the stack is a choice of which modules to start and in which order to connect them. That choice is the compose list in the configuration file.

2. Storage: block devices

At the bottom, a block-device module (bdev) turns one piece of hardware into a uniform pool of space: a region of RAM, a file on an NVMe drive or disk, an erasure-coded array, or an S3 or Google Cloud bucket. It hands out and frees blocks, and reads and writes them. It knows nothing about files or names. Each configured bdev is a storage tier, with a capacity and a score from 0 to 1 that ranks how fast it is.

3. The Context Transfer Engine: tags and blobs

The Context Transfer Engine (CTE) is the storage engine. It stores data as blobs grouped into tags, and decides which tier each blob lives on.

Blob
A named run of bytes, typically up to a few megabytes: one page of a file, one chunk of a dataset, one value in a key-value store. The blob is the unit the engine places, moves, copies and logs.
Tag
A named group of blobs, like a folder or a bucket. A file in Context FS is one tag whose blobs are its pages; a dataset or a model checkpoint can be one tag.
Blob score
A number from 0 to 1 saying how important a blob is. The placement engine puts a blob on the tier whose score best matches it, so hot data lands in RAM and cold data on disk. Changing a blob's score moves it.
Home
Each blob and tag is assigned to one node by hashing its name. That node keeps its metadata and orders its updates, so there is no central metadata server.

The CTE also keeps a metadata log on persistent storage, so blob locations survive a restart, and runs background work that reorganizes, flushes and evicts blobs between tiers. Data model and data path and Placement and tiering go into detail.

4. The chain: optional data operators

Between the applications and the CTE sits a chain of optional modules, each doing one job. Each speaks the same interface as the CTE itself, so it can stand in front of the CTE (or in front of another chain module), handle the requests it cares about, and forward everything else to the next pool. This is interposition; the link to the next pool is the module's next_pool_id.

  • Cache keeps a copy of hot blobs on the node that reads them, so repeat reads skip the network.
  • Indexer keeps term counts for what is written, so blobs can later be searched by their contents.
  • Compressor encodes blobs on the way down and decodes them on the way up.
  • Replication keeps extra copies on other nodes or a persistent tier, so data survives a node loss or a restart.

Because each operator only knows "the next pool", any of them can be left out and the chain closes around the gap. Your own modules plug in the same way. The interposition chain explains each operator and why they stack in the order they do.

5. Namespace and streams: files on top of blobs

Blobs and tags have no directories, permissions or file sizes. The filesystem module (clio-fs) adds them, storing directories, inodes (the record of a file's size, owner and permissions) and extended attributes as ordinary blobs. The stream module tracks file sizes and puts concurrent appends from many nodes into one order. Filesystem and FUSE describes both.

6. Interceptors: applications unchanged

Most applications already read and write files. Interceptors let them use CLIO Core without changes. The FUSE mount makes Context FS appear as a normal folder on Linux, macOS and Windows. POSIX, STDIO and MPI-IO interceptors are preloaded into a program and redirect its file calls. HDF5 and ADIOS2 plugins route those libraries' I/O. I/O adapters covers what each one gives up for speed.

7. Front ends: the products

The products are what people use, and each one is a combination of the pieces above.

  • Context FS: the filesystem module behind the FUSE mount, over the CTE.
  • Key-value API: tags and blobs directly from C++, Python or GPU code.
  • Memory expansion: vectors larger than GPU or CPU memory, paged in and out as CTE blobs.
  • Machine learning (clio-ml): training algorithms that run over those paged vectors, out of core.
  • CAE and CEE: the assimilation engine imports outside data (files, HDF5, S3) into tags; the exploration engine finds and retrieves it.

Every module has a cost

Each module buys a capability with time, memory or space. CLIO Core is built so that you pay only for what you compose, which leaves one rule in your hands: if you use a module, or plan to, enable it; if you do not, keep it off the path. A module that is not composed costs nothing. One that is composed is paid for on every request that passes through it, whether you use its feature or not.

The same holds below the chain: a RAM-only stack is the fastest and loses its data on restart, and a persistent tier with fsync is durable and slower. The choice is always explicit, in the compose file.

Design principles of the CTE

The storage engine follows a short list of rules. Most behavior on the other Design pages follows from one of them.

  1. No central metadata service. Every blob, tag, directory block and inode has exactly one home container chosen by hashing. There is no metadata server to scale or fail over. The cost is that whole-namespace questions (sizes, listings, searches) are broadcasts.
  2. One writer per object. Each object's home serializes its mutations. That makes versioning, coherence and crash ordering tractable. Parallelism comes from many objects, not from concurrent writers to one object.
  3. Everything is a blob. File data, directory blocks, inode records, extended attributes and staged appends are all ordinary CTE blobs. One tiering, replication and durability mechanism covers data and metadata alike.
  4. Mechanism in the core, policy in layers. The core provides replica slots, transform flags, invalidation, fault handlers and conditional puts. Replication, caching, compression, indexing and filesystem semantics are separate, optional ChiMods composed into a chain.
  5. Operators rank tiers; data carries a score. Placement matches a blob's score to configured tier scores, and measurements only break ties. Movement between tiers is explicit, by rescoring, flushing or eviction, and always copies before it frees.
  6. Durable on fsync, like ext4. Acknowledged writes run at memory speed. Power-loss and node-loss durability are paid for on request, through fsync and replication.
  7. Order operations so a crash leaks rather than corrupts. Logs trail data, new copies precede frees, records precede names, link counts rise before links appear. The failure mode is wasted space, never a reference to the wrong bytes.
  8. Fail closed. Lost volatile data reads as an I/O error, not zeros. Expired caches that cannot be revalidated fail, rather than serving stale data. Coherence stamps that cannot vouch for a file drop the cache.
  9. Keep hot paths off the network. Zero-IPC reads from shared memory, local path resolution from pushed caches, write sieves and write-behind, and node-local cache copies all exist to turn common operations into memory accesses.

One write, end to end

An application on node A appends 4 KiB to /mnt/clio/run/log.txt through the FUSE mount, then calls fsync.

  1. Kernel to daemon. FUSE delivers the write to the daemon on node A. On a single node, the kernel's cached size supplies the append offset. On a multi-node mount, the append is staged locally and merged by the file's stream home.
  2. Sieve. The bytes are copied into the client's write sieve: a 64 KiB shared-memory page for the file's 1 MiB page blob. The write returns immediately.
  3. Ship. Within about 500 µs the sieve page is sent as a put to the filesystem's chain. The cache layer routes it to node A. The file's page blob is owned by node B, the hash of (file tag, page number), so the authoritative put travels to B. B invalidates other nodes' cache copies and registers A's copy.
  4. Owner. On B, replication writes the primary (and any remote copies) and passes the put to the core. The core takes the blob's write token, drains readers, places the bytes (the RAM tier, since the blob's score defaults to 1.0), writes them, logs the new layout, and acknowledges.
  5. fsync. The daemon drains the sieve, publishes the file's size to its stream home, and waits for replication. It then syncs the file's tag: B moves the page blob to a persistent tier (place, swap, log, free) and fsyncs that device and its metadata log. The daemon then fsyncs the stream's size log and syncs the parent directory's tag, so the name is durable too. Only then does fsync return.

Any later reader on node A finds the bytes in its node-local cache copy and reads them through shared memory without a request. A reader on node C fetches them from B and gets a cache copy of its own, registered against B's current version.
