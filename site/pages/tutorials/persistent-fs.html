What makes it persistent

A file in Context FS is three kinds of state: its bytes (1 MiB page blobs), its logical size, and its name in a directory. Each must reach durable storage, and each must be found again after a restart:

StateWhere it livesSetting
File bytesThe persistent core's (512.0) file tier, on a durable diskpersistence_level: long_term on the tier. The write-back cache (567.0) flushes to it through replication (561.0)
Which blob owns which bytesThe persistent core's metadata logperformance.metadata_log_path on the 512.0 entry
File sizesThe stream pool's size loglog_path on clio_cte_stream
Names and directoriesThe filesystem's namespace logmetadata_log_path on clio_cte_filesystem

The default file sets the two metadata logs, but its only disk tier is temporary and its stream pool has no log_path, so file sizes are lost on a restart. Put every path on a durable disk, not under /tmp or another scratch directory.

Writes are acknowledged once they are in the volatile core's RAM (540.0). They become durable when the write-back cache flushes them to the persistent core: every 10 s, on fsync, and during a graceful clio-run stop.

1. Write the configuration

Save this as ~/clio-persistent.yaml. It is the default chain without the CAE, with the changes marked. Every path is under ${CLIO_STORAGE_ROOT}, which clio-run start --disk sets in step 2:

compose:
  - mod_name: clio_bdev
    pool_name: "ram::chi_default_bdev"
    pool_query: local
    pool_id: "301.0"
    bdev_type: ram
    capacity: "0g"

  # Persistent core: the durable copy of every file lives here.
  - mod_name: clio_cte_core
    pool_name: cte_main
    pool_query: local
    pool_id: "512.0"
    durability: persistent
    storage:
      - path: "${CLIO_STORAGE_ROOT}/cte_disk_tier.dat"
        bdev_type: file
        capacity_limit: 200GB          # the most data the filesystem can hold
        score: 0.2
        persistence_level: long_term   # (1) a durable tier
    performance:
      metadata_log_path: "${CLIO_STORAGE_ROOT}/cte_metadata_log"   # (2)

  # Volatile core: where the write-back cache lands writes first.
  - mod_name: clio_cte_core
    pool_name: cte_volatile
    pool_query: local
    pool_id: "540.0"
    durability: volatile
    storage:
      - path: "ram::cte_ram_tier1"
        bdev_type: ram
        capacity_limit: 8GB            # size it to your memory
        score: 1.0

  - mod_name: clio_cte_replication
    pool_name: clio_cte_replication
    pool_query: local
    pool_id: "561.0"
    next_pool_id: "512.0"
    replication_factor: 1
    replica_score: 0.2

  - mod_name: clio_cte_core_persist_write_back
    pool_name: clio_cte_core_persist_write_back
    pool_query: local
    pool_id: "567.0"
    next_volatile: "540.0"
    next_persistent: "561.0"           # (3) flushes reach the persistent core
    flush_period_ms: 10000
    flush_pool: "568.0"
    fallback_to_persistent: true

  - mod_name: clio_cte_core_shm_cache_writethru
    pool_name: clio_cte_core_shm_cache_writethru
    pool_query: local
    pool_id: "568.0"
    next_pool_id: "567.0"
    md_only: true
    invalidate_on_flush: true
    capacity: "256M"

  - mod_name: clio_cte_stream
    pool_name: clio_cte_stream
    pool_query: local
    pool_id: "565.0"
    next_pool_id: "568.0"
    staging_pool_id: "561.0"
    log_path: "${CLIO_STORAGE_ROOT}/cte_stream_log"   # (4) file sizes survive a restart

  - mod_name: clio_cte_filesystem
    pool_name: clio_cte_filesystem
    pool_query: local
    pool_id: "560.0"
    next_pool_id: "568.0"
    stream_pool_id: "565.0"
    metadata_log_path: "${CLIO_STORAGE_ROOT}/cfs_namespace_log"   # (5)
  1. A long_term tier in the persistent core. The default tier is temporary; long_term states that this one is meant to keep data. Put it on a durable disk (step 2).
  2. The persistent core's metadata log. Without it the tier's bytes are kept but nothing remembers which blob they belong to.
  3. A write-back cache that flushes to the persistent core. next_persistent points through replication (561.0) to the persistent core (512.0). Data that has only reached the volatile core is not durable.
  4. A stream size log. Without log_path, file sizes are lost on a restart.
  5. The filesystem's namespace log. It journals the directory tables; without it, names are not recovered from disk.

Each compose entry must come after every pool it names, and each needs its own pool_id: a compose that reuses one is refused at startup.

2. Start the runtime on a durable disk

--disk sets the storage root, ${CLIO_STORAGE_ROOT}, so the tier, every log in the file above and the rest of the runtime's on-disk state go to that directory. Choose a directory on a durable disk.

Linux, macOS

$ mkdir -p /data/clio
$ export CLIO_SERVER_CONF=~/clio-persistent.yaml
$ export CLIO_BIND_ADDR=127.0.0.1
$ clio-run start --disk /data/clio

Windows

PS> mkdir D:\clio
PS> $env:CLIO_SERVER_CONF = "$HOME\clio-persistent.yaml"
PS> $env:CLIO_BIND_ADDR = "127.0.0.1"
PS> clio-run start --disk D:\clio

Never pass --fresh to this runtime: it discards the node's persistent state.

3. Mount and write

Mount exactly as in the quickstart, with CLIO_WITH_RUNTIME=0, and write a file. sync (or fsync from a program) makes the write-back cache flush the file to the persistent core; it is the point after which a file survives a crash:

Linux, macOS

$ cp -r ~/project ~/clio-mnt/
$ sync

Windows

PS> Copy-Item -Recurse $HOME\project Z:\

Windows has no sync command; a program calls FlushFileBuffers (Python: os.fsync).

4. Restart and check

Unmount, stop the runtime, start it again on the same configuration and storage root without --fresh, and mount. Your files are back:

$ fusermount3 -u ~/clio-mnt          # Windows: Stop-Process -Name clio_cte_fuse -Force
$ clio-run stop
$ clio-run start --disk /data/clio
$ CLIO_WITH_RUNTIME=0 clio_cte_fuse ~/clio-mnt -f
$ ls ~/clio-mnt/project

What survives what

EventFiles written, not fsyncedFiles fsyncedChecked by cfs_persistence
clio-run stop, then startKept: a graceful stop flushes the write-back cache firstKeptYes
Runtime killed or crashedNot guaranteed: only what the write-back cache had flushed (it flushes every 10 s)KeptYes

The cfs_persistence unit test checks both rows: it runs this chain from one configuration file, writes files (several pages, a truncated file, a rename, and a file never fsynced), stops the runtime gracefully or kills it, restarts it without --fresh, and compares every file byte for byte. It sets the periodic flush to 10 minutes, so within the test only fsync and the graceful stop make data durable. Durability and recovery explains the ordering behind the table.
