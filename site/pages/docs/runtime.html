Module layout

A ChiMod is a directory with a YAML descriptor, a public header set and two shared libraries: a client library that user programs link, and a runtime library that the daemon loads. The template in context-runtime/modules/MOD_NAME has this shape (replace MOD_NAME with your module name and clio_runtime with your include namespace):

MOD_NAME/
  CMakeLists.txt
  clio_mod.yaml                           module name, namespace, method ids
  include/clio_runtime/MOD_NAME/
    autogen/MOD_NAME_methods.h            method id constants and names
    MOD_NAME_tasks.h                      CreateParams and one struct per task
    MOD_NAME_client.h                     client: Async* methods returning futures
    MOD_NAME_runtime.h                    the container class
  src/
    MOD_NAME_client.cc                    usually just includes the client header
    MOD_NAME_runtime.cc                   handler bodies, ends with CLIO_TASK_CC
    autogen/MOD_NAME_lib_exec.cc          dispatch: Run, Save/LoadTask, NewTask, ...

The operator guide names the dispatch file bytecount_exec.cc instead of autogen/..._lib_exec.cc. The name does not matter; what matters is that the runtime library compiles both the handler file and the dispatch file.

An external repository that holds several modules adds a clio_repo.yaml at its root. The CMake helpers search up the directory tree for it to learn the namespace:

name: external-chimod
namespace: external_test
version: 1.0.0
description: External ChiMod development test repository

modules:
  - simple_mod

clio_mod.yaml and the methods header

clio_mod.yaml names the module and assigns an integer id to every method. Ids 0 to 9 are reserved for the inherited methods; your own start at 10. A method set to -1 is not implemented.

module_name: MOD_NAME
namespace: clio::run
version: 1.0.0

# Inherited methods
kCreate: 0        # create the container
kDestroy: 1       # destroy the container
kNodeFailure: -1  # not implemented
kRecover: -1
kMigrate: -1
kUpgrade: -1
kMonitor: 9       # monitor container state

# Custom methods (start from 10)
kCustom: 10

The methods header repeats the ids as constants, defines kMaxMethodId (one past the largest id) and returns the method names the dashboard and the scheduler's per-method cost model use:

namespace clio::run::MOD_NAME::Method {
GLOBAL_CROSS_CONST clio::run::u32 kCreate = 0;
GLOBAL_CROSS_CONST clio::run::u32 kDestroy = 1;
GLOBAL_CROSS_CONST clio::run::u32 kMonitor = 9;
GLOBAL_CROSS_CONST clio::run::u32 kCustom = 10;
GLOBAL_CROSS_CONST clio::run::u32 kMaxMethodId = 11;

inline const std::vector<std::string>& GetMethodNames() {
  static const std::vector<std::string> names = [] {
    std::vector<std::string> v(kMaxMethodId);
    v[kCreate] = "Create";
    v[kDestroy] = "Destroy";
    v[kMonitor] = "Monitor";
    v[kCustom] = "Custom";
    return v;
  }();
  return names;
}
}  // namespace clio::run::MOD_NAME::Method

Tasks

Every operation is a task: a struct derived from clio::run::Task that names a pool, a method and a PoolQuery, and carries input and output fields. The tasks header defines three things.

CreateParams and the standard tasks

CreateParams is the configuration the container receives at creation. It must carry a static chimod_lib_name naming the library the runtime loads, a cereal serialize, and only fields that cereal can serialize. The create, destroy and monitor tasks come from the admin module:

#include <clio_runtime/clio_runtime.h>
#include <clio_runtime/admin/admin_tasks.h>
#include "autogen/MOD_NAME_methods.h"

namespace clio::run::MOD_NAME {

struct CreateParams {
  clio::run::u32 worker_count_;
  clio::run::u32 config_flags_;

  // Required: the library the module manager loads (lib<name>_runtime.so).
  static constexpr const char* chimod_lib_name = "clio_MOD_NAME";

  CreateParams(clio::run::u32 worker_count = 1, clio::run::u32 config_flags = 0)
      : worker_count_(worker_count), config_flags_(config_flags) {}

  template<class Archive>
  void serialize(Archive& ar) { ar(worker_count_, config_flags_); }
};

using CreateTask  = clio::run::admin::GetOrCreatePoolTask<CreateParams>;
using DestroyTask = clio::run::admin::DestroyTask;
using MonitorTask = clio::run::admin::MonitorTask;

A module that is created from the compose file reads its YAML entry in a LoadConfig(const clio::run::PoolConfig &) method on its params struct; the operator guide shows one that parses next_pool_id.

A custom task

A task struct marks each field IN, OUT or INOUT. It needs a default constructor, an emplace constructor that sets the method id, SerializeIn (fields sent to the runtime), SerializeOut (fields sent back), Copy (used when the runtime replicates a task) and AggregateOut (merges a replica's output fields back into the original). Strings that cross the boundary use clio::run::priv::string allocated with CLIO_PRIV_ALLOC.

struct CustomTask : public clio::run::Task {
  INOUT clio::run::priv::string data_;
  IN clio::run::u32 operation_id_;

  CustomTask() : clio::run::Task(), data_(CLIO_PRIV_ALLOC), operation_id_(0) {}

  explicit CustomTask(const clio::run::TaskId &task_node,
                      const clio::run::PoolId &pool_id,
                      const clio::run::PoolQuery &pool_query,
                      const std::string &data, clio::run::u32 operation_id)
      : clio::run::Task(task_node, pool_id, pool_query, Method::kCustom),
        data_(CLIO_PRIV_ALLOC, data), operation_id_(operation_id) {
    task_id_ = task_node;
    pool_id_ = pool_id;
    method_ = Method::kCustom;
    task_flags_.Clear();
    pool_query_ = pool_query;
  }

  CTP_CROSS_FUN ~CustomTask() {}

  template<typename Archive>
  CTP_CROSS_FUN void SerializeIn(Archive& ar) {
    Task::SerializeIn(ar);
    ar(data_, operation_id_);
  }
  template<typename Archive>
  CTP_CROSS_FUN void SerializeOut(Archive& ar) {
    Task::SerializeOut(ar);
    ar(data_);
  }
  void Copy(const ctp::ipc::FullPtr<CustomTask> &other) {
    Task::Copy(other.template Cast<Task>());
    data_ = other->data_;
    operation_id_ = other->operation_id_;
  }
  // Merge ONLY the OUT fields of a replica. Never delegate to Copy():
  // that would overwrite this task's identity.
  void AggregateOut(const ctp::ipc::FullPtr<clio::run::Task> &other_base) {
    Task::AggregateOut(other_base);
    data_ = other_base.template Cast<CustomTask>()->data_;
  }
};

}  // namespace clio::run::MOD_NAME

Tasks that take part in the collective routing modes (see below) also define AggregateIn, which folds another submitter's input into this task before the handler runs once for the whole batch. The template's ManyToOneSumTask sums value_ that way.

Tasks are copied, not shared

A task lives in the submitting process. Its input fields are serialized into a buffer that crosses into the runtime, and only the output fields come back. Do not design a task around the idea that both sides see the same memory.

The runtime class and coroutine handlers

The runtime class derives from clio::run::Container, exposes using CreateParams = ...; for the CLIO_TASK_CC macro, and declares one handler per method. A handler takes a clio::run::shared_ptr<TaskType> & and returns clio::run::TaskResume.

#include <clio_runtime/clio_runtime.h>
#include <clio_runtime/container.h>
#include <clio_runtime/comutex.h>
#include <clio_runtime/corwlock.h>
#include "MOD_NAME_tasks.h"
#include "MOD_NAME_client.h"

namespace clio::run::MOD_NAME {

class Runtime : public clio::run::Container {
 public:
  using CreateParams = clio::run::MOD_NAME::CreateParams;

  void Init(const clio::run::PoolId& pool_id, const std::string& pool_name,
            clio::run::u32 container_id = 0) override;
  clio::run::TaskResume Run(clio::run::u32 method,
                            clio::run::shared_ptr<clio::run::Task> task_ptr) override;

  clio::run::TaskResume Create(clio::run::shared_ptr<CreateTask> &task);
  clio::run::TaskResume Custom(clio::run::shared_ptr<CustomTask> &task);
  clio::run::TaskResume Monitor(clio::run::shared_ptr<MonitorTask> &task);
  clio::run::TaskResume Destroy(clio::run::shared_ptr<DestroyTask> &task);

  clio::run::u64 GetWorkRemaining() const override;
  // Serialization and copy plumbing (SaveTask, LoadTask, AllocLoadTask,
  // LocalSaveTask, LocalLoadTask, LocalAllocLoadTask, NewCopyTask, NewTask,
  // AggregateOut, AggregateIn): see the dispatch file.

 private:
  Client client_;   // the module's own client, for subtasks
};

}  // namespace clio::run::MOD_NAME

Handler bodies sit between CLIO_TASK_BODY_BEGIN and CLIO_TASK_BODY_END, wait on a future with CLIO_CO_AWAIT, and finish with CLIO_CO_RETURN. The file ends with CLIO_TASK_CC(Namespace::Runtime), which defines the entry points the module manager looks up.

#include "clio_runtime/MOD_NAME/MOD_NAME_runtime.h"

namespace clio::run::MOD_NAME {

clio::run::TaskResume Runtime::Create(clio::run::shared_ptr<CreateTask> &task) {
  CLIO_TASK_BODY_BEGIN
  // Init() already ran. Read task->GetParams() here if you need the config.
  CLIO_CO_RETURN;
  CLIO_TASK_BODY_END
}

clio::run::TaskResume Runtime::Custom(clio::run::shared_ptr<CustomTask> &task) {
  CLIO_TASK_BODY_BEGIN
  // A subtask through the module's own client. The worker runs other tasks
  // while this one waits; the result is read from the future afterwards.
  auto sub = client_.AsyncCustom(task->pool_query_, "child", 0);
  CLIO_CO_AWAIT(sub);
  task->data_ = sub->data_;
  task->return_code_ = 0;
  CLIO_CO_RETURN;
  CLIO_TASK_BODY_END
}

clio::run::TaskResume Runtime::Destroy(clio::run::shared_ptr<DestroyTask> &task) {
  CLIO_TASK_BODY_BEGIN
  task->return_code_ = 0;
  CLIO_CO_RETURN;
  CLIO_TASK_BODY_END
}

clio::run::u64 Runtime::GetWorkRemaining() const { return 0; }

}  // namespace clio::run::MOD_NAME

CLIO_TASK_CC(clio::run::MOD_NAME::Runtime)
  • Never hold a lock across CLIO_CO_AWAIT. The worker thread runs other tasks while the handler is suspended. For locks that may be held across a wait, use the coroutine-aware clio::run::CoMutex and CoRwLock with the ScopedCoMutex, ScopedCoRwReadLock and ScopedCoRwWriteLock guards.
  • Several workers run handlers concurrently. Container state touched by more than one task needs an atomic or a lock.
  • Monitor answers with msgpack. Pack the reply into task->results_[container_id_] and the dashboard turns it into JSON (see the operator guide).

The dispatch file

The dispatch file implements the virtual methods of Container by switching on the method id. Init calls the base Init, builds the module's own client, and registers the cost model and method names. Run casts the task to its concrete type and awaits the handler:

void Runtime::Init(const clio::run::PoolId &pool_id, const std::string &pool_name,
                   clio::run::u32 container_id) {
  clio::run::Container::Init(pool_id, pool_name, container_id);
  client_ = Client(pool_id);
  DefineModel(Method::kMaxMethodId);
  SetMethodNames(Method::GetMethodNames());
}

clio::run::TaskResume Runtime::Run(clio::run::u32 method,
                                   clio::run::shared_ptr<clio::run::Task> task_ptr) {
  CLIO_TASK_BODY_BEGIN
  switch (method) {
    case Method::kCreate: {
      auto& typed = task_ptr.template Cast<CreateTask>();
      CLIO_CO_AWAIT(Create(typed));
      break;
    }
    case Method::kCustom: {
      auto& typed = task_ptr.template Cast<CustomTask>();
      CLIO_CO_AWAIT(Custom(typed));
      break;
    }
    // ... kDestroy, kMonitor ...
    default: break;
  }
  CLIO_CO_RETURN;
  CLIO_TASK_BODY_END
}

The same switch appears in SaveTask and LoadTask (archive << *typed and archive >> *typed), LocalSaveTask and LocalLoadTask, NewTask (CLIO_IPC->NewTask<T>()), NewCopyTask (allocate, then Copy), AggregateOut and AggregateIn. Copy the template's file and change the case list; the operator guide shows the whole file as an X-macro.

The client

A client derives from clio::run::ContainerClient and is bound to a pool id. Each method allocates a task through the IPC manager, sends it, and returns a clio::run::Future<TaskType>. Wait() blocks until the task completes; the fields are then read through ->. Create goes to the admin pool as a GetOrCreatePoolTask, which loads the module if needed and creates the pool if it does not exist.

namespace clio::run::MOD_NAME {

class Client : public clio::run::ContainerClient {
 public:
  Client() = default;
  explicit Client(const clio::run::PoolId& pool_id) { Init(pool_id); }

  clio::run::Future<CreateTask> AsyncCreate(const clio::run::PoolQuery& pool_query,
                                            const std::string& pool_name,
                                            const clio::run::PoolId& custom_pool_id) {
    auto* ipc_manager = CLIO_CPU_IPC;
    auto task = ipc_manager->NewTask<CreateTask>(
        clio::run::CreateTaskId(), clio::run::kAdminPoolId, pool_query,
        CreateParams::chimod_lib_name, pool_name, custom_pool_id, this);
    return ipc_manager->Send(task);
  }

  clio::run::Future<CustomTask> AsyncCustom(const clio::run::PoolQuery& pool_query,
                                            const std::string& input_data,
                                            clio::run::u32 operation_id) {
    auto* ipc_manager = CLIO_CPU_IPC;
    auto task = ipc_manager->NewTask<CustomTask>(
        clio::run::CreateTaskId(), pool_id_, pool_query, input_data, operation_id);
    return ipc_manager->Send(task);
  }

  clio::run::Future<MonitorTask> AsyncMonitor(const clio::run::PoolQuery& pool_query,
                                              const std::string& query) {
    auto* ipc_manager = CLIO_CPU_IPC;
    auto task = ipc_manager->NewTask<MonitorTask>(
        clio::run::CreateTaskId(), pool_id_, pool_query, query);
    return ipc_manager->Send(task);
  }
};

}  // namespace clio::run::MOD_NAME

Initialising a client program

A program calls clio::run::CLIO_INIT(mode, default_with_runtime, is_restart) once per process before touching any client, and clio::run::CLIO_RUNTIME_FINALIZE() before it exits.

  • mode is RuntimeMode::kClient for a program, or RuntimeMode::kServer for a process that is the runtime.
  • default_with_runtime is used when CLIO_WITH_RUNTIME is not set. In client mode, "with runtime" means try to start a runtime in this process, and attach to the existing one if the port is already bound. That lets several processes launched together elect one host.
  • CLIO_WITH_RUNTIME=0 attaches to a running runtime only; CLIO_WITH_RUNTIME=1 makes sure one is available.
  • CLIO_SERVER_CONF names the YAML configuration an in-process runtime reads.
#include <clio_runtime/clio_runtime.h>
#include <clio_runtime/admin/admin_client.h>
#include <clio_runtime/MOD_NAME/MOD_NAME_client.h>

int main() {
  // Attach to a running runtime (CLIO_WITH_RUNTIME=0), else start one here.
  if (!clio::run::CLIO_INIT(clio::run::RuntimeMode::kClient, true)) return 1;

  constexpr clio::run::PoolId kMyPool = clio::run::PoolId(7001, 0);
  clio::run::MOD_NAME::Client client(kMyPool);

  auto pq = clio::run::PoolQuery::Local();
  auto created = client.AsyncCreate(pq, "my_pool", kMyPool);
  created.Wait();

  auto fut = client.AsyncCustom(pq, "hello", 1);
  fut.Wait();
  // fut->data_ and fut->return_code_ are now valid.

  clio::run::CLIO_RUNTIME_FINALIZE();
  return 0;
}

Creating pools from the compose file

The runtime's configuration file (the one CLIO_SERVER_CONF points at, or a separate file given to clio_run compose start) has a compose: list. Each entry creates one pool at startup. Four keys are read by the runtime itself; everything else in the entry is handed to the module as a YAML string, which its params struct parses in LoadConfig.

compose:
  - mod_name: clio_MOD_NAME      # chimod_lib_name of the module
    pool_name: my_pool
    pool_query: local            # routing used for the create task
    pool_id: "7001.0"            # "major.minor"
    restart: true                # recreate on the next clio_run start
    # module-specific keys follow; see the operator guide for next_pool_id

pool_query accepts the strings local, broadcast, dynamic, direct_id:N, direct_hash:N, range:OFFSET:COUNT, physical:NODE and many_to_one:HASH[:KEY[:NS]]. The CLI reference covers clio_run compose start, list and stop.

PoolQuery routing modes

Every task carries a clio::run::PoolQuery that says which container of the pool runs it. The factories are in clio_runtime/pool_query.h:

  • PoolQuery::Local(parallelism = 32): the container on this node. The default, and the usual choice for a create.
  • PoolQuery::Dynamic(): the runtime picks, through the monitor's global scheduler. Recommended for data operations in a multi-node pool; the CTE client uses it by default.
  • PoolQuery::Broadcast(): every container runs the task. Each copy's output is merged into the original with AggregateOut.
  • PoolQuery::DirectId(container_id) and PoolQuery::DirectHash(hash): one container, chosen by id or by hashing a key you supply.
  • PoolQuery::Range(offset, count): a contiguous range of containers.
  • PoolQuery::Physical(node_id): the container on a specific node.
  • PoolQuery::ManyToOne(container_hash, batch_key = 0, batch_for_ns = 10000): tasks with the same pool, method, hash and key that arrive within the window are folded into one task with AggregateIn, run once, and the result is sent back to every submitter.
  • PoolQuery::AllToOne(container_hash, batch_key = 0): like ManyToOne, but the folded task runs only once a task from every container in the pool has arrived. This is a collective barrier or reduction.
  • PoolQuery::Null(): do nothing.

Every query also takes SetNetTimeout(seconds) (per-task network timeout, -1 for the default), SetTtl(seconds) (a hard cap on how long the origin waits for a cross-node task, negative for none) and SetParallelism(n) (threads used when a GPU submits the task).

How the runtime finds modules

When a create task names a chimod_lib_name, the module manager scans directories for a shared library whose name ends in _runtime.so (.dylib on macOS, .dll on Windows). The scan order is:

  1. the directory that holds the runtime's own library;
  2. each entry of CLIO_REPO_PATH, separated by : (; on Windows);
  3. each entry of LD_LIBRARY_PATH;
  4. ./lib, ../lib and /usr/local/lib.

So the usual way to run a module from its build directory is to point CLIO_REPO_PATH at it before starting the daemon. The runtime log reports Loaded ChiMod: <name> for each library it loads.

$ export CLIO_REPO_PATH=$HOME/MOD_NAME/build
$ export CLIO_SERVER_CONF=$HOME/clio.yaml
$ clio_run start &

Building against an installed prefix

Install CLIO Core, then build the module with CMAKE_PREFIX_PATH pointing at the prefix. The add_clio_module_client and add_clio_module_runtime functions come with the installed CMake package. They read the module name from clio_mod.yaml and the namespace from clio_repo.yaml, and create the targets <namespace>_<module>_client and <namespace>_<module>_runtime. Pass LIB_NAME to override that prefix; it must then match chimod_lib_name. Both functions also accept INCLUDE_DIRECTORIES, LINK_LIBRARIES and COMPILE_DEFINITIONS.

$ cmake --install build --prefix $HOME/clio-inst
$ export PATH=$HOME/clio-inst/bin:$PATH

cmake_minimum_required(VERSION 3.20)
project(MOD_NAME CXX)
set(CMAKE_CXX_STANDARD 20)

find_package(yaml-cpp REQUIRED)        # clio-core uses it but does not find it itself
find_package(clio-core CONFIG REQUIRED)

add_clio_module_client(
  LIB_NAME clio_MOD_NAME
  SOURCES src/MOD_NAME_client.cc)
add_clio_module_runtime(
  LIB_NAME clio_MOD_NAME
  SOURCES src/MOD_NAME_runtime.cc src/autogen/MOD_NAME_lib_exec.cc)

add_executable(my_program main.cc)
target_link_libraries(my_program clio_MOD_NAME_client clio::run::admin_client)

$ cmake -S . -B build -DCMAKE_PREFIX_PATH=$HOME/clio-inst
$ cmake --build build

The external module test in context-runtime/test/unit/external-chimod uses find_package(clio_run REQUIRED) and find_package(clio_run_admin REQUIRED) instead of the umbrella package, with the namespace coming from its clio_repo.yaml; its targets are then external_test::simple_mod_client and clio::run::admin_client. Either form works against an installed tree.
