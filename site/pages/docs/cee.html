What it is

CEE is one class, iowarp::ContextInterface, with five methods. Bundle imports sources into tags. Query returns the names of matching blobs. Retrieve returns their bytes packed into one buffer. Destroy deletes tags. Splice is declared but not implemented. The class does no storage of its own: every call becomes a task on the Context Assimilation Engine (CAE) or the Context Transfer Engine (CTE).

The source is context-exploration-engine/api. The C++ library target is clio_cee_api (CMake package clio_cee_api, link target clio_cee::api). The Python module clio_cee is built with nanobind from api/src/python_bindings.cc and is skipped with a warning when nanobind is not found.

Connecting to the runtime

Constructing a ContextInterface does nothing. The first method call initializes the CLIO Runtime client, then the CAE client, which initializes the CTE client. If the runtime is not running the call logs an error and returns a failure value (1 for bundle and destroy, an empty list for query and retrieve). A failed initialization is remembered for the life of the process, so start the runtime before the first call.

Two environment variables matter and must be set before the first call (in Python, before the import is safest):

  • CLIO_WITH_RUNTIME=0 attaches to the runtime started by clio_run start instead of starting a private one.
  • CLIO_CTE_POOL selects the CTE pool the shared client talks to. Keyword search is answered by the indexer, so set it to 564.0 (the indexer) or 563.0 (the chain top, which forwards to the indexer). Without it the client binds to the bare core at 512.0 and semantic queries return nothing.
import os
os.environ["CLIO_WITH_RUNTIME"] = "0"
os.environ["CLIO_CTE_POOL"] = "564.0"

import clio_cee as cee
ctx = cee.ContextInterface()

Python API

Python names are snake_case versions of the C++ methods. Defaults below are the ones declared in the bindings.

context_bundle(bundle)

Takes a list of AssimilationCtx and submits one CAE ParseOmni task for the whole list on the CAE pool 400.0, then waits. Returns 0 on success or the task's result code. An empty list logs a warning and returns 0.

AssimilationCtx

Two constructors are bound:

cee.AssimilationCtx(src, dst, format, depends_on="", range_off=0, range_size=0,
                    src_token="", dst_token="")
cee.AssimilationCtx(src, dst, format, src_data, depends_on="", range_off=0,
                    range_size=0, src_token="", dst_token="")
  • src: source URL, for example file::/path/to/file or string::<blob_name>.
  • dst: destination URL, iowarp::<tag_name>.
  • format: data format such as binary or hdf5.
  • src_data: inline payload for a string:: source. It is stored verbatim as one blob named by the part after string::.
  • depends_on, range_off, range_size, src_token, dst_token: dependency id, byte range of the source, and credentials.

All of these are also readable and writable attributes. The C++ struct has further fields (include and exclude patterns, on-fault ingestion, chunk size, blob prefix) that the Python binding does not expose. The CAE core page lists the supported source schemes and formats.

context_query(tag_re, blob_re, max_results=0, prompt="", time_begin=0, time_end=0)

Returns a list of blob names. Both patterns are full-string regular expressions (std::regex_match), so use .*part.* to match a substring. The arguments select one of three modes, checked in this order:

  1. Temporal. If time_begin or time_end is non-zero, the call is a CTE TemporalSearch. Blobs whose last-modified time lies in the inclusive range are returned sorted ascending by time. 0 for either bound means no bound. max_results caps the list; 0 means unlimited.
  2. Semantic. Otherwise, if prompt is non-empty, the call is a CTE SemanticSearch: BM25 keyword scoring of the prompt against the contents of every blob that matches both patterns, best first. max_results is the top-k; 0 falls back to 10.
  3. Regex. Otherwise the call is a CTE BlobQuery and returns every blob whose tag and blob names match. max_results of 0 means unlimited.
Temporal bounds are not wall-clock time yet

The docstrings say epoch nanoseconds, but the Python API page documents that last_modified currently comes from a steady clock. Use temporal mode to order blobs within one run of the runtime, not to filter by calendar time.

context_retrieve(tag_re, blob_re, max_results=1024, max_context_size=268435456, batch_size=32, prompt="", time_begin=0, time_end=0)

Resolves blobs with the same three modes, then reads their bytes. The result is a list with one str holding every retrieved blob, or an empty list when nothing matched or nothing could be read. Details from the implementation in api/src/context_interface.cc:

  • The buffer is the blobs' bytes concatenated back to back, in the order the query returned them. There are no headers, lengths or separators. If you need to split the buffer, query the names first and read sizes with the CTE client, or give each blob a fixed size.
  • max_results defaults to 1024 here, not 0. The same 0 rules apply as for query.
  • max_context_size (default 256 MiB) is allocated up front as one shared-memory buffer. Retrieval stops at the first blob that would not fit; blobs already copied are returned.
  • Blobs are fetched batch_size at a time with AsyncGetBlob. Within a batch the tag lookup and size lookup are still sequential.
  • A blob of size 0 is skipped. A GetBlob that fails logs a warning but its reserved bytes stay in the buffer.
  • Each blob's tag is resolved with GetOrCreateTag, so a tag name that no longer exists is created empty as a side effect.

context_splice(new_ctx, tag_re, blob_re)

Not implemented. It logs a warning and returns 1 without touching the runtime.

context_destroy(context_names)

Calls CTE DelTag for each name and waits. Returns 0 when every delete succeeded, 1 if any failed. An empty list returns 0. Deleting a tag deletes its blobs and, when the indexer is in the chain, its index entries.

Example

import os
os.environ["CLIO_WITH_RUNTIME"] = "0"
os.environ["CLIO_CTE_POOL"] = "564.0"
import clio_cee as cee

ctx = cee.ContextInterface()
rc = ctx.context_bundle([
    cee.AssimilationCtx(src="string::ice", dst="iowarp::climate_docs", format="string",
                        src_data="Arctic sea ice extent fell to a record low."),
    cee.AssimilationCtx(src="string::co2", dst="iowarp::climate_docs", format="string",
                        src_data="Atmospheric CO2 passed 420 ppm."),
])
assert rc == 0

ctx.context_query("climate_docs", ".*")                               # ['ice', 'co2'] in some order
ctx.context_query("climate_docs", ".*", max_results=1, prompt="sea ice")   # ['ice']
packed = ctx.context_retrieve("climate_docs", "ice")                  # one str with the bytes
ctx.context_destroy(["climate_docs"])

C++ API

The header is clio_cee/api/context_interface.h. Signatures and defaults match the Python ones above.

#include <clio_cee/api/context_interface.h>

namespace iowarp {
class ContextInterface {
 public:
  int ContextBundle(const std::vector<clio::cae::core::AssimilationCtx> &bundle);
  std::vector<std::string> ContextQuery(const std::string &tag_re, const std::string &blob_re,
                                        unsigned int max_results = 0, const std::string &prompt = "",
                                        uint64_t time_begin = 0, uint64_t time_end = 0);
  std::vector<std::string> ContextRetrieve(const std::string &tag_re, const std::string &blob_re,
                                           unsigned int max_results = 1024,
                                           size_t max_context_size = 256 * 1024 * 1024,
                                           unsigned int batch_size = 32, const std::string &prompt = "",
                                           uint64_t time_begin = 0, uint64_t time_end = 0);
  int ContextSplice(const std::string &new_ctx, const std::string &tag_re, const std::string &blob_re);
  int ContextDestroy(const std::vector<std::string> &context_names);
};
}

iowarp::ContextInterface ctx;

clio::cae::core::AssimilationCtx item;
item.src = "file::/data/run42/output.bin";
item.dst = "iowarp::run42";
item.format = "binary";
if (ctx.ContextBundle({item}) != 0) { /* runtime not reachable or import failed */ }

auto names  = ctx.ContextQuery("run42", ".*");                       // regex listing
auto ranked = ctx.ContextQuery("run42", ".*", 5, "temperature gradient"); // BM25, top 5
auto packed = ctx.ContextRetrieve("run42", ".*", 1024, 64 * 1024 * 1024);
ctx.ContextDestroy({"run42"});

Link with find_package(clio_cee_api REQUIRED) and target_link_libraries(app PRIVATE clio_cee::api). The library depends on the runtime client, clio_cte_core_client and clio_cae_core_client.

The README in context-exploration-engine/api still lists ContextRetrieve as a placeholder and shows it without the prompt and time arguments. The header and implementation in the same directory implement it as described here; this page follows the code.

How CEE uses the Context Transfer Engine

Every method except bundle is a thin wrapper over the CTE core client singleton. Knowing the mapping explains the behavior:

  • ContextQuery calls AsyncTemporalSearch, AsyncSemanticSearch or AsyncBlobQuery with PoolQuery::Broadcast(), so every node answers for the blobs it owns and the runtime merges the results.
  • ContextRetrieve runs the same query, then per blob AsyncGetOrCreateTag, AsyncGetBlobSize and AsyncGetBlob into one shared-memory buffer.
  • ContextDestroy calls AsyncDelTag by name.
  • ContextBundle is the exception: it calls the CAE client's AsyncParseOmni on pool 400.0. The CAE core writes the imported blobs through its own next_pool_id.

BlobQuery and TemporalSearch are answered by the core's metadata. SemanticSearch is not: the core no longer implements it, and the indexer module at pool 564.0 terminates it from its keyword index. That is why the client must be bound to the indexer or to a pool that forwards to it. The CTE page describes the data model and the full client.

How CEE sees Context FS

Context FS stores files as CTE tags and blobs, so anything written through a mount is visible to CEE without an import step:

  • Each file is a tag named by its path inside the mount.
  • File data is split into 1 MiB pages, one blob per page, named by page index (0, 1, ...). Each file also has a small attribute blob named ~i.
  • The filesystem pool (560.0) writes through the chain top at 563.0, so pages pass the indexer and are keyword-searchable when they are text.

So ctx.context_query(".*notes/.*", "[0-9]+", prompt="sea ice") ranks the pages of files under notes/. The blob pattern [0-9]+ keeps the ~i blob out. The limitation is that context_query returns blob names only, which for files are page numbers with no file name attached. For mounted files use clio_cte_core_ext directly: its BlobQuery returns (tag name, blob name) pairs and its search results carry the tag id. The query files from Python tutorial shows that path. context_retrieve does work on files, and returns the matched pages concatenated.

Composing storage for search

CEE has no configuration of its own. What it can find and how fast it can read depends on the chain composed in the runtime's YAML. The default context-runtime/config/clio_default.yaml already composes a working layout; the points below are what to keep when writing your own. Module pages document each key.

  • Keep the indexer in the chain, and route every writer through it. The default order is cache (563.0) to indexer (564.0) to optional compressor (562.0) to replication (561.0) to core (512.0). The CAE core (400.0), the filesystem (560.0) and the stream pool (565.0) all set next_pool_id: "563.0", so imports and files are indexed. A writer pointed at 512.0 bypasses the index. Scope the index with the indexer's tag_re and blob_re keys so binary data is not tokenized, and set index_log_path so the index survives a restart.
  • Add the summarizer for semantic labels. The summarizer (clio_cae_summarizer, pool 401.0 by convention) runs a prompt from label_prompts over each put that matches a label_matches rule and stores the reply as a sibling blob <blob>_label in the same tag. Give it next_pool_id: "563.0" so the label blob itself passes through the indexer, then point the CAE core's next_pool_id at 401.0. A BM25 prompt then matches the model's description as well as the raw text, and blob_re=".*_label" restricts a query to labels.
  • Give retrieval a fast tier. context_retrieve is a GetBlob per blob. Blobs land on the highest-scoring tier with room (storage[].score, capacity_limit on the core entry), and the cache at the chain top keeps a raw node-local copy of blobs read from other nodes. Data that an organizer or an explicit ReorganizeBlob has demoted is read from the slower tier; promote a working set with Tag.ReorganizeBlob(name, 1.0) before a large retrieve.
  • Bound the result. max_context_size is allocated in shared memory in full, so size it to what you will actually read rather than leaving the 256 MiB default for small queries.

Excerpt of a chain that satisfies all of the above (the core, replication and cache entries are as on the CTE core page):

compose:
  - mod_name: clio_cte_core
    pool_name: cte_main
    pool_query: local
    pool_id: "512.0"
    storage:
      - path: "ram::cte_ram_tier1"
        bdev_type: "ram"
        capacity_limit: "0g"
        score: 1.0
      - path: "${CLIO_STORAGE_ROOT}/cte_disk_tier.dat"
        bdev_type: "file"
        capacity_limit: "10GB"
        score: 0.2
        persistence_level: "temporary"

  - mod_name: clio_cte_replication
    pool_name: clio_cte_replication
    pool_query: local
    pool_id: "561.0"
    next_pool_id: "512.0"

  - mod_name: clio_cte_indexer
    pool_name: clio_cte_indexer
    pool_query: local
    pool_id: "564.0"
    next_pool_id: "561.0"
    index_log_path: "${CLIO_STORAGE_ROOT}/cte_indexer_index"
    tag_re: ".*"
    blob_re: ".*"

  - mod_name: clio_cte_cache
    pool_name: clio_cte_cache
    pool_query: local
    pool_id: "563.0"
    next_pool_id: "564.0"

  - mod_name: clio_cae_summarizer
    pool_name: clio_cae_summarizer
    pool_query: local
    pool_id: "401.0"
    next_pool_id: "563.0"
    label_endpoint: "http://127.0.0.1:11434"
    label_prompts:
      summarize: "Summarize the following text in one short sentence."
    label_matches:
      - tag_re: ".*"
        blob_re: ".*"
        model: "gemma3:1b"
        prompt: "summarize"

  - mod_name: clio_cae_core
    pool_name: cae_main
    pool_query: local
    pool_id: "400.0"
    next_pool_id: "401.0"

Each entry must come after the pool its next_pool_id names. Clients then set CLIO_CTE_POOL=563.0 or 564.0.

MCP server

context-exploration-engine/iowarp-cei-mcp/server.py is a Model Context Protocol server built on FastMCP. Despite the directory name it wraps the CTE Python module clio_cte_core_ext, not clio_cee, and runs inside the server process. It searches for the bindings in the build's bin directory, CTE_PYTHON_PATH and PYTHONPATH.

Tools, with their arguments:

  • get_client_status() and get_cte_types(): safe before initialization.
  • initialize_cte_runtime(): calls clio_init(RuntimeMode.kClient, True) and initialize_cte. With no CLIO_SERVER_CONF it writes a one-tier file-backed configuration under the temp directory and starts a private runtime; set CLIO_SERVER_CONF and CLIO_WITH_RUNTIME=0 in the server's environment to attach to an existing one instead. It also registers a 512 MB file target.
  • put_blob(tag_name, blob_name, data, offset=0), get_blob(tag_name, blob_name, size=0, offset=0) (UTF-8 text, or base64 for binary), get_blob_size(tag_name, blob_name), list_blobs_in_tag(tag_name), delete_blob(tag_name, blob_name).
  • tag_query(tag_regex, max_tags=0), blob_query(tag_regex, blob_regex, max_blobs=0), poll_telemetry_log(minimum_logical_time=0), reorganize_blob(tag_id_major, tag_id_minor, blob_name, new_score).

Every tool returns a JSON string. The README warns that the query tools crash the server if called before the runtime is initialized. There is no semantic or temporal search tool. Setup from the README:

$ cd context-exploration-engine/iowarp-cei-mcp
$ python3 -m venv venv && source venv/bin/activate
$ pip install -r requirements.txt
$ export PYTHONPATH=/path/to/build/bin:$PYTHONPATH
$ python3 test_mcp_tools.py        # exercises every tool over stdio

{
  "mcpServers": {
    "iowarp-cte": {
      "command": "python3",
      "args": ["/full/path/to/context-exploration-engine/iowarp-cei-mcp/server.py"],
      "env": { "PYTHONPATH": "/path/to/build/bin" }
    }
  }
}

Limits

  • context_splice is unimplemented.
  • context_query returns blob names without tag names; use clio_cte_core_ext.Client.BlobQuery when the tag matters.
  • The retrieve buffer has no framing.
  • Keyword search is exact-token BM25 over ASCII text; there is no embedding model. See the indexer page.
  • The MCP server exposes CTE operations, not the clio_cee methods, and has no search tool.

Tests

context-exploration-engine/api/test holds Catch2 tests for bundle, query (including the three modes in test_context_query_modes.cc) and destroy, plus Python tests test_context_interface.py, test_context_interface_enhanced.py and test_context_retrieve_roundtrip.py. All need a running runtime; the directory's clio_config.yaml is the configuration they use, and ctest -L cee runs the C++ ones.
