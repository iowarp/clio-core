The idea in four steps

A gpu_vector is split into fixed-size pages. Every page is stored in the Context Transfer Engine, which puts it in RAM, on NVMe or on disk depending on the tiers you configured. The GPU only keeps the pages a kernel is working on right now. Inside the kernel, each page goes through the same four steps:

  1. Fetch

    Ask for a range of elements. The page that holds them is copied into the GPU cache and pinned so it cannot be evicted.

  2. Hold

    Get a pointer into the cached page and read or write it like an ordinary array.

  3. Flush

    Write the elements you changed back to the CTE. Nothing is written back automatically.

  4. Unpin

    Release the page so its slot in the cache can be reused for the next one.

The program has two halves. The CPU side starts the runtime, creates the vector, fills it, launches the kernel and reads the result. The GPU side is the kernel, which does the four steps above. The example below doubles every element of a 256 MiB vector of floats through a 64 MiB cache on the GPU.

GPU side: the kernel

The work is written as a device coroutine (YCoroMain). Each co_await is a point where the block may pause while the CPU completes a transfer; the GPU runs other blocks in the meantime. Each block walks its own share of the pages, one page at a time.

namespace gv = clio::cte::gpu_vector;
namespace gy = clio::run::gpu;
using clio::run::u32;
using clio::run::u64;

// Block `block` of `nblocks` doubles pages block, block + nblocks, ...
__device__ gy::YCoroMain DoublePages(gv::DeviceVector v,
                                     u32 block, u32 nblocks) {
  const u64 epp = v.ElemsPerPage();                 // elements per page
  for (u64 pg = block; pg < v.NumPages(); pg += nblocks) {
    const u64 off = pg * epp;                       // first element of the page
    const u64 count = (v.size() - off < epp) ? v.size() - off : epp;

    co_await v.Fetch(0, off, count);                // 1. bring the page in, pin it
    {
      auto h = co_await v.HoldPage(off, count, /*write=*/true);  // 2. hold it
      for (u64 i = off + threadIdx.x; i < off + h.run(); i += blockDim.x) {
        h[i] = 2.0f * h[i];                         // h is indexed by absolute offset
      }
    }
    co_await v.Flush(0, off, count);                // 3. write the page back
    v.UnpinRange(off, count);                       // 4. let the cache reuse the slot
  }
}

// The kernel entry point. The four lines before CLIO_YCORO_RUN are the same
// in every gpu_vector kernel.
__global__ void DoubleKernel(clio::run::IpcManagerGpuInfo info,
                             gv::DeviceVector v, u32 nblocks,
                             gy::YieldableView<> yv, gy::YieldStackView ys) {
  CLIO_GPU_INIT(info, nullptr);                 // connect the kernel to the runtime
  v.Init(yv.Block());                           // yv.Block() is this block's id
  gy::YieldTlsPublish(ys, yv.Y(), yv.Block());  // where the coroutine saves its state
  __syncthreads();
  CLIO_YCORO_RUN(DoublePages(v, yv.Block(), nblocks));
}
Ranges are in elements
Fetch(0, off, count) means elements [off, off + count). The leading 0 is the generation; 0 is an ordinary transfer. One call can name up to eight (off, count) pairs.
A hold is a page-sized window
h.run() is how many of the requested elements lie on this page, and h[i] takes the absolute element offset, the same number you passed to Fetch.
The whole block calls together
Every DeviceVector call is block-collective. All threads run the loop and split the elements between them with threadIdx.x; never wrap a co_await in if (threadIdx.x == 0).
Use yv.Block(), not blockIdx.x
A block that pauses is relaunched later, possibly as a different CUDA block. yv.Block() stays the same across relaunches.

CPU side: create, fill, launch, read back

The host never touches pages directly while the kernel runs. It creates the Vector, which allocates the GPU cache, hands the kernel a DeviceVector by value with GetDevice(0), and runs the kernel through the yield driver. The driver relaunches paused blocks until every block has finished.

#if !CTP_IS_DEVICE_PASS   // host-only code: skipped when clang compiles for the GPU
int main() {
  // 1. Start a runtime in this process (or attach to one) and the CTE client.
  if (!clio::run::CLIO_INIT(clio::run::RuntimeMode::kClient, true)) return 1;
  if (!clio::cte::core::CLIO_CTE_CLIENT_INIT()) return 1;
  auto gpu_info = CLIO_CPU_IPC->GetGpuIpcManager()->GetGpuInfo(/*gpu=*/0);

  // 2. Create the vector: 64M floats (256 MiB) in 1 MiB pages, on GPU 0.
  //    The cache has nblocks sets of set_size pages: 8 x 8 = 64 MiB.
  const u64 n = 64ull << 20;
  const u64 page_bytes = 1ull << 20;
  const u32 nblocks = 8, nthreads = 32;
  gv::Vector vec("doubled", /*gpu_ids=*/{0}, page_bytes,
                        nblocks, /*set_size=*/8, n);

  // 3. Fill it from the host. This writes straight to the CTE.
  std::vector data(n, 1.5f);
  vec.Preload(data.data(), n);

  // 4. Launch the kernel and run it until every block is done.
  gy::Yieldable<> driver(nblocks, nthreads);
  gy::YieldStack stack(nblocks, nthreads, /*bytes_per_lane=*/8192);
  driver.RunToCompletion(
      [&](dim3 grid, dim3 block, gy::YieldableView<> yv) {
        DoubleKernel<<>>(
            gpu_info, vec.GetDevice(0), nblocks, yv, stack.View());
      },
      [] {}, /*max_rounds=*/200000, gv::ResumeWhenComplete);
  ctp::GpuApi::Synchronize();

  // 5. Read the result back. Every page was flushed by the kernel.
  vec.Download(data.data(), n);
  bool ok = (data[0] == 3.0f && data[n - 1] == 3.0f);

  clio::run::CLIO_RUNTIME_FINALIZE();
  return ok ? 0 : 2;
}
#endif
Vector(tag, gpu_ids, page_bytes, nblocks, set_size, n)
The tag names the vector in the CTE; open the same tag again and you get the same data. nblocks must match the number of blocks you launch, because each block gets its own transfer slots. The cache holds nblocks * set_size pages by default.
Preload and Download
Move data between a host array and the CTE, bypassing the GPU cache. For data that never fits in host memory either, PreloadPages and DownloadPages take a callback per page.
The yield driver
Yieldable launches the grid, and after the kernel returns it relaunches only the blocks that paused on a transfer. gv::ResumeWhenComplete holds a paused block back until its transfer has actually finished. YieldStack is where paused coroutines keep their state; 8192 bytes per thread is what the adapter's tests use.

Compile with clang

The co_await calls in the kernel are C++20 coroutines running on the GPU. nvcc cannot compile coroutines in device code, so gpu_vector needs clang as the CUDA compiler. clang compiles the same source file twice, once for the CPU and once for the GPU. That is why the host code above sits inside #if !CTP_IS_DEVICE_PASS: the GPU pass skips it.

nvcc builds have no gpu_vector

Without CLIO_GPU_CLANG=ON the configure step prints that gpu_vector is disabled and builds nothing for it. The CUDA pip wheel is compiled with nvcc, so it does not include gpu_vector either. Build from source.

Configure CLIO Core with CUDA and clang. CMake finds the newest clang++ on the path (clang++-22 is what the tree is tested with), or you can name one:

$ cmake -S . -B build-gv -G Ninja -DCMAKE_BUILD_TYPE=Release \
    -DCLIO_CORE_ENABLE_CUDA=ON -DCLIO_GPU_CLANG=ON \
    -DCMAKE_CUDA_COMPILER=clang++-22          # optional; found automatically
$ cmake --build build-gv -j"$(nproc)"

In that build tree, add your program the way the adapter's own tests are added. add_cuda_executable marks the source as CUDA, so it goes to clang with the C++ standard and GPU architecture CLIO Core was configured with:

add_cuda_executable(scale_example FALSE
    scale_example.cc
    INCLUDE_DIRS
        ${CMAKE_SOURCE_DIR}/context-runtime/include

        ${CMAKE_SOURCE_DIR}/context-runtime/modules/bdev/include

    LINK_LIBS

On Intel GPUs the oneAPI compiler is already clang-based: configure with -DCLIO_CORE_ENABLE_SYCL=ON and icpx, and the same DeviceVector calls work from a SYCL kernel lambda. Run it

The runtime needs a CTE pool with at least one storage tier big enough for the vector. Save this as clio.yaml and point CLIO_SERVER_CONF at it:

gpu:
  queue_depth: 64            # more than the number of blocks you launch
compose:
  - mod_name: clio_cte_core
    pool_name: clio_cte
    pool_query: local
    pool_id: 512.0
    storage:
      - path: "ram::vector_dram"
        bdev_type: "ram"
        capacity_limit: "1GB"
        score: 1.0
    dpe:
      dpe_type: "max_bw"

$ CLIO_SERVER_CONF=$PWD/clio.yaml ./build-gv/bin/scale_example; echo "exit $?"
exit 0

If a kernel stops with a trap, call gv::FatalReport() on the host. It returns the reason, such as a hold over a page that was never fetched or a cache set with every slot pinned.

Rules that keep a kernel working

  • Flush before you unpin. There is no dirty bit. A page evicted before it was flushed loses its writes.
  • Unpin everything you fetch. A pinned page can never be evicted; a set full of pinned pages stops the next fetch.
  • Hold only what you fetched. HoldPage never fetches. Holding elements that no fetch named stops the kernel.
  • Size the cache for your blocks. Give each set at least as many slots as blocks that may hold a page of it at once, and set gpu.queue_depth above the block count.
  • Several blocks may share a page. Each flushes only the elements it wrote, so they do not overwrite each other.

Overlap transfers with compute

Fetch and Flush each have a split form. Start the next page's fetch, work on the current page, then wait:

co_await v.BeginFetch(0, next_off, next_count);   // submitted; returns at once
/* ... compute on the page you already hold ... */
co_await v.AwaitFetch();                          // now the next page is in

co_await v.BeginFlush(0, off, count);             // start writing this page back
/* ... compute ... */
co_await v.EndFlush();                            // wait for the write

For moving pages between storage tiers ahead of the kernel, see prefetch hints on the usage page.
