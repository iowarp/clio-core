What it is

The runtime, started with clio_run start, loads shared libraries called ChiMods, creates pools of them, and serves tasks that clients submit to those pools. A client is any process that calls CLIO_INIT: a Python script, the FUSE daemon, an MPI rank, or another module inside the runtime. The runtime also serves a web dashboard and, in a cluster, talks to the runtimes on the other nodes listed in its hostfile.

Key concepts

  • Module (ChiMod). A directory with a clio_mod.yaml, a set of task structs, a client library that programs link, and a runtime library the daemon loads. It defines numbered methods; ids 0 to 9 are reserved for Create, Destroy and Monitor.
  • Pool and container. A pool is a running instance of a module with a name and a major.minor id. A container is the pool's instance on one node; the container id equals the node id, and the number of containers is fixed by the hostfile. Two pools of one module can run side by side with different settings.
  • Task. A method call on a pool: a struct with input and output fields. A task lives in the submitting process; its inputs are serialized into a buffer that crosses into the runtime, and only its outputs come back. Tasks are not shared memory.
  • Coroutine handlers. A container's handler for a method is a coroutine. When it awaits a subtask or a device, its worker thread runs other tasks. The runtime supports C++20 stackless coroutines and, with CLIO_CORE_ENABLE_BOOST_COROUTINES, Boost.Context fibers behind the same macros.
  • Pool query. Every task carries a PoolQuery that says which containers run it: this node, one container by id or hash, a range, every container, a specific node, or wherever the module decides. Collective queries fold tasks from many submitters into one run.
  • Transports. A client reaches the runtime over shared memory on the same machine, a Unix socket when shared memory is unavailable, or TCP across machines and containers, chosen automatically unless CLIO_IPC_MODE says otherwise. Runtimes talk to each other over TCP. GPU kernels can submit tasks through a GPU queue.
  • Interposition. A module can stand in front of another, handle some methods and forward the rest to its next_pool_id. The cache, indexer, replication and compressor modules are built this way.
  • Compose file. The compose: list of the configuration names the pools to create at startup, in order. clio_run compose start and stop create and destroy the pools of another file while the runtime keeps serving.

Scheduling

The runtime starts runtime.num_threads worker threads (four by default). Worker 0 is the scheduler worker; with four or more threads the last two are a network send worker and a network receive worker,, and a GPU-polling worker is carved out when there are enough threads. The rest form one pool of general workers. The default scheduler books every task at the time it is predicted to hold a worker, learned per module and method from observed run times. A task stays on the worker that submitted it if that worker has room, otherwise it goes to the least-loaded worker, and when no worker has room the pool grows by one. A monitor thread, every 500 ms, rescues the backlog of a worker stuck on one task, lets idle workers steal work, and retires idle extra workers. The scheduler is a replaceable component; see Write a scheduler and Design.

Modularity and extensibility

The runtime itself does no storage, search or computation. Everything it serves comes from modules, including the block devices and the admin module that creates other pools. Writing a custom ChiMod is how you add a capability, and a custom module is a peer of the built-in ones: it runs on every node, takes part in scheduling and failure handling, and can sit in the storage chain.

  • A runtime half and a client half. A module builds two shared libraries. The runtime library, which the daemon loads, holds the container class whose coroutine handlers run each method. The client library, which applications link, gives them a typed call per method that builds a task and submits it.
  • Declared, then generated. A clio_mod.yaml names the module and lists its methods with their numbers. clio_run refresh regenerates the dispatch code that maps method numbers to handlers.
  • Built outside the tree. Modules build against an installed CLIO Core with its CMake package; no fork is needed.
  • Found at startup. The runtime scans its own library directory, CLIO_REPO_PATH, LD_LIBRARY_PATH and a few defaults for libraries whose names contain _runtime, and loads them.
  • Composed at run time. Pools of a loaded module are created and destroyed while the runtime serves, from a client, the compose file or clio_run compose start/stop. A new module library, or a new version of one, is picked up by restarting the runtime; clients reconnect on their own and durable pools are recreated.
  • Hooks beyond methods. Optional callbacks let a module migrate, recover and re-partition its data, predict its own task costs, aggregate collective requests, add pages and endpoints to the dashboard, and run on GPUs.

Usage builds a module step by step, and Extending the runtime covers schedulers, monitoring and the other extension points.

Elasticity and failure handling

  • Durable pools. Pools created from the compose file, or with restart: true, are recorded in each node's pool log and recreated by the next clio_run start. --fresh discards the log with the rest of the node's state.
  • Adding nodes. clio_run start --induct registers a node with an existing cluster. Every container receives an Expand callback and may re-partition its data.
  • Migration and recovery. A container can be moved with its Migrate callback (clio_run migrate), and rebuilt on another node after a node loss with Recover; ScheduleRecover lets the module choose where. The defaults do nothing beyond re-initialising, so a module that holds state must implement them.
  • Restarted peers are detected from an incarnation number on every message. Requests in flight to the old incarnation fail and are retried.
  • Silent peers are probed and declared dead after CLIO_PROBE_SILENCE_S seconds (default 30). A send to an unreachable peer is retried for CLIO_NET_RETRY_TIMEOUT_S seconds (default 30) before its task fails; CLIO_NET_DEAD_FAIL_FAST=1 fails tasks to a dead peer at once.
  • Gossip detection (the swim section) exists but is off by default, because wide collectives starved its probes at scale. With it off, a dead node produces failed tasks, not automatic container recovery. Data availability across node loss comes from the replication module.
  • Clients survive a restarted runtime. A heartbeat detects the loss, the client waits for the runtime to return, reconnects and resends. The runtime reclaims the shared-memory segments of dead clients after runtime.client_reap_grace_s seconds.

How it relates to the other technologies

  1. Front endsContext FS, memory expansion, machine learning, CAE, CEE
  2. InterceptorsPOSIX, STDIO, MPI-IO and HDF5 adapters; FUSE mount
  3. ChiMod chainCache, replication, compressor, indexer, summarizer
  4. CTE coreTags, blobs, placement across tiers
  5. Context RuntimeModules, pools, tasks, scheduling, transports
  6. StorageBlock devices: RAM, NVMe, SSD, HDD, S3/GCS

The runtime is the floor that every other layer stands on: each box above it, and the block devices below it, is a module running inside it. It relies only on the operating system, shared memory and the network.

  • Context Transfer Engine: the core, cache, indexer, replication, compressor and block-device modules. The runtime's block-device module, clio_bdev, is what every storage tier is built on.
  • Context FS: the filesystem and stream modules, plus the FUSE daemon, which is a runtime client.
  • Context Assimilation Engine and Context Exploration Engine: modules and clients for importing and querying data.
  • Memory expansion: paged vectors whose pages are tasks on the CTE pools, including tasks submitted from GPU kernels.
  • Machine learning: clio-ml algorithms that run over those vectors.
