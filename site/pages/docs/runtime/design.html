The pieces at a glance

The managers

Config manager
Reads ~/.clio/clio.yaml (or the file named by the environment), the hostfile and the compose list, and applies environment overrides. Everything else asks it for settings such as the thread count, the scheduler name and the ports.
Module manager
At startup, scans the runtime's own library directory, CLIO_REPO_PATH, LD_LIBRARY_PATH and default paths for shared libraries whose names contain _runtime, opens each one, and records its factory functions. It can then construct a container of any loaded module by name. On load it also builds a throwaway prototype container so the module can register its dashboard pages before any pool exists.
Pool manager
Owns the table of pools and their local containers. It creates and destroys pools on request from the admin module, resolves a task's pool id and PoolQuery to a container (here or on another node), saves and restores each container's learned cost model, and hands containers to workers through a lightweight handle cached at routing time.
IPC manager
Owns every way a task can enter or leave the process, described below, plus node identity, peer liveness and the heartbeat clients use to notice a restarted runtime.
Work orchestrator
Spawns and owns the worker threads and their lanes, holds the active scheduler, and runs the monitor thread that calls the scheduler's load-balancing hook every 500 ms.
Viz server
A small HTTP server with its own thread pool. It serves the dashboard, a registry of REST routes that modules add, and static assets a module ships in a viz/ directory.

Tasks and futures

A task is a C++ struct with input and output fields plus a header: its pool, method, PoolQuery, flags and return code. Submitting a task returns a future. The future's completion flag lives in memory both sides can see, so a caller in another process or on a GPU can wait for it without a message. Only inputs travel toward the container and only outputs travel back: tasks are serialized at every process boundary and are never shared objects.

Inside the runtime a handler that submits a subtask passes it by pointer, with no serialization, and co_awaits its future. When the subtask completes, the parent coroutine is put back on its worker's queue.

Transports and queues

The IPC manager picks a transport for each direction a task can travel. Every transport has the same four steps: send the input, receive the input, send the output, receive the output.

Worker lanes are multi-producer, single-consumer ring buffers: any thread may push, and only the owning worker pops. A worker that would push onto its own full lane is redirected to another worker, so a full queue becomes back-pressure instead of a deadlock.

Workers, coroutines and the scheduler

Each worker loops over its lane, its blocked queue (coroutines waiting on a subtask or a device), its retry queue and its periodic tasks. Running a task means resuming its handler coroutine until it finishes or suspends. Handlers are C++20 stackless coroutines; with CLIO_CORE_ENABLE_BOOST_COROUTINES they are Boost.Context fibers behind the same macros, which allows suspending from nested ordinary functions at the price of a stack per task.

Roles are fixed by position. Worker 0 is the scheduler worker. With four or more threads the last two are the network send and receive workers, so send-side back-pressure never stops incoming replies and probes from draining. A GPU worker is carved out before them when there are enough threads, and otherwise shares the scheduler worker. The rest are general workers.

The scheduler is an object behind a small interface, chosen by runtime.local_sched. The default one predicts how long each task will hold a worker, using a per-method linear model that each container learns from measured run times and that the pool manager saves to disk between runs. It keeps each worker below about 100 µs of booked work: a task stays on the submitting worker when it fits, otherwise it goes to the least-loaded worker, and when nothing fits the pool grows by one thread. Every 500 ms the monitor thread treats a worker stuck in one task for over a second as stalled, starts a replacement and moves its backlog, lets idle workers steal, and retires idle extra threads. The local scheduler maps tasks by a hash of the submitting process and thread and never rebalances. Write a scheduler describes the interface.

Pools, containers and routing

A pool has one container per node, and the container id is the node id. When a task is routed, its PoolQuery selects containers: the local one, one by id or hash, a range, all of them, a physical node, or a collective. Tasks for this node go to a worker lane; tasks for another node go to the network send worker. A module that holds data receives Expand when a node joins, so it can re-partition, and Recover when a container is rebuilt on another node.

Collectives. A ManyToOne or AllToOne query sends each submitter's task to a leader, where the batch manager parks it, grouped by pool, method, target and batch key. When the batch window closes, it builds one aggregate task by folding each member's inputs in through the container's AggregateIn, runs it once, and copies the output back into every member. A thousand ranks asking for the same thing cost one execution.

What persists

  • The restart log is an append-only log of the compose files that should be re-composed at the next clio_run start. Pools created with restart: true are recorded the same way. --fresh discards it.
  • Cost models are saved per module, pool, node and container, flushed about once a second while they change and on shutdown, and restored when the container is recreated, so a restarted runtime schedules well from the first task.
  • Module state is the module's own business: the CTE keeps its metadata log, a block device its allocation log. A container's recovery callback is where it reloads them.

The dashboard

The viz server answers built-in routes such as /api/health, /api/topology, /api/pools, /api/config, /api/chimods and /api/routes (the list of every registered route). Module routes and asset directories are added at load time. Handlers run on the server's own threads, not on workers, so a slow page never delays a task; they may submit a task and wait for it.
