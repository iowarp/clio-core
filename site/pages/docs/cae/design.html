The pieces

A transfer, step by step

  1. Load. The clio_cae tool's OMNI loader reads the YAML, expands each entry into an assimilation context (source, destination, format, range, dataset filters, credentials) and submits the list as one ParseOmni task. The CEE and the language clients build the same contexts directly.
  2. Choose. In the runtime, the core asks the assimilator factory for the class that handles each source's scheme.
  3. Assimilate. The assimilator's schedule coroutine reads the source and puts blobs into the destination tag through the CTE client: 1 MiB chunk_N blobs for files, one tag per dataset for HDF5, one blob for a string. Puts go to the CAE's next_pool_id, so imports pass the cache, indexer and replication like any other write.
  4. Finish. Transfers run in order, each completing before the next starts, and the task returns one status.

Assimilators

An assimilator is a C++ class implementing a small base interface. Besides scheduling a whole transfer, it can optionally produce the bytes of one destination blob on request (for ingest on fault) and describe the source's page layout (for pagify). The shipped ones cover local files, inline strings, HDF5, HTTP and HTTPS, S3 (with a pooled keep-alive connection set and forwarded credentials, since the daemon does not inherit the client's environment), Google Cloud Storage and Globus. Extending the CAE adds a new one.

Ingest on fault

With on_fault set, a transfer copies nothing. The core records the context in a registry under a hashed id, and the destination carries that id as its fault parameters. When a read misses a blob, the CTE sends the CAE a fault task carrying the id; the core looks up the context and asks the source's assimilator for exactly that blob, stores it, and lets the read continue. Source reads can take seconds on a parallel filesystem, so they run on a separate pool of threads (32 by default, CLIO_CAE_REF_IO_THREADS) while the fault task yields, keeping runtime workers free. CLIO_CAE_FAULT_STATS=1 logs per-stage counters every five seconds.

Pagify and page maps

Paged consumers such as memory expansion and clio-ml address data only as page 0, 1, 2 and so on. A page map, produced by the assimilator that knows the source layout, is an ordered list of extents saying which bytes of which blob occupy which range of page space. Pagify uses it to build a page: it fetches the slices, composes pages made of several blobs, and zero-fills uncovered ranges. The split keeps the arithmetic pure and testable and the I/O injectable.

The summarizer

The optional summarizer module is a CTE interposer: it forwards every operation, and after a matching put sends the content to a language model endpoint (by default a local Ollama server) and stores the label as a sibling blob. The model call runs inline on the put's task, so every matching put waits for the model. Enable it only for data you want described.
