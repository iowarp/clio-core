What the CAE is

Everything in CLIO Core stores data as CTE tags holding blobs. The CAE is the part that turns something else, a file on disk, a dataset in an HDF5 file, an object in a bucket, a string in a program, into tags and blobs, so that it can then be tiered, replicated, searched and mounted like data written through the normal client. It also hosts the modules that attach meaning to data as it flows: labels produced by a language model, a keyword index, and page maps that let a consumer address an ingested file by page number.

The CAE core is a pool in the runtime. The default configuration composes it at pool 400.0 with next_pool_id set to 563.0, the top of the interposition chain, so imported data passes through the indexer and becomes keyword-searchable. Its reference page is CAE core.

Kinds of modules

Two kinds of code extend the CAE.

Assimilators, one per source scheme

An assimilator reads one kind of source and writes it into a destination tag. The scheme of the src URL selects it: everything before ://, or before :: for the custom forms. The factory in assimilator_factory.cc maps schemes to classes:

  • file::/path: the binary file assimilator. Reads a local file in chunks and stores blobs named chunk_0, chunk_1, and so on. Byte ranges apply.
  • string::name: an inline payload carried in the request's src_data, stored verbatim as one blob named by the part after the scheme.
  • hdf5::/path.h5: each dataset becomes a tag named <dst>/<dataset path>, large datasets are split into several blobs, and include and exclude glob patterns select datasets. Needs CLIO_CORE_ENABLE_HDF5=ON.
  • http:// and https://: a web download through a curl child, POSIX builds only. A URL under https://app.globus.org is handed to the Globus assimilator instead.
  • s3://bucket/key: Amazon S3 or a compatible store, with credentials, region and endpoint from the runtime's AWS environment. Needs CAE_ENABLE_S3=ON.
  • gs:// or gcs://bucket/object: Google Cloud Storage through Application Default Credentials. Needs CAE_ENABLE_GCS=ON.
  • globus://: a Globus endpoint, with the access token from src_token or GLOBUS_ACCESS_TOKEN. Needs CAE_ENABLE_GLOBUS=ON.

A scheme whose support was not compiled in logs an error naming the CMake option to turn on, and the factory returns no assimilator.

Interposers on the CTE task interface

An interposer is a module that speaks the CTE core's own task interface, forwards every operation to the pool named by its next_pool_id, and does something extra on the way. The CAE ships one, the summarizer, which runs a language-model prompt over matching blobs after each put. The CAE core itself behaves as an interposer for GetOrCreateTag, PutBlob, GetBlob and SemanticSearch. The chain layers under Modules (cache, indexer, replication, compressor) follow the same pattern and are what the CAE forwards into.

Adding an assimilator

Assimilators live in context-assimilation-engine/core: an interface header under include/clio_cae/core/factory/ and an implementation under src/factory/. The interface is BaseAssimilator in base_assimilator.h:

  • Schedule(ctx, error_code), required. A coroutine that reads the source described by an AssimilationCtx and puts blobs into the destination tag through the CTE client. It uses co_await for CTE operations and reports failure through the output parameter.
  • ReadBlob(ctx, blob_name, dst, cap) and BlobBytes(ctx), optional. Together they let the assimilator ingest one blob at a time for ingest-on-fault. ReadBlob is plain blocking I/O with no tasks and returns the byte count, 0 past the end of the source, or a negative errno. The default returns -ENOSYS, meaning "cannot ingest per blob".
  • BuildPageMap(ctx, page_size), optional. Publishes how the source maps onto a page space for pagify. The default returns an empty map, meaning the assimilator does not support paged access.

The context an assimilator receives is AssimilationCtx in assimilation_ctx.h: src, dst, format, depends_on, range_off, range_size, src_token, dst_token, src_data, the S3 s3_region and s3_profile hints, the dataset include_patterns and exclude_patterns, and the ingest-on-fault fields on_fault, chunk_size and blob_prefix.

To add one: subclass BaseAssimilator, implement Schedule, and add a branch for the new scheme in AssimilatorFactory::Get in src/factory/assimilator_factory.cc. Sources that need an SDK follow the existing pattern of a CMake option and an #ifdef around the include and the factory branch, so a build without the SDK still compiles and reports the missing option at run time. The string and binary assimilators are the smallest examples to copy.

Assimilating diverse formats with OMNI files

An OMNI file is a YAML list of transfers. Each transfer names a source, a destination tag and a format, and the clio_cae tool submits the list to the CAE pool as one ParseOmni task. Transfers run in order, each finishing before the next starts.

name: import_results

transfers:
  - src: file::/data/run42/field.bin
    dst: iowarp::run42_field
    format: binary
  - src: hdf5::/data/run42/diagnostics.h5
    dst: iowarp::run42_diag
    format: hdf5
    dataset_filter:
      include_patterns: ["/temperature/*"]
  - src: s3://my-bucket/reference/baseline.bin
    dst: iowarp::baseline
    format: binary

$ clio_run start &
$ clio_cae transfers.yaml

The tool initializes a client of the running runtime, loads the file, executes any run preprocessing steps locally, then waits for ParseOmni. It exits non-zero when the assimilation result code or the task framework code is non-zero, and also when transfers were requested but zero assimilations were scheduled. Its success message says that assimilation is scheduled, not complete: dataset-level errors such as a full tier are logged by the runtime, not the tool. Confirm the blobs landed by listing the destination tag or searching for it.

The format field takes binary, hdf5, hdf5_vol or globus. hdf5_vol stages a file in the layout the CTE's HDF5 VOL connector expects, so an application opening it through the connector is served from the CTE from its first read. Every per-transfer key (depends_on, range_off, range_size, src_token, dst_token, dataset_filter, run, run_out) is described on the CAE core page. Cloud credentials are read by the runtime process, so set them where the runtime runs. The cloud storage tutorial walks through S3 and Google Cloud imports.

Describing content live in the I/O path

Because the CAE core and the summarizer speak the CTE's task interface, they can be placed where ordinary puts and gets pass through them, and describe data as it is written rather than in a later pass.

  • CAE as interceptor. Compose clio_cae_core at the CTE's entry pool ID, 512.0, with next_pool_id pointing at the real core or at another interposer. A CTE client or the filesystem pointed at 512.0 then runs through the CAE without changes. Only the four data-path operations are mirrored, so this placement is used in the dedicated interceptor configurations, not in the default file, where the CAE sits at 400.0 beside the chain.
  • Summarizer labels. clio_cae_summarizer forwards every verb and, after a successful PutBlob whose tag and blob names match a rule in label_matches, sends the bytes to the model named by the rule and stores the reply as {blob_name}_label in the same tag with the same placement score. The label is an ordinary blob, so anything that reads blobs can read it. Rules, prompts, the Ollama and OpenAI-compatible backends and chunking are on the summarizer page.
  • Indexer. The chain's clio_cte_indexer at 564.0 owns the term index behind SemanticSearch. A put through it enqueues a dirty key and is forwarded unchanged; a periodic sweep tokenizes the data, and a search drains the queue first. Imported data reaches it because the default CAE entry forwards to the chain top rather than the bare core. Labels written by the summarizer are indexed the same way when the summarizer sits above the indexer.

A chain that does all three, from the summarizer labeling test, is: CAE core at 512.0, then the summarizer at 401.0, then the CTE core. The operators tutorial shows how to enable the summarizer in the default file.

Ingest on fault

A transfer context can be marked on_fault. ParseOmni then ingests nothing. Instead it records the context under a key of the form fault:<16 hex>, a hash of the context, publishes that record as a blob in the registry tag __cae_on_fault so every node can read it, and registers the CAE pool as the destination tag's fault handler on every CTE container, using the CTE's GetOrCreateTag variant that takes a fault pool and fault parameters.

From then on, a GetBlob for a blob the tag does not hold is dispatched by the CTE to the CAE's GetBlob handler with the key in the context's fault_params_. The handler:

  1. Looks the key up in memory, or, when the registration was made on another node, loads the context from the registry tag.
  2. Calls the source assimilator's ReadBlob for exactly that blob, on a separate I/O thread pool because it is blocking source I/O. A short final blob is zero-filled past the end of the source, like a page.
  3. Stores the blob in the tag with a put flagged kNoFault, so the next read does not fault, then serves the read from the staged bytes. A size-0 request, which the CTE sends before a partial write, only stores.

Blob size and naming come from the context: chunk_size bytes per blob (0 means the assimilator's default) and blob_prefix followed by the blob index. The default prefix is chunk_; an empty prefix names blobs 0, 1, and so on, which are the page names a gpu_vector pager faults on. The binary file assimilator implements ReadBlob; an assimilator without it fails the fault with ENOSYS.

Ingested-on-fault blobs can always be re-ingested, so they are not allowed to take the last of a tier. The handler keeps CLIO_CAE_FAULT_RESERVE_MB (default 512) free across the node's targets and serves from the source without storing when a store would cross that line. A failed store drops the partial blob, serves from the source for the next 256 faults, then tries again. CLIO_CAE_FAULT_STORE=0 turns storing off entirely, giving pure read-through. on_fault is not an OMNI key; programs that build contexts in code set it, and the loader does not read it from YAML.

The same CTE fault mechanism is used elsewhere in the stack without the CAE. The cpu_vector and gpu_vector adapters implement Copy() as a lazy copy-on-write checkpoint: they create the copy's tag with the checkpoint module registered as its fault handler and the source tag's name as the fault parameter, so a page of the copy is materialized from the source the first time anything touches it. The vectors themselves page data into host or device memory on demand, and the HDF5 VOL binds its tag lazily on first access.

Pagify: numbered pages over named blobs

A paged consumer such as the gpu_vector addresses its data as page 0, page 1, page 2, and knows nothing about blob names. Pagify is the CAE layer that turns a page number into bytes. It is split into two parts in page_map.h and pagify.h:

  • PageMap is pure arithmetic: a list of extents, each saying which bytes of which blob land at which page offset. ToPage returns the slices composing one page, and FromPage returns the pages holding a byte range of one blob. The map serializes to a string.
  • Pagify does the I/O over a map with injected read and write callables, so the assembly is testable without a runtime and the same code serves the CAE pool, a direct client or a test stub.

At run time the mapping travels with the data: the serialized map is stored as a plain blob named pagemap in the same tag as the data. The BuildPageMap hook on BaseAssimilator is where an assimilator produces that map, but none of the shipped assimilators overrides it yet; today the map is written by the program that ingests the data, as the pagify test does. The CAE core's GetBlob handler treats a blob name of the form page:<id> as a page request: it loads the tag's pagemap blob once, zeroes the caller's buffer, and reads every slice of that page directly into its place in the buffer. A page composed of several blobs, a blob covering only part of a page, and gaps covered by no extent all read correctly, with gaps as zero. A tag with no pagemap blob fails the page read with a warning. Any blob name without the prefix forwards unchanged, so pagify is opt-in per request and costs an unpaged deployment one string comparison.

The end-to-end test in test/unit/test_cae_pagify.cc writes four blobs and a map into a tag, then reads page:0 and page:1 through a CTE client pointed at the CAE pool: page 0 is assembled from three blobs, and page 1 holds 1000 bytes at offset 500 with zeros around them.
